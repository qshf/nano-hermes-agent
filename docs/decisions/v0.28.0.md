## 0. 一句话

`raise New(...) from exc` 把原始异常挂到 `__cause__`，traceback 显示完整
"X 导致 Y" 链路。本档只在**链全挂抛 `FailoverExhausted` 的两处**补上 cause——
让排障时能直接看到压垮链的最后一个真实底层异常（`ConnectionError` /
`TimeoutError` …），而不是只剩一句聚合的 "All transports failed: ..."。

---

## 1. 改了什么（2 处，同一文件）

`transports/chain.py`，同步 `call()` 与流式 `stream_call()` 各一处：

```python
raise FailoverExhausted(attempts) from (errors[-1] if errors else None)
```

两处都在 `for entry in self.entries` 循环**耗尽后**抛出，本身**不在** `except`
块内（在循环外）。原始异常埋在循环内部：
- **sync 路径**：原始 exc 在 `_try_with_retry()` 的 `except Exception as exc` 里被
  捕获，分类后 `return None` 吞掉——异常对象本身没带出来。
- **stream 路径**：原始 exc 在 `stream_call` 自己的 `except Exception as exc` 里，
  但 Python 在 except 块结束后会删除 `exc` 绑定，循环外拿不到。

### 做法：平行收集列表带出原始异常

既有 `attempts: list[ClassifiedError]` 收集每次失败的**分类结果**（用于日志/消息），
但 `ClassifiedError` 是 dataclass，**不持有原始异常对象**（只有 reason/status_code）。
所以新增一个平行列表 `errors: list[BaseException]`，和 `attempts` 同生命周期、同
append 点收集原始 exc，循环耗尽时取 `errors[-1]`（最后一家的最后一次失败）作为 cause：

- `call()` 开头声明 `errors`，传入 `_try_with_retry(entry, kwargs, attempts, errors)`。
- `_try_with_retry()` 签名加形参 `errors: list[BaseException]`，在它的 except 里
  `errors.append(exc)`（与 `attempts.append(classified)` 紧挨）。
- `stream_call()` 开头声明 `errors`，在它自己的 except 里 `errors.append(exc)`。

`errors[-1] if errors else None`：理论上抛 `FailoverExhausted` 时 errors 必非空
（链耗尽必有失败），但断路器全开导致**所有 entry 都被 skip、一次都没真调**时
errors 为空——此时 `from None` 显式切断链路，语义正确（没有原始异常可挂）。

### 补：cause 的出口（消费点 logger）

挂 `__cause__` 只是把因果挂到**异常对象**上；要真能被追溯，得有人读它。审核时发现
原本两个消费点只 `print(e)`，打的是 `FailoverExhausted` 自己的聚合 message，
**`__cause__` 从没被展开**——cause 挂了等于没出口。所以本档在两处消费点补一行
`logger.error(..., exc_info=True)`（traceback 标准展开 `__cause__`，落进 v25.1
结构化日志），给用户的 `print` 一行摘要保持不变：

- `agent/turn_loop.py` `except FailoverExhausted`（同步/流式主路径）——顺带补了该文件
  缺失的 module logger `logging.getLogger(__name__)`。
- `agent/child_loop.py` `except FailoverExhausted`（子 agent 路径，已有 logger）。

> 严格说"改消费点"略超"只加 from"的红线，但挂了没人看是半个功能，审核时一并补齐。
> 仍未碰任何控制流——只多了一条日志语句。

## 2. 为什么不动其它"看着像候选"的 raise

定位命令 `grep -rn "raise " ... | grep -v "from "` + AST 粗筛全仓扫描后，逐一人工确认，
**只有上述两处真在"except 内抛新异常"的语义里**。以下排除项记录在案，防下次误改：

| 位置 | 为什么不改 |
|------|-----------|
| `chat_completions.py:303` / `anthropic.py:293` `raise ValueError("Invalid response ...")` | **不在 except 内**，是响应合法性校验失败。grep 命中是因为 message 文本里含单词 "from"，非异常链。 |
| `chain.py:144/476/490` `raise ValueError/RuntimeError(...)` | 参数/配置校验（entries 空、TRANSPORT_CHAIN 空、mode 未注册），无原始异常可挂。 |
| `client_factory.py:47` `raise ValueError(...)` | validate 失败，不在 except 内。 |
| `tools/__init__.py:36`、`mcp_client.py:73/84`、`session_store.py:*`、`skill_loader.py:*`、`provider.py:65`、`voice_orchestrator_client.py:60` | 全部是参数/状态/路径校验或 NotImplementedError，不在 except 内。 |
| `chain.py:279/289/295/354`、`mcp_client.py:92`、`turn_loop.py:565` 的**裸 `raise`** | 裸重抛**本身保留链路**，加 from 反而错。`except StreamCancelled: raise` 等保持不动。 |

**红线**：本档只加 `from`，没碰 `FailoverExhausted` 签名（仍只收 `attempts`）。
若未来想让 FailoverExhausted 显式持有 cause 列表，那是另一档的事。

## 4. 教学点

- `raise New from exc` 挂 `__cause__`（显式因果，traceback 显示 "The above exception
  was the direct cause of..."）；裸 `raise` 重抛保留 `__traceback__`，**不需要也不应该**
  加 from。
- **不在 except 内的 raise（参数校验）不是候选**——没有"原始异常"这个东西可挂。
- 想**切断**噪音链才用 `from None`（本档仅在 errors 为空的兜底分支用到）。
- 聚合型异常（FailoverExhausted 把 N 次失败压成一句话）尤其需要挂 cause：
  否则聚合消息会**完全吞掉**底层真实异常的 traceback，排障时只能靠日志反推。
