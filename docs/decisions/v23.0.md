# V23.0 — 多智能体最小可用版（delegate_task）

## 一句话定位

引入"父子两个 agent loop 同进程共存"的最小形态：父用 LLM 工具 `delegate_task`
派一个隔离子 agent，子在受限工具集下跑同步 loop，跑完返回纯文本 summary 给父。

## 痛点起源

V22 收尾后体感问题被推到前台 — agent 仍然单线程串行，复杂任务（"并行分析 3
个文件并对比"）父只能连串调三次工具，每次同步阻塞 5–30s。前 22 档抽象的隔离
质量也无法被真实场景检验：父加了一个工具后会不会污染整个对话？没法验证。

更深的前置问题在 V22 已经埋好：`CancelToken` 用 `threading.Event` 是为
"让父子线程共享同一个取消标记"准备的，V22 自身只用了单线程语义 — 这个承诺
在 V23.0 还没兑现，但已经把基础设施摆上了桌。

## 设计选型

### 选型 1：子 loop 抽成独立函数，不复用父 main loop

源项目走"父子复用同一份 `AIAgent.run_conversation`"（`run_agent.py` 1300+
行同时被父和子调），代价是子能跑的所有路径都要兼容父的所有特性（streaming /
cache / failover / trajectory / on_session_switch / on_pre_compress 等）。

nano 走**裁剪版**：`agent/child_loop.py` 是一个不到 200 行的纯函数，
显式不调 memory_manager、不调 compressor、不调 stream_call、不打印 UI。

| 路径 | 优点 | 缺点 |
|------|------|------|
| 父子复用同一 `AIAgent` 类 | 任何父能力子自动有 | 父的 if/else 分支爆炸；子的"我不要 X"靠 `role==leaf` 之类的标志砍 |
| **裁剪版独立 child_loop** | 父子差异在代码层一目了然；测试无 mock 父全套 | 子加新能力时需要在两边各加一次 |

选裁剪版。三个具体好处：

- 父的 main loop 行 502-625 完全不动 —— V22 流式 / cancel 等不变量自动保留
- 子的"不能写 memory" / "不能流式" / "不能压缩" 不再是 if 分支，而是结构性的
  「我没拿这个对象」 —— 教学叙事是"子能做什么"而不是"子被禁止做什么"
- V23.2 / V23.3 后续档加流式中继 / 结构化结果时，改动范围天然限定在 child_loop +
  delegate handler，不会溢出到 main.py

### 选型 2：黑名单走"精确名 + 前缀"双轨

源项目 `DELEGATE_BLOCKED_TOOLS` 是 `frozenset({"delegate_task", "clarify",
"memory", "send_message", "execute_code"})` 五个精确名。但 nano 当前
`memory_manager.get_all_tool_names()` 只暴露单一的 `"memory"`（V8 设计），
未来若拆出 `memory_recall_v2` / `memory_hindsight_*` 等子工具，前缀匹配能
自动覆盖。

最终：

```python
_DELEGATE_BLACKLIST_NAMES = frozenset({"delegate_task", "memory"})
_DELEGATE_BLACKLIST_PREFIXES = ("memory_",)
```

测试不变量 02 显式覆盖前缀路径（`"memory_recall_v2"` 应被过滤），教学保证
"未来 memory 子系统拆分时无需修 delegate"。

### 选型 3：setter 注入 vs constructor 注入

`delegate_task` 工具在 `tools/__init__.py` 自动发现期就注册到 registry，但
此时 main.py 还没构建 chain，更没决定父 toolsets。两条路径：

| 路径 | 优点 | 缺点 |
|------|------|------|
| 把 chain / model 通过 `register(...)` 直接绑给 handler | 一次注册一次注入 | 自动发现期没有这些对象，要把注册时机延后到 main.py 内 → 破坏 V1 自动发现机制 |
| **`set_delegate_context()` setter（仿 skill_view_tool）** | 自动发现期自然完成；运行期 main.py 选时机注入 | handler 调用前必须 check `_chain is None`，多一层防御 |

选 setter。`tools/skill_view_tool.set_skill_loader` 已经验证过这套模式
（V21.3）—— 同款解法保持一致性。check_fn `_check_delegate_ready` 在注入前
返回 False，让"没启用 delegate"的部署不会在父 LLM 工具列表里看到一个永远
返回 error 的 `delegate_task`。

### 选型 4：返回值仍是 V21.4 纯字符串

V23.0 子返回的结果是字典 `{"summary", "exit_reason", "iterations"}`，但
`delegate_task` 工具 handler 只取 `summary` 包装成 `tool_result(output=...)`。
父 LLM 看到的就是一段文本，不需要 `json.loads` 二次解析。

为什么不直接返回结构化 JSON？V23.3 才升级到结构化 — 这一档故意留白，让
"父 LLM 视角下子返回的就是一个字符串"这个观察成立，作为 V23.3 的痛点起点
（"等等，子吃了多少 token？"）。

## 真实踩坑

### 坑 1：memory 工具名是 `"memory"` 单数，不是 `memory_*`

实现完跑测试 02 时还过了，因为我用的 fake parent_full 是 `["memory_retain",
"memory_recall", ...]`。但跑真启动 banner 时发现父 LLM 看到的子允许集还含
`memory` —— 测试和现实分叉。

**根因**：nano 的 `memory_manager.get_all_tool_names()` 在 V8 设计时返回单一
名 `{"memory"}`（dispatcher 内部按 args 路由 retain/recall/reflect），跟源
项目 `memory_*` 多工具拆分不同。

**修复**：黑名单加精确名 `"memory"`；保留前缀做未来兼容。测试 02 改用
`["memory", "memory_recall_v2", "delegate_task", ...]` 同时覆盖两条路径。

**教训**：写黑名单测试时不能只造源项目里出现过的工具名 — 必须同时造目标
项目（nano）当下真实的工具名。等于第二天上班再看代码时也是这种感觉。

### 坑 2：startup banner 里 toolset 缓存先于 set_delegate_context

`get_available_tool_names(["core"])` 第一次被调用是在 `build_system_prompt()` 里，
而 `build_system_prompt` 在 `messages = [{"role":"system",...}]` 处求值。如果
注入顺序写反 —— 先 `messages = [...]` 再 `_inject_delegate_context(...)` ——
则首次缓存命中时 `delegate_task` 是隐藏的，30s 内父 LLM 工具列表里看不到它。

**当前代码顺序**（main.py:357-373 → 375）：
1. `client = chain.primary_client`
2. `_inject_delegate_context(...)` ← 必须在 build_system_prompt 之前
3. `messages = [{"role": "system", "content": build_system_prompt()}]`

**教训**：setter 注入模式天生有时序耦合 — 任何"在工具列表生成前"的步骤都
必须有 inject。下次再加类似工具时考虑写一个 docstring 注释或一个启动期
sanity-check。

## 验证（10 项）

`scripts/test_v23_0_delegate.py`：

1. child_loop 隔离 — 父 messages 不被 mutate；子内部新建 list
2. 黑名单 — `delegate_task` / `memory` 精确名 + `memory_*` 前缀双轨
3. check_fn — 注入前 `available_tool_names` 不含 delegate_task；注入后包含
4. child system prompt — 含 goal 字面量；不含父 SKELETON_PROMPT 标识
5. context 段 — 空时不渲染 `CONTEXT:` 段；非空时渲染
6. handler 输入校验 — goal 缺失/空白/context 非字符串 → tool_error
7. child_loop 自然终止 — finish_reason=stop + 无 tool_calls → exit_reason=completed
8. child_loop 兜底 — LLM 一直返回 tool_call 时 max_iterations=3 后停止
9. 黑名单二次校验 — 子 LLM 幻觉调用 delegate_task 在 dispatch 前被拦
10. handler 返回值 — V21.4 工具协议合规 JSON `{"output": <summary>}`

回归（零回归）：V17 (11) / V19 (17) / V20 (13) / V21.2 (15) / V21.3 (13) /
V21.4 (10) / V21 slash (14) / V22 (13) = 106 项不变量原样过；V23.0 新增
10 项。total = 116/116。
