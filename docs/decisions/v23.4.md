# v23.4 — 多智能体结构化结果 + 父子成本聚合

> 实现日期：2026-05-29
> 分支：`delegate/v0.23.2`（继续推进，下次切档号再开新分支）
> 基于：`v23.3`（多智能体流式中继 + 父子 cancel 桥接）
> iteration-plan 编号：[V23.4 结构化结果 + 成本聚合](../Multi-agent-system/iteration-plan.md#v234--结构化结果--成本聚合)

## 这一档解决什么

v23.3 闭合了"父 UI 不静默 + 子可立即 kill"，但子 → 父的回传仍是黑盒一行字符串：

- 父 LLM 看到 `{"output": "已完成。三个文件分别是 ..."}`，**不知道**子内部跑了几次 LLM、用了多少 token、读了哪些文件、是否中途有工具失败
- V20 的 prompt cache 命中率在子层完全看不见——父侧 chain entry 的 `cache_*_total` 是混合统计，无法回答"子第二次调用是否吃到 cache"
- 子的 4 种退出形态（completed / max_iterations / interrupted / error）当前都被压成"返回了一段文字就算完成"，父 LLM 只能从 summary 文本里揣测

v23.4 把"子返回什么 + 父能看到什么"两件事一起升级，让父 LLM 后续决策（再调谁、是否补充、是否 abort）有结构化依据，并为 v24 trajectory（数据飞轮）打底。

## 关键设计决策

### 1. 协议统一升级：单任务 output 也是 JSON 字符串

**选了什么**：`tool_result(output=json.dumps({"results": [...], "total_duration_seconds": ...}))`，单任务 = 含 1 条的 results 数组；父 LLM 永远 `json.loads → r["results"][i]`，无单 / 批分支。

**为什么不保 v23.0 plain string 兼容**：

- 与源项目 [tools/delegate_tool.py:2283](https://github.com/qshf/hermes-agent/blob/main/tools/delegate_tool.py#L2283) 同向，外层永远是 `{"results":[...]}`
- 单任务保 plain string 等于让一半场景拿不到 token / tool_trace —— 结构化的反面
- 父 LLM 看两套 schema 才是真正的认知负担；统一一种最清晰
- v23.5 嵌套 delegate 时还得再升级一次，不如这一次到位

代价：v23.0/v23.1/v23.3 测试里 5–8 处"output == 'hello'"断言**会回归**，需同步升级。这是有意的协议演进，不是 bug —— 教学叙事里"v23.0 单任务 output 就是 summary 文本"这条约定被本档明确推翻，决策日志记录推翻理由。

### 2. status 4 态不含 timeout

**选了什么**：`status` 枚举 = `{completed, max_iterations, interrupted, error}`。

**为什么不引入 timeout**：

- nano child_loop 没有真实超时机制（只有 max_iterations + cancel）
- 引入 `threading.Timer` 与 v22 的 `CancelToken` 设计互相冲突（都是"外部信号 → 内部退出"模式，重复机制等于双重事实源）
- 教学清晰性：诚实标注当前能力边界，比"为对齐源项目而硬塞 fake timeout 测试"更有价值
- iteration-plan 文档原预告的 5 态语义同步降级到 4 态，验证项 #4 改"4 态全覆盖"

**扩展位**：`status` 与 `exit_reason` 双字段并存当前完全冗余（同源），但保留是为 v23.5+ 扩展（如 `status="error"` 时 `exit_reason="failover_exhausted"` / `"tool_dispatch_crash"`）—— 教学要点：**为可观测留扩展位，但当下不滥用**。

### 3. session_tokens 挂在 AgentRuntime（不新建 SessionTokens 类）

**选了什么**：`agent/runtime.py` 加 `session_tokens: dict[str, int]` 字段（4 维：`input` / `output` / `cache_read` / `cache_write`），与 `transports.types.Usage` 字段名 1:1 映射。

**为什么不独立类化**：

- 当前只是 4 个 int 累加，加一个 dict 字段足够；独立类是过度设计
- AgentRuntime 已是父子共享真理源（`cancel_token` / `stream_enabled`），新累加字段加在这里语义自然延续
- v24 trajectory / insights 真要做 cost breakdown / 历史落盘时再独立类化，届时用 `runtime.session_tokens` 替代点已经全部对齐到一个调用面

**累加点**：

- 父 turn 路径：`main.py:_accumulate_parent_turn_tokens(runtime, normalized.usage)`，与现有 `compressor.update_usage(...)` 并列调用（compressor 用 prompt_tokens 做压缩阈值，runtime 做累计统计，语义完全独立）
- 子 worker 路径：`tools/delegate_tool.py:_accumulate_runtime_tokens` 在 `run_child_loop` 返回后立即累加；模块级 `_SESSION_TOKENS_LOCK = threading.Lock()` 保护（与现有 `_PROGRESS_STDERR_LOCK` 同款模式）

**为什么子要 lock 但父不需要**：父 turn 在 main loop 单线程里跑；子 worker 是 ThreadPoolExecutor 的并发线程，`d[k] += n` 的 LOAD/ADD/STORE 三步在 GIL 下不是原子的，两个 worker 同时累加同一键会丢一次。

### 4. session_tokens 在 `/transport` 末尾轻量暴露

**选了什么**：`/transport` 命令尾部加一行 `[session_tokens] input=X output=Y cache_read=Z cache_write=W`。

**为什么不放 banner / 不藏起来**：

- 数据已经填好了，让用户立即可见的成本是 ~10 行 print，几乎零成本
- v23.4 测试不变量本就要验"父 token 累加"——`/transport` 末尾的这行就是"验证项的活教程"
- banner 是启动一次性输出，不适合放运行期累计；`/transport` 是按需查询的命令，天然适合
- 字段命名朴素（不带成本估算 / 不分 turn vs session），v24 insights 升级时直接覆盖即可，不会有"先暴露成 A、又改成 B"的破坏性

### 5. tool_trace 用现场 append（不 post-hoc 从 messages 重建）

**选了什么**：child_loop 工具循环里 dispatch 后立即 `tool_trace.append({...})`。

**vs 源项目做法**：源项目 `tools/delegate_tool.py:1621-1653` 是子完成后从 `result.get("messages")` post-hoc 扫描重建 trace（要 match `tool_call_id` 配对 assistant 与 tool 消息）。nano 现场 append 简化为：

- dispatch 时同时知道 `name` / `raw_args` / `result`，直接写一条 trace 记录，不需要后续 match
- 取消 / 异常路径下 `messages` 可能不完整，post-hoc 扫描会漏 trace；现场 append 不丢
- 代码量 ~20 行 vs 源项目 ~30 行 + 复杂度更低

**字段裁剪**：

- 保留：`tool` / `args_preview` / `result_bytes` / `status`（4 字段）
- 不保留：`tool_call_id`（nano 不做并行 tool_call match）/ `arguments` 完整（用 args_preview 截断 200 字节代替）/ `result` 完整（用 result_bytes 代替；完整 trajectory 留 v24）

### 6. 实现细节小辑（从代码注释里清出来的次要权衡）

把"删掉这条注释下次有人会犯错吗？不会"判定为辩论性的小决策，集中放这里，避免污染代码 hot-path 的可读性：

- **`_SESSION_TOKENS_LOCK` 是模块级而非注入式**：lock 与 token dict 不绑定，所有 runtime 共享一把。教学版同进程只有一个 runtime 实例，不会因为多 runtime 互锁；代价是测试如果想把多个 runtime 完全隔离需要自己包装，但当前 7 项不变量都没这个需求。
- **`_build_result` helper 收口 7 处 return 路径**：child_loop 有 7 个终止分支（自然完成 / max_iter / 4 类 except / 流式 done 帧缺失），新加字段时如果分散填，漏一处的概率 = 7 倍。helper 让"加字段"只改一处签名 + 一处构造体，新字段在每条 return 上必填。
- **父 turn 累加与 compressor 语义独立**：`main.py:678` 处 `compressor.update_usage(prompt_tokens)` 用 prompt_tokens 绝对值做压缩阈值；新加的 `_accumulate_parent_turn_tokens` 用完整 Usage 做累计统计。两者**不可合并**：compressor 看每轮当前值（去抖判定阈值），runtime 看历史累积值（4 维 sum）。下次有人想"统一调用面"时必须看到这条。

## 真实踩坑

### 坑 1：LSP 提示"未存取 X"在 import 阶段就报，要忍住

写 helper 函数时常见的反模式是"import 立即提交、helper 后续追加"。LSP 实时分析在 import 完成那一刻就会标 "未存取" hint，看着难受会让人忍不住先把 helper 写完再 import。

正确做法：先按调用顺序自然写，import / 常量都先就位，等 helper 实际用到时 hint 自动消失。每次"未存取"hint 等 1-2 个 edit 就消失了，不要为它返工。

### 坑 2：v23.4 单任务也升级 JSON 触发 5 处测试回归

预估改 5–8 处，实际改了：
- `test_v23_0_delegate.py` 测试 #10：1 处
- `test_v23_1_batch.py` 测试 #1 / #2 / #7 / #7b：4 处
- `test_v23_3_streaming.py` 测试 #1 / #2 / #4 / #4b / #5：5 处

合计 10 处。其中 v23.3 测试因为同时验"批量 + 单任务"两条路径，比预期多 2 处。每处只是 `output_arr = json.loads(parsed["output"])` → `output_arr = json.loads(parsed["output"])["results"]`，机械替换。

教训：协议升级的连锁影响要按"前档每个 fake chain 的形态"枚举，而不是按"前档测试数"——v23.3 的两个 fake chain（`_FakeStreamingChain` 流式路径 + 同步路径）各贡献几条断言。

### 坑 3：max_iterations 测试需要 fake registry + 真 registry 联动

测试 `status="max_iterations"` 时构造的子要"永远 tool_call"。但 child_loop 的工具白名单是从父 `parent_toolset_names` ∩ `registry.available_tool_names` 取交集 —— 单纯本地 fake 一个 ToolRegistry 不够，要把 noop tool **register 到全局 registry**。

最初我建了一个独立 ToolRegistry 实例传 fake，但 child_loop 用的是模块级的 registry，对不上。改为：测试体内 `registry.register(...)` + `try/finally registry.deregister(...)` 包裹，只对本测试可见，不影响其他 fixture。

教训：模块级 singleton（registry / `_delegate_context`）的测试隔离要靠 register/deregister 配对，不是注入新实例。
