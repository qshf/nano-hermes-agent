# V23.1 — 批量并行 + 工具子集白名单

## 一句话定位

V23.0 的"父子隔离骨架"基础上加 `tasks: []` 数组 + `ThreadPoolExecutor`
并行 + 每条任务可选 `tools` 白名单交集。父 LLM 现在可以一次调用 spawn
多个独立子 agent 并行跑，且能给每个子单独收紧权限。

## 痛点起源

V23.0 落地后立刻露出两条具体问题：

1. **批量场景下 V23.0 比 V21 还慢**：用户问 "并行分析 A/B/C 三个文件并
   对比"，父 LLM 必须连串发起 3 次 `delegate_task`，每次父都阻塞等子
   完成。3 次串行子调用累计的 LLM 启动开销 + 子 system prompt 解析开销
   反而比 V21 单 turn 串行 `read_file` 还高 — V23 承诺的"并发"在 V23.0
   完全没兑现
2. **工具黑名单写死，无法收紧**：希望子 agent "只能读文件，禁掉
   terminal" 时，V23.0 没法表达；只能改源码常量

## 设计选型

### 选型 1：跳过 `FilteredToolRegistry` 包装类

iteration-plan §V23.1 原文写的是"构造一个 FilteredToolRegistry（轻量
包装：转发 dispatch，只重写 list_schemas）"。但 V23.0 落地时 `run_child_loop`
已经把 `allowed_tool_names: set[str]` 当一等参数传入，并在两处过滤：

- `registry.get_definitions(effective_tools)` — schema 级
- `if name not in allowed_tool_names: tool_error()` — dispatch 级

这两处加起来已经是"成品 FilteredToolRegistry"，再开一个 `FilteredToolRegistry`
类只是名词包装 — 让"per-call filter"换个壳。决定**跳过该类**，把 V23.1
的工具白名单交集做成 `_resolve_child_toolset(requested=...)` 的一个
可选参数即可。

| 路径 | 优点 | 缺点 |
|------|------|------|
| 写 `FilteredToolRegistry` 类 | 与 plan 原文严格对齐；为 V23.4 嵌套子各自不同允许集铺垫 | 名词包装，无行为增量；V23.4 真嵌套时仍可用 set 解决 |
| **`_resolve_child_toolset(requested)` 加参数**（推荐） | 不引入新类型；与 V23.0 现有 ``allowed_tool_names`` 直通 | iteration-plan 的"FilteredToolRegistry"标题与最终代码不对应（决策日志要补 why） |

教训：iteration-plan 是 V23.0 落地**前**写的，落地后发现 V23.0 的实现
已经吸收掉了某些后续档预留的抽象 — 这种情况要敢于偏离原计划，把"双
份过滤"塌缩成一份。

### 选型 2：`executor.map` 而非 `as_completed`

iteration-plan §V23.1 验证项 #2 显式要求"结果顺序与 tasks 数组对齐"。
两条路径：

| 路径 | 优点 | 缺点 |
|------|------|------|
| **`executor.map(fn, items)`**（推荐） | 自然按输入顺序返回；无须排序 | 不能边跑边收（V23.2 加 stderr 进度时要换） |
| `as_completed(futures)` + 按 `task_index` 排序 | 边跑边收；进度中继天然就近 | 多一行排序代码；V23.1 用不上"边跑边收"的优势 |

V23.1 做并行加速但**不**做进度中继（V23.2 才接），所以选 `map` —
代码更直白，且与 plan 文档显式对齐"V23.1 用 executor.map 自然有序；
V23.2 加进度时再换"。

### 选型 3：批量返回单层 JSON 数组而非二级嵌套结构化

V23.1 仍按 V21.4 协议：`tool_result(output=<str>)` 顶层。批量模式下
`output` 字段值是 JSON 数组的字符串：

```json
{"output": "[{\"task_index\": 0, \"summary\": \"...\", \"exit_reason\": \"completed\"}, ...]"}
```

父 LLM 看到的是字符串，但被设计为可 `json.loads` 的二次结构。这与
V23.3 完整结构化（含 `tokens` / `tool_trace`）的二级嵌套语义一脉相承
— V23.1 先把"父能 `json.loads`"这件事建立起来，V23.3 只是往二级 JSON
里塞更多字段，不破坏协议层。

为什么 V23.1 不直接把 `tokens` / `tool_trace` 一起塞进去？因为成本聚合
+ trace 收集需要修改 `run_child_loop` 返回 dict、`AIAgent.session_*`
字段、子工具结果统计 ~3 处；V23.1 单档铺这么大不划算，且会让"批量并行"
本身的不变量验证（顺序 / 黑名单 / 加速）和"结构化结果"的不变量验证
（token 累加 / status 五态）混在一起，分析路径不清晰。**V23.3 单独一档**。

### 选型 4：构建期错"全拒"而非"半启动"

iteration-plan §V23.1 验证项 #5 显式要求"批量 5 个任务，第 3 个的 `tools`
里包含语法错误 → 整个 `delegate_task` 调用直接 `tool_error(...)`，不
启动任何子 agent；前两个不会"半启动"。"

实现：handler 在 `ThreadPoolExecutor.submit` 之前**串行**校验所有 tasks
（`_validate_task_entry` 逐条），任一不合法立刻返回 `tool_error`。这
和源项目 `tools/delegate_tool.py:2031-2069` 的"主线程构建循环"语义
一致 — 主线程做一切非 LLM 调用的准备工作，worker 只跑 LLM。

为什么不"半启动"（合法的子先跑、不合法的报 error）？两个原因：

- 父 LLM 一次给一个 batch 时往往是"打包计划"，部分跑不一致会让父对
  剩余任务做错误决策（如以为 task#0/1 完成 = 计划完成）
- "半启动"需要在批量结果里给"未启动的任务"一个 placeholder dict，
  增加协议复杂度；fail-fast 让父简单重派即可

## 真实踩坑

### 坑 1：iteration-plan 的 "FilteredToolRegistry" 是 V23.0 落地后的死信

写 V23.1 时第一反应是按 plan 原文先做 `FilteredToolRegistry` 类。开始
写时发现：

```python
class FilteredToolRegistry:
    def __init__(self, parent, allowed): ...
    def get_definitions(self, names): ...   # 又过一次 allowed
    def dispatch(self, name, args):  ...    # 又过一次 allowed
```

但 `run_child_loop` 已经做了**两遍** allowed 过滤（`get_definitions`
拉 schema 时 + dispatch 前白名单二次校验）。再加一层 `FilteredToolRegistry`
就是**第三遍**过滤。

**根因**：iteration-plan 是在 V23.0 实现之前写的，那时候默认的"子拿
父 registry 后自己处理过滤"还没实现成 `allowed_tool_names` 参数化。

**修复**：决定跳过 `FilteredToolRegistry` 类，把 V23.0 的
`allowed_tool_names: set[str]` 接受为"成品 filter"。在
`_resolve_child_toolset(requested=...)` 加可选参数实现"白名单交集"。

**教训**：写完一档后**回头校对** iteration-plan 的下一档承诺 — 当前
代码是不是已经吸收了某些预留抽象？如果是，敢于减少。

### 坑 2：`_FakeChain` 不是线程安全的

V23.0 的测试 `_FakeChain` 用 list `responses.pop(0)` + `calls.append()`，
单线程下完全 OK。V23.1 直接复用时跑批量测试出现：

```
RuntimeError: FakeChain ran out of responses
```

明明给了 3 个 response，3 个并发 worker 各 pop 一次。**根因**：`pop(0)`
不是原子操作 — 两个 worker 几乎同时进 `if not self.responses` 检查，
都看到非空，都去 pop，第二个就 IndexError 然后 except 转成 RuntimeError。

**修复**：测试里 `_FakeChain` 加 `threading.Lock` 保护 `pop` + `append`；
sleep 在锁外（让并发延迟模拟真 LLM）。

**教训**：从 V23.0 复制 fixture 到 V23.1 时，不能复制完就跑 — 要先想"V23.1
新引入的并发会让哪些隐式假设失效"。这一坑 30 秒就发现，但原则要写下来。

### 坑 3：父 loop 对坏 args JSON 没有 try/except — 进程崩穿（真模型烟测发现）

V23.1 真模型烟测里在 DeepSeek 上手测"调用子智能体并行读正文 + 大纲"，
父 LLM 还在流式吐 args 时整个 agent 进程崩了：

```
File "main.py", line 611, in run_agent
    args = json.loads(tool_call.function.arguments)
json.decoder.JSONDecodeError: Expecting ',' delimiter: line 1 column 92 (char 91)
```

**根因**：流式拼帧的 args 偶发会拼出无效 JSON——chunk 边界正好切在中文
字符 / 分隔符上、模型自身格式错、或者超长复杂 args（V23.1 的 `tasks: []`
数组 + 每条 goal/context 几乎必然让 args 长度突破任何启发式阈值）都
会触发。`child_loop.py:208` 早就用了 `try/except json.JSONDecodeError`
把错误翻成 `tool_error` 塞回 LLM 让它修正，但**父 loop main.py:611 是裸
`json.loads`** —— 一旦 LLM 返坏 JSON，父进程直接 `JSONDecodeError` 崩穿，
连"让 LLM 重试"的机会都没有。

V23.0 fake-chain 测试覆盖的 args 都是 `_tool_call_response` 手工构造的
合法 JSON，永远 trigger 不到这条路径，所以 V23.0 不变量全过；真模型 + 流式
+ 复杂 args 三个条件凑齐时才暴露。

**修复**：`main.py:611` 改与 `child_loop.py:208` 完全对齐的 `try/except`
→ 构造 `tool_error(message, raw_arguments=args[:500])` 塞进 messages 让 LLM
下一轮自然修正。`raw_arguments` 字段保留前 500 字符让 LLM 能"看到自己写
错了什么"，比纯 error message 让模型更容易 self-correct。

**测试锁**：`scripts/test_v23_1_batch.py` test 08 是回归锚点 — 既验证
`tool_error` 协议合法、`raw_arguments` 字段存在，**还**反向 grep `main.py`
源码确认修复用的是 `json.JSONDecodeError` 而不是 catch-all `Exception`
（避免未来有人"为了'稳定'"把 except 范围改宽，把别的真 bug 也吞掉）。

**教训**：
- "fake 测试全过 + 真模型烟测发现新 bug" 是迭代项目的常态。fake 测试只能
  覆盖**已知**的失败模式，真模型 + 流式会暴露**未知**的拼接 / 边界 / 格式错
  组合。V23.0 → V23.1 的真模型烟测必须每档都跑一遍
- 父 loop 和子 loop 的容错对齐很关键 — child_loop 早就做对了，父 loop
  漏了一处。下次类似改动要主动 grep 同款代码确认对齐
- 修复 bug 时如果改的地方不在本档承诺范围内（这次是 main.py 的非 V23.1
  代码），仍要把 bug 记录到本档决策日志 — 因为是本档触发暴露的，时间
  上和本档绑定，分散到 "main.py 历次修改" 反而难追溯

## 验证（10 项）

`scripts/test_v23_1_batch.py`：

1. 批量并行加速 — 3 个 sleep(1s) 并行 < 1.8s（串行 V23.0 同等条件 ~3s）
2. 结果顺序与 tasks 数组对齐 — `task_index == [0, 1, 2]` 即便完成顺序无序
3. 白名单 ∩ 父全集 — 用户写 `nonexistent` 静默丢；空 list 给空集；`None` 走 V23.0 兼容
4. 黑名单强制 — 用户白名单含 `delegate_task`/`memory`/`memory_recall_v2` 仍被剔
5. 校验失败 → 整体 tool_error，0 子启动（chain.calls == 0）
5b. tools 字段类型错（不是 list[str]）也被主线程拦
6. schema 互斥 — goal/tasks 同时 / 都不给 → tool_error
7. V23.0 单任务路径回归 — 输出仍是 `{"output": <plain str>}`（不 JSON 嵌套）
7b. 单任务也支持 V23.1 的 `tools` 白名单字段
8. 父 loop 对坏 args JSON 容错（真模型烟测踩坑回归）— `tool_error` + `raw_arguments` + 反向 grep main.py 锁住 `JSONDecodeError` 而不是 `Exception`

回归（零回归）：V17 (11) / V19 (17) / V20 (13) / V21.2 (15) / V21.3 (13) /
V21.4 (10) / V21 slash (14) / V22 (13) / V23.0 (10) = 116 项不变量原样过；

## 教学要点速查

- "批量加速"不是新概念但首次落地：V23.1 第一次出现"主线程构建 +
  worker 跑 LLM 调用"的形态；强调**线程安全责任分层**（构建期主线程
  独占，worker 不修改父 agent 状态）
- "白名单交集语义"与 V3 toolsets 挂载的"白名单"语义不同：V3 是"至少
  包含"，V23.1 是"至多包含"；最终生效集 = `min(tools, parent_full) - blacklist`
- "fail-fast 校验"vs"半启动"：批量场景下 fail-fast 让父能简单重派；
  半启动需要 placeholder dict 增加协议复杂度
