# V15.1 — 压缩边界修复 + assistant 消息合法性兜底

## 一句话定位

V15 上下文压缩流水线落地时埋了两类隐性 bug，长会话 + reasoning 模型场景下**压缩看起来触发但啥也没压**、**replay 历史时下一轮请求 400**。V15.1 是修复档：兜底语义反转 + 写入侧 helper + 读出侧 sanitize 双道防线。

## 痛点起源

V15 落地数月后真实长会话出现两类故障：

1. **假压缩**：`tail_start = 4, len(messages) = 106, head_end = 3` —— `/compress` 触发了，middle 只摘要了 1 条，剩下 102 条全部留在 tail。anti-thrashing 把这种压缩记录为低效压缩，连续 2 次后干脆停止压缩，会话最终炸 context window
2. **400 Invalid assistant message: content or tool_calls must be set** —— deepseek-v4-flash 偶发把可见正文塞 `reasoning_content`（`content=None`）但又不发 `tool_calls`，旧回填代码把这种"纯 reasoning"消息原样写进 history，下一轮请求被服务端拒
3. **/compress 报 NoneType.strip 崩** —— 同上的 `content=None` 流到 `_format_messages` 的 `content.strip()`，AttributeError 直接吐到 CLI

## 设计选型

### 选型 1：兜底语义反转 — 最大化压缩 vs 最小化压缩

`_find_tail_boundary` 的循环 `for i in range(n-1, head_end-1, -1)` 在 `tail_token_budget` 大到能罩住整个会话时会一路走到 `head_end`，`cut_idx` 最终是 `head_end`。这种情况下兜底语义有两条路：

| 路径 | 行为 | 缺点 |
|------|------|------|
| 旧实现：`cut_idx = head_end + 1` | tail 拿满，middle 只剩 1 条 | "假压缩"，触发 anti-thrashing，会话最终炸 |
| **新实现**（推荐）：`cut_idx = max(fallback_cut, head_end + 1)` | middle 拿到所有可摘要消息，tail 只留 `min_tail = 3` 条 | 一次性大压缩，tail 历史短 — 但这是预期行为 |

源项目 [agent/context_compressor.py:1324-1325](/Users/qshf/my-project/hermes-agent/agent/context_compressor.py#L1324-L1325) 同款实现：兜底走 `fallback_cut = n - min_tail` 而非 `head_end + 1`。这一行是直接修 bug 的关键。

**为什么不引入 `soft_ceiling = budget * 1.5`（源项目额外做的）**：那是另一个独立维度的稳健性提升（对单条超大 tool 输出更稳定），跟当前"假压缩"bug 不在同一根因路径上。留 v15.2 单独做。

### 选型 2：`_align_boundary` 方向 — backward 而非 forward

旧实现碰到 `tool` 消息往**后**走（`cut_idx += 1`），可能把 `tool_call + tool_result` 群拆到 middle / tail 两侧；下游 `_sanitize_tool_pairs` 会把孤立的 result 删掉，造成静默丢消息。

源项目 [agent/context_compressor.py:1188-1210](/Users/qshf/my-project/hermes-agent/agent/context_compressor.py#L1188-L1210) 用 backward 对齐：碰到 tool 群一路退到父 assistant + tool_calls 之前，整组进 middle 一起摘要。改成 backward 后 tool 群语义自洽。

### 选型 3：写入侧抢救 vs 读出侧 sanitize — 都做

`content=None` + 无 `tool_calls` 的脏消息有两层处理点：

| 路径 | 优点 | 缺点 |
|------|------|------|
| 只在写入侧抢救（`build_assistant_history_msg`） | 源头干净，history 永远合法 | 已被污染的 history 仍会 400 |
| 只在读出侧 sanitize（`convert_messages`） | 兜旧账 | 每次请求都过一遍，写入侧仍然写脏数据 |
| **两层都做**（推荐） | 源头干净 + 旧 history 兜底；故障域分层 | 多 ~30 行代码 |

实现：
- 写入侧：`transports/types.py` 新增 `build_assistant_history_msg(normalized) -> dict` helper，集中实现"reasoning 抢救 / DeepSeek thinking padding / 全空兜底"。`main.py` + `agent/child_loop.py` 两处调用点替换为 helper 调用，避免 18 行重复
- 读出侧：`ChatCompletionsTransport.convert_messages` 改为遍历 sanitize — `assistant` 角色 + content 空 + 无 tool_calls → reasoning 提升为 content / 全空兜底为 `" "`

### 选型 4：reasoning 提升 vs prefill 重试 — 选了"提升"，但记下偏离

源项目档 3 ([run_agent.py:14728-14752](/Users/qshf/my-project/hermes-agent/run_agent.py#L14728-L14752)) 的处理是：发现 `reasoning-only` 响应 → 把这条 assistant 原样 append 进 history → 让模型下一轮看到自己的思考续写出 visible content（`_thinking_prefill_retries` 最多 2 次）→ 仍空才退化到 `(empty)` 兜底。

这条路径**比直接把 reasoning 当 content 存** 更接近正确语义：reasoning 是模型内心独白，把它当回答会让下次 turn 模型 confused。但实现 prefill retry 涉及主 loop 的重试计数器、消息序列状态机改造，单 v15.1 一档塞不下。

| 路径 | 优点 | 缺点 |
|------|------|------|
| **reasoning 提升 content**（推荐） | 一行抢救，保证流程不崩 | 语义不严格 — reasoning ≠ assistant 回答 |
| prefill 重试 + sentinel + fallback 切链 | 接近源项目正确语义 | 主 loop 改造面大；retry 计数器 + sentinel 标记位 + 后续清理逻辑 ~3 处 |

V15.1 选保守路径，把 prefill 三件套留作 v15.2 单独一档（"演进剧本"上承 v15.1 的 sanitize、下启 v15.2 的 retry 状态机，对 nano 教学叙事更值）。

### 选型 5：/compress 输出补节省汇总

旧输出只有 `compacted to N messages`，看不出压缩有没有实质效果。改成 `pre_msgs → post_msgs messages, ~pre_tokens → ~post_tokens tokens (saved X tok, Y%)`。`saved%` 与 `_ineffective_count` 用同一套粗估口径，肉眼判断 anti-thrashing 是否会触发。`~tokens` 带波浪线表示 chars/4 粗估，区别于 API 真实 prompt_tokens。

### 坑 2：deepseek-v4-flash 把可见正文塞 reasoning_content

真实复现的脏消息：

```python
{"role": "assistant", "content": None,
 "reasoning_content": "Now I can see the original structure clearly..."}
```

这条 message 显然有正文但塞错字段。源项目讨论里也提到这个 provider 的字段归类问题（具体引用见 [run_agent.py:9637-9660](/Users/qshf/my-project/hermes-agent/run_agent.py#L9637-L9660) 的 `Additive fallback (refs #16844, #16884)` 注释）。

**修复**：写入侧 `build_assistant_history_msg` 把 reasoning 提升为 content；下次 turn 模型至少能看到自己说过什么（即便是从 reasoning 字段 promote 上来的）。读出侧 `convert_messages` 兜底已被污染的 history。

**教训**：相同 provider quirk 源项目有 5+ 个 issue 编号（#9400 #15250 #16844 #16884 #17341 #17400 #8878 #9568 #9306）证明这是真实场景的高频 bug，nano 不能假装不存在。

### 坑 3：流式拼帧的 `reasoning_content` 真有可能是空字符串

测试场景里 reasoning_content 要么有内容要么 `None`，但流式累加 `_ChatStreamAccumulator.reasoning = []` 后 `"".join([])` 是 `""`（空字符串而非 None）。第一版 `build_assistant_history_msg` 的判断写成 `if rc is not None` 漏了这种情况：

```python
content_is_empty = content is None or (isinstance(content, str) and not content.strip())
if content_is_empty and not tool_calls:
    if rc and rc.strip():   # ← rc="" 时 False，正确退化到全空兜底
        content = rc
    else:
        content = " "
```

**教训**：写"判空"分支时区分 `None` / `""` / 全空白；流式 accumulator 路径上多一步 `or None` 转换可以让下游判断更简单。这次没改 accumulator（怕动 V22 不变量），只在 helper 里多写一次 `.strip()`。

## 教学要点速查

- **"兜底"语义方向**：写"安全失败"分支时永远问一句"失败时该退化到什么状态"。压缩兜底应该退化到"压缩得**更狠**"（最大化压缩）而不是"压缩得**更松**"（middle 1 条假压缩），因为后者会把会话彻底卡死。同款思路适用于：缓存兜底应清空而不是返回旧值；rate limit 兜底应拒绝而不是放行
- **写入 vs 读出双道防线**：脏数据问题最干净的修法是"源头别污染"，但已部署系统的 history 已经脏了，只改写入侧救不了存量。读出侧 sanitize 是兜旧账的补丁，新代码必须靠写入侧保证。两层一起做才稳
- **provider quirk 不能假装不存在**：deepseek-v4-flash 字段归类错、DeepSeek v4 thinking padding 要求、Anthropic 拒绝空 content — 每一个都是 real-world bug。nano 教学版可以省略 16+ provider 的特化路径，但不能省略**至少一个 quirk** 的真实修复 — 否则学不到"协议层标准化"和"实现层 quirk 容错"的分层意识
- **偏离 plan 要写明 why**：v15.1 选了"reasoning 提升 content"而非"prefill 重试"，这跟源项目正确语义有偏差。决策日志显式标记为"v15.2 还债"，避免下次接手时看到代码以为这就是终态
