# v23.3 — 多智能体流式中继 + 父子 cancel 桥接

> 实现日期：2026-05-29
> 分支：`delegate/v0.23.2`（继续推进，下次切档号再开新分支）
> 基于：`v23.2`（项目上下文注入 + --cwd）
> iteration-plan 编号：[V23.2 流式中继 + 中断传播](../Multi-agent-system/iteration-plan.md#v232--流式中继--中断传播)

## 这一档解决什么

V23.1 让批量并行落地，但和 V22 流式之间**完全脱节**：

- `STREAM_ENABLED=1` 时父外层是流式（用户看到打字），但**子内层走同步 `chain.call`**。
  父 LLM 一旦决定 delegate，UI 立刻冻结 1-3 分钟，体感比 V22 之前更糟
  （用户已经习惯 V22 实时反馈，此时反而觉得"agent 卡死了"）。
- 子 agent 死循环没法 kill：父按 Ctrl+C 后 V22 设父侧 `cancel_token.cancel()`，
  但 worker 线程里的子 agent 完全不知道，会继续吃 token 到 `max_iterations`。
- 批量 3 子并跑时，UI 上看不到"task#0 已完成 / task#1 read_file 中 / task#2
  还在等 LLM"，黑盒等待。

V23.3 把"父 UI 不静默 + 子可立即 kill"两件事一起做完，形成闭环。

## 关键设计决策

### 1. 父子**共享同一份** `CancelToken`，不各开

**选了什么**：父侧 V22 已构造的 `cancel_token` 直接 setter 注入到 `delegate_tool`，
所有子 agent 都拿这同一个实例。父 cancel 一次，所有 worker 下一帧 `check()`
同步收到。

**为什么不各开**：源项目 `_run_single_child` 用 `child._interrupt_requested = True`
是因为子 agent 不一定支持 streaming，需要在工具调用边界轮询子自己的标记。
nano V22 把 `CancelToken` 用 `threading.Event` 实现 —— Event 本身是跨线程
原子可见的，多线程同时 `check()`/`cancel()` 零成本，正是为这一档准备。
各开一个 token 还要再写一层"父→子"广播逻辑，徒增复杂度。

V22 当时注释里写的"为 V23 多 agent 准备"，本档兑现。

### 2. `StreamCancelled` 在子层**翻译**为 `exit_reason="interrupted"`，**不重抛**

**选了什么**：子 loop 内 catch `StreamCancelled` → 返回结果 dict
（`exit_reason="interrupted"`），不让异常穿出 worker 线程到父 handler。

**为什么不让它穿出**：父正在 `executor.map()` 等批量结果。如果某个子抛
`StreamCancelled` 出去，`executor.map` 会让整个迭代器在那条结果上抛异常 ——
**已经完成**的兄弟子的 summary 会被 cancel 一并丢掉。这违反 V23.1 "已完成的
子结果不丢" 契约。

把 cancel 翻译成"软状态"，让 handler 收齐所有 worker 的 dict 再聚合。父 LLM
看到的是 JSON 数组里 `exit_reason: interrupted` —— 它能据此决定要不要重试，
而不是被一个 unhandled 异常断掉对话。

### 3. progress 走**侧路 stderr**，不污染主路 `tool_result`

**选了什么**：子的 `StreamEvent` 经 `progress_callback` → 写父 stderr，
**不**经过 `tool_result(output=...)` 字符串。

**为什么不让 progress 进 output**：V21.4 工具协议 + V23.0 单任务 / V23.1 批量
output 协议都已稳定。如果把进度行拼进 output，会让父 LLM 误以为 progress 是
工具的返回内容，对话历史里堆一大坨 noise，长期会把 cache 命中率打穿。

**为什么 stderr 不是 stdout**：父侧 V22 流式正在用 stdout 实时打字，子侧
progress 进 stdout 会和父对话流交织成一锅粥（`Agent > 我先帮你分析[task#0]
read_file: foo.py三个文件...`）。stderr 是父也在用的状态行通道，分开不
冲突；终端默认两个 fd 都是 tty 实时显示，用户体验等价。

### 4. 用 `threading.Lock` 做 fan-in 同步，不引 queue + 单消费者

**选了什么**：模块级 `_PROGRESS_STDERR_LOCK = threading.Lock()` —— 多 worker
写 stderr 前 acquire，单行 atomic 写完释放。

**为什么不上 queue + 单消费者线程**：教学版唯一目的是"杜绝行交织"。
queue + consumer 模式（源项目用过类似结构）能在长 progress 突发时不阻塞 worker，
但代价是再开一个长生命周期的后台线程 + shutdown 协议。本档 progress 行短
（< 200 字符）+ 频率低（仅 done / tool_call_started 里程碑事件），lock acquire
的争抢成本远低于一行 print，多此一举。

V23.5（如果做）把进度做成 SSE 输出给 gateway 时再换 queue 模式 —— 那时是
真的有性能压力。

### 5. progress 只在 `done` / `tool_call_started` 里程碑事件回显，**不**逐 delta 回显

**选了什么**：`text_delta` / `reasoning_delta` 全部静默 —— callback 直接 return。

**为什么**：3 个 worker 同时各 yield 30+ 个 text_delta 时，即便有 lock，stderr
也会被 `[task#0] [task#1] [task#0] [task#2] ...` 的里程碑刷成滚动条。
里程碑事件足以让用户知道"进度推进到哪一步"，就够了。源项目同样选择
（`tools/delegate_tool.py:678-862` 的 `_build_child_progress_callback` 也只取
里程碑）。

### 6. `stream_enabled=False` 时彻底**不挂 callback**（不是空操作）

**选了什么**：`_build_child_progress_callback` 在 `_stream_enabled=False` 时
**返回 None**；child_loop 看到 None 直接跳过 callback 调用 + 走同步
`chain.call` 路径。

**为什么不挂个空 callback**：测试 / 部署若不开流式，挂空 callback 会让
fake chain（V23.0/V23.1 测试用）必须实现 `stream_call`。彻底 bypass 的好处：
V23.0/V23.1 的 `_FakeChain` 不需要任何改动，10 项 + 10 项不变量直接回归通过。

### 7. 不做的事

- **不做"子 agent 死锁检测"**：源项目 `_run_single_child` 里有 30s 心跳；
  nano 同进程线程池 + cancel 桥接已经覆盖"卡死"场景，心跳是 ACP 跨进程
  才需要的产物。
- **不做"延迟超过 N 秒的子任务自动 timeout 取消"**：留给 V23.4 / V23.5。
  当前唯一兜底仍是 `max_iterations=8`，加上 V23.3 的 cancel 已够。
- **progress sink 仅 stderr**：不挂 ACP / gateway / TUI 渲染层（nano 都没有）。
- **不做"子 reasoning_delta 实时回显"**：V22 父侧本身也只显示一次
  `[think] ...`，子继续静默是一致的。
- **不做"以 `as_completed` 替代 `executor.map`"**：V23.1 已选 `executor.map`
  保留输入顺序。本档的 progress 中继是侧路输出，不依赖 future 完成顺序，
  没必要换实现。

## 真实踩坑

### 坑 1：fake `time.sleep(5)` 测不出 cancel 传播

最初 fake `_FakeStreamingChain.stream_call` 内只在帧之间 `cancel_token.check()`
+ 一次性 `time.sleep(per_event_sleep)`。test_01 因此卡 5s 才返回 —— 父 cancel
没法在 sleep 中途打断（`time.sleep` 不响应 Event）。

**修法**：fake 内分片 sleep（每 50ms 一个 slice），每片之间 check token。
真实 SSE transport 本来就是分片到达的，分片 + check 才是 V22 cancel 模型的
正确仿真。

### 坑 2：cancel 后已完成的兄弟子 summary 不能丢

如果让 `StreamCancelled` 直接抛出 worker 线程，`ThreadPoolExecutor.map` 会
让整个结果迭代失败。V23.1 已经有"task#0 完成 / task#1 还在跑 / task#2 已完成"
的混合场景测试 —— V23.3 必须在子 loop 内层 catch + 翻译为 dict 字段，
让所有 worker 都能正常归档结果。

`test_02_cancel_does_not_lose_completed_siblings` 专门覆盖这条契约。

### 坑 3：`_inject_delegate_context` 必须在 `cancel_token` 创建之后

最初 main.py 顺序是：构建 chain → 注入 delegate_context → 后面再 `cancel_token = CancelToken()`。
导致 setter 注入时 `cancel_token=None`，子永远拿不到父 token。

**修法**：把 `cancel_token = CancelToken()` 上提到 `_inject_delegate_context` 之前。
SIGINT handler 注册可以晚一点（它只是把 token cancel/不 cancel 翻译成 SIGINT
路径，不创建 token），但 token 实例本身必须更早。
