# v24.1 — append-only 写入迁移 + 压缩链（会话分裂 + resume 重定向 + 列表折叠）

> 实现日期：2026-05-31
> 分支：`session/v0.24.1`（基于 `session/v0.24.0`）
> 基于：`v24.0`（SQLite 会话子系统 + 真 resume）+ `v15`（5 阶段上下文压缩）
> 计划：[docs/session-persistence-v24.md](../session-persistence-v24.md)（§0 拆档 + 决策 2/7）
> 源项目对照：`hermes-agent/hermes_state.py`（`resolve_resume_session_id` /
> `get_compression_tip` / `list_sessions_rich`）+ `run_agent.py`（压缩点会话分裂）

## 这一档解决什么

**v24.0 全量删重插会丢压缩前历史。** v24.0 修掉了假 resume，但用的是"每次 save
都 DELETE 整段再重插当前视图"。这与 v15 的 in-place 压缩（`messages[:]=compacted`）
直接冲突：压缩让运行时 messages 整个变短，下一次 save 一 DELETE，**压缩前的完整
原文就永久没了**——磁盘上只剩压缩后的摘要视图，再也回溯不到原始对话。

v24.1 让"压缩前历史可回溯"成立，靠两件绑死的事（计划决策 2/7）：

1. **写入迁 append-only**：每个 `session_id` 的 messages 只增不删，游标无状态
   （`COUNT(*)`）。
2. **压缩点会话分裂**：压缩时换 `session_id`、旧 session 打封存标但消息不删、新
   session 游标归零写压缩后视图。`parent_session_id` 把新旧串成压缩链。

这俩为什么必须一起做：append-only 单独用，碰上 in-place 压缩会让游标与变短的
messages 错位（游标 4、列表只剩 2，下次 append 从索引 4 起插 → 越界 no-op，新摘要
永远写不进去）。唯一解法是压缩时换 id + 游标归零——这正是源项目的做法。所以
append-only 与压缩链是一体的，同进 v24.1，进不了 v24.0（计划 §0 已论证）。

## 关键设计决策

### 1. append-only 游标 = `COUNT(*)`，无状态（计划决策 2）

**选了什么**：新增 `append()`，每次只插"剔除 system 后、索引 ≥ 已写条数"的新消息，
绝不 DELETE。游标 = `SELECT COUNT(*) FROM messages WHERE session_id=?`，不在内存存
`_last_flushed_idx`。

**为什么无状态游标**：重启 / resume / 多次 append 后游标自动正确——重算一次 COUNT
即可，没有"内存计数器与磁盘不同步"的故障面。源项目用内存游标
`_last_flushed_db_idx`（[run_agent.py:4484](../../../hermes-agent)）是因为它每轮高频
flush、COUNT 有成本；nano 教学版每轮就插几条，COUNT 开销无感，换来零状态。

**保留 v24.0 的 `save()` 不删**：`save`（全量删重插）仍在，v24.0 的 10 项测试零
回归，且"全量重写"语义本身没错（适合不压缩的简单场景）。生产路径（main.py /
slash）全切到 `append`，`save` 退居测试 + 备用。

**短列表是 no-op**（防御）：若传入的 persistable 比已写条数还短（同一 session 不该
缩——缩了说明该走分裂换 id），`range(already, len)` 为空 → 什么都不插，旧行原样保留。
这条不变量由测试 11 守住。

### 2. 压缩点会话分裂：四步串联，顺序不能乱（计划决策 7）

main.py 压缩点（[main.py](../../main.py) tool loop 内）在 `messages[:]=compacted`
**之前**串起：

```
1. append(old_sid, messages, ...)        # 压缩前完整 messages 落底（可回溯的根基）
2. end_session(old_sid, "compression")   # 旧 session 打 ended_at + end_reason 标，不删消息
3. current_session_id = f"{old}-c{N}"     # 换 id；N = compressor.compression_count
   create_session(new, parent=old)        # 新行，游标天然 0 → 下轮从 seq 0 插压缩后视图
4. on_session_switch_all(new, reset=False) # 联动 memory bank 轮换（对齐源 run_agent.py:10148）
   ctx.current_session_id = new            # 同步回 ctx（易错点！否则轮末 append 写旧 id）
```

**顺序为什么死**：第 1 步必须在 `messages[:]=compacted` 前——一旦 messages 被替换成
压缩视图，原文就从内存消失，append 进去的就是残缺的。第 3 步换 id 必须在轮末 append
之前，否则压缩后视图会被 append 到旧 session（游标错位 + 污染封存历史）。

**只有真压缩了才分裂**（踩坑点）：`compressor.compress()` 仅在 LLM 摘要成功时
`compression_count += 1`；LLM 失败 / 无可摘要 middle 会**早返回原列表且不 +1**。所以
分裂前快照 `compression_count`，比对确认真 +1 了才分裂——否则会建出一串空的 `-cN`
子会话 + 重复 flush。这条用 `_did_compress` 守。

### 3. resume 重定向：无条件走到 tip（偏离源项目，计划决策 7 的 nano 取舍）

**选了什么**：`resolve_resume_tip(id)` 沿 `parent_session_id` **无条件**往子代走到压缩链
最末 tip，深度上限 32 防环。`/resume` 和启动 load 都先过它。

**与源项目的差异（诚实标注）**：源项目有两个函数——`resolve_resume_session_id`
（[hermes_state.py:1621](../../../hermes-agent)，3 个 resume 入口调）在"root 自己有
消息"时**短路返回 root**；`get_compression_tip`（hermes_state.py:1126）才无条件走到
tip（列表折叠用）。nano 的 `resolve_resume_tip` 取的是**后者的语义**（无条件到 tip），
理由：

- 教学版要的就是"resume = 跳到压缩后的最新连续点"，符合用户直觉（你说的"resume
  落在压缩后的 tip"）
- 源项目 root 短路是因为它每轮 flush、root 总是带着压缩前全文，resume root 也连续；
  但 nano 若 resume 那个超长 root，下一轮立刻触发重压，体验差
- nano 库**只含压缩链**（delegate 子不入库，决策 8），不会有 delegate 子混进来把走向
  带偏——所以无条件走子代是安全的，不需要源项目 `started_at >= ended_at` 那种判别

**代价**：压缩前 root 默认对用户隐藏（被折叠 + resume 跳过）。想回溯压缩前原文走
`load(root_id)` 直读或 `/sessions --all`。

### 4. 列表折叠：被引用为 parent 的节点一律隐藏

**选了什么**：`list_sessions(fold_chains=True)`（默认）把"任何被别人 `parent_session_id`
指向的会话"全隐藏，只留 tip + 无链独立会话。一条逻辑对话 = 一行。tip 的 preview 取自
**链 root** 的首条 user 消息（原始第一问，而非压缩摘要——用户认得出是哪段对话）。
`fold_chains=False`（`/sessions --all`）展开所有节点。

**为什么用"被引用为 parent"判隐藏而非递归走链**：nano 库只有压缩链（线性父子），
"被指为 parent" ⟺ "非 tip 节点"，一条 `SELECT DISTINCT parent_session_id` 就够，比源
项目的递归 CTE（`list_sessions_rich` 的 `project_compression_tips`）简单一个量级，语义等价。

### 5. 启动 load 也先 resolve_resume_tip

重启时若 `MEMORY_SESSION_ID` 指向的会话曾被压缩分裂（成了链 root），启动直接 load 它
会重载压缩前超长 root → 下一轮立刻重压。启动先 `resolve_resume_tip` 跳到 tip，与
`/resume` 行为一致（对齐源项目"所有 resume 入口都 resolve"）。

### 6. 压缩 + 分裂抽成共用执行器 `agent.compaction.apply_compaction`（补档）

**踩到的真 bug**：v24.1 初版只把会话分裂接进了 main.py 的**自动**压缩点，手动
`/compress`（[cli/commands/compress.py](../../cli/commands/compress.py)）还停在旧的
"只 `messages[:] = compress(...)`、不碰分裂"。后果是 append-only 下的**静默丢数据**：
`/compress` 让内存 messages 变短，但磁盘游标（`COUNT(*)`）卡在压缩前条数 → 下一轮
`append` 的 `range(已写, 更少)` 为空 → 什么都不写。压缩后你新聊的内容**永远进不了盘**，
且无任何报错。比自动路径漏接更隐蔽。

**选了什么**：把"压缩检查后的执行体"（`on_pre_compress_all` → 快照 count → `compress`
→ did_compress 守卫 → 真压缩则会话分裂四步）抽成 `apply_compaction(ctx)`，自动压缩点
和 `/compress` **共用同一实现**。函数全程只读写 ctx（`ctx.messages[:]` 原地替换保持
引用、`ctx.current_session_id` 切新 id），返回"是否真压缩了"。

**为什么放 `agent/` 而非 `cli/`**：agent 层不依赖 cli（cli 反过来 import agent），放
agent 侧无循环导入；用 duck typing 收 ctx 不 import `AgentCtx`，保持 agent 对 cli 零依赖。

**自动路径的 turn_count 对齐**：主循环自动压缩点的局部 `turn_count` 此刻已 +1，但
`ctx.turn_count` 要到轮末才同步。`apply_compaction` 从 ctx 读 turn_count，所以自动路径
调用前手动把局部 `session_id`/`turn_count` 灌进 ctx、调用后读回（main.py 压缩点已加这
两行同步）。

## 真实踩坑

1. **`ctx.current_session_id` 同步**：压缩分裂改的是 main loop 的局部变量
   `current_session_id`，但轮末 append 用 `ctx.current_session_id`。改完不同步回 ctx，
   轮末就把压缩后视图 append 到**旧** session 上——封存历史被污染 + 新 session 永远空。
   计划决策 7 专门标了这个易错点。（抽出 `apply_compaction` 后由它统一改 ctx，自动路径
   再读回局部，根治了这个分叉。）
2. **空压缩不分裂**：见决策 2 的 `did_compress` 守卫——LLM 失败时不能分裂。
3. **手动 `/compress` 漏接分裂 = 静默丢数据**：见决策 6。两条压缩路径必须共用执行器，
   否则任何一条漏了分裂都会让 append-only 游标卡死。
3. **preview 取 root 不取 tip**：折叠后若 preview 取 tip 自己的首条 user 消息，那是
   `[CONTEXT COMPACTION...]` 摘要前缀，用户根本认不出是哪段对话。必须回溯到链 root 取
   原始首问。`_chain_root` 辅助函数干这个。

## 与计划的偏差

- **resume 重定向语义**：计划文档决策 7 写"对齐源 `resolve_resume_session_id`"，实际
  nano 取的是 `get_compression_tip` 的**无条件到 tip** 语义（见决策 3）。这是计划成文后
  与用户讨论敲定的取舍——用户明确要"resume 落在压缩后 tip"。计划文本未及更新，以本日志为准。
- 其余（append-only / 会话分裂四步 / 列表折叠 / `--all`）与计划 §4 一致。
