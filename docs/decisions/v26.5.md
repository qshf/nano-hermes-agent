# v26.5 — 事件驱动语音进度服务实验：废弃记录与后续路线

> 本档记录一次**不进入主线的失败实验**。v26.5 曾尝试把 `agent/voice_heartbeat.py` 从固定 heartbeat 扩成事件驱动语音进度服务：main/tool/delegate/slash 多处投递结构化事件，服务根据事件写死模板播报上下文进度。实验能改善“还在处理，稍等”太死板的问题，但实现形态不理想：代码冗余、策略硬编码、侵入点过多。因此本版本代码已回滚，主线保留 v26.4 作为稳定基线。

---

## 0. 一句话

v26.5 的方向“宿主侧理解进度并播报”是对的，但实现方式“到处插 emit + Python 里硬编码模板”是错的。后续应先做通用事件总线，再让语音作为 listener，并把播报策略外置。

---

## 1. 实验动机

v26.4 解决了模型在 terminal 阻塞期 / token 生成期无法定时报活的问题：后台 `VoiceHeartbeat` 线程直连 `nano_voice_kit`，在 `agent_busy.is_set()` 且静默超过阈值时播一条固定 `progress`。

用户体验反馈两个问题：

1. agent 起手阶段还会调用 `voice-runtime`，后半程多步执行时可能不再调用。
2. 后台心跳一直播“还在处理，稍等”，能防挂机，但不知道当前是在跑命令、查记忆、等 delegate，还是整理结果。

因此曾提出 v26.5 实验：让 `voice_heartbeat.py` 接收结构化事件，根据当前任务和最近工具播上下文相关文案。

---

## 2. 实验实现过什么

实验版大致做了：

| 文件 | 实验改动 |
|------|----------|
| `agent/voice_heartbeat.py` | 新增 `VoiceProgressEvent`、事件队列、上下文状态、模板选择、`emit()`；保留 fallback heartbeat。 |
| `main.py` | 在 turn/model/tool/busy 生命周期多处插入 `_voice_emit(...)`。 |
| `tools/delegate_tool.py` | `DelegateContext` 增加 `voice_progress`，delegate spawn/done + child stream milestone 发事件。 |
| `cli/registry.py` | slash command started/finished/error 发事件。 |
| `skills/voice-runtime/SKILL.md` | 改成“宿主事件服务负责常规进度”。 |
| `scripts/test_v26_5_voice_progress_service.py` | 覆盖模板、fallback、suppress、debounce、delegate bridge。 |

实验测试曾通过，但这只能说明功能可跑，不能说明设计可维护。

---

## 3. 为什么废弃

### 3.1 语音策略硬编码在 Python 里

实验版把大量字段和文案写死在 `voice_heartbeat.py`：

```python
if event.kind == "tool_started":
    if tool_name == "terminal":
        return "正在执行命令，这一步可能要等一下"
```

问题：

- 每新增一个工具 / 场景，都要改 Python 代码。
- 播报风格无法由 skill / 项目 / 用户配置调整。
- `voice_heartbeat.py` 逐渐变成另一套业务规则中心。
- 语音策略与 agent 控制流耦合，不符合 skill “能力外置”的方向。

### 3.2 多处插入，横切逻辑污染主流程

实验版需要在多个位置插入 voice 事件：

- `main.py` 的 user turn、model call、stream milestone、tool dispatch、busy finally；
- `delegate_tool.py` 的 spawn、done、child stream callback；
- `cli/registry.py` 的 slash dispatch；
- 后续如果要覆盖 compaction、memory、session、trajectory，还会继续扩散。

这说明问题不在 voice，而在缺少统一的 agent event boundary。语音只是 observability 输出之一，不应该直接侵入所有业务路径。

### 3.3 事件协议没有上升为公共基础设施

实验版的 `VoiceProgressEvent` 是 voice 私有事件。这样未来如果日志、metrics、trajectory、UI status 也想复用运行时事件，就会各自再造一套。

更合理的是先做通用 `AgentEventBus`，voice 只是订阅者之一。

### 3.4 v26.4 的职责边界反而更清楚

v26.4 虽然文案固定，但边界清晰：

- 模型：有语义的播报。
- 后台线程：阻塞期防挂机 heartbeat。
- main.py：只负责 busy set/clear + heartbeat lifecycle。

v26.5 实验版为了解决体验问题牺牲了架构清晰度，不适合进入主线。

## 5. 后续版本路线图

### v26.6 — `AgentEventBus`：先做统一事件总线，不做语音

目标：解决“多个地方直接插 voice emit”的根因。

新增类似：

```python
@dataclass(frozen=True)
class AgentEvent:
    type: str
    payload: dict[str, Any]
    source: str = ""

class AgentEventBus:
    def emit(self, event: AgentEvent) -> None: ...
    def subscribe(self, listener: Callable[[AgentEvent], None]) -> None: ...
```

原则：

- `emit()` fail-safe：listener 异常不影响主流程。
- 事件总线是通用基础设施，不属于 voice。
- hook 点只放在少数统一边界：turn、model call、tool dispatch wrapper、delegate、slash。
- v26.6 不做语音文案，不接 `VoiceClient`，只把事件协议立稳。

### v26.7 — `VoiceProgressListener`：语音作为 event bus listener

目标：voice 不再污染 main/tool/delegate/slash，只订阅 `AgentEventBus`。

形态：

```text
main / tool / delegate / slash
        │
        ▼
AgentEventBus
        ├─ StructuredLogger
        ├─ MetricsCollector
        ├─ TrajectoryAnnotator
        └─ VoiceProgressListener
```

建议拆分职责：

- `agent/voice_heartbeat.py`：保留 v26.4 的纯 fallback heartbeat。
- `agent/voice_progress.py`：订阅事件，决定是否播常规进度。

### v26.8 — `voice_policy.yaml`：播报策略外置

目标：解决“播放字段 / 文案写死”。

策略不再写 Python，而是作为 skill 资源或配置文件：

```text
skills/voice-runtime/resources/voice_policy.yaml
```

示例：

```yaml
events:
  turn_started:
    intent: info
    templates:
      - "开始处理这个任务"
      - "我开始看这个问题"

  tool_started:
    default:
      intent: progress
      templates:
        - "正在使用工具处理"
    by_tool:
      terminal:
        intent: progress
        templates:
          - "正在执行命令，这一步可能要等一下"
          - "命令已经开始跑了，我继续等结果"
      delegate_task:
        intent: progress
        templates:
          - "正在派发子任务"
      memory:
        intent: progress
        templates:
          - "正在查询记忆"

heartbeat:
  default:
    - "还在处理，稍等"
    - "我还在推进，没有卡住"
  by_recent_tool:
    terminal:
      - "命令还在跑，稍等"
    delegate_task:
      - "子任务还在处理，稍等"
```

Python 只做：加载 policy、匹配事件、模板选择、debounce、调用 `VoiceClient`。

### v26.9 — `PhraseProvider`：可选更自然文案

目标：在不破坏默认稳定性的前提下支持更灵活句式。

接口：

```python
class VoicePhraseProvider:
    def render(self, event: AgentEvent, context: VoiceContext) -> VoicePhrase | None:
        ...
```

默认 provider：YAML template provider。

可选 provider：

- LLM provider；
- rule-based provider；
- project-specific provider；
- user-personality provider。

默认绝不依赖 LLM，避免慢、贵、不稳定。

### v27.0 — Observability 总线

目标：把日志、语音、metrics、trajectory、UI status 统一到同一事件源。

```text
AgentEventBus
  ├─ StructuredLogger
  ├─ VoiceProgressListener
  ├─ TrajectoryAnnotator
  ├─ MetricsCollector
  └─ UIStatusRenderer
```

语音从“特殊功能”降级为 observability 的一个输出通道。

---

## 6. 经验总结

- 体验问题不能只靠 prompt 修；模型在阻塞期物理上不能行动，v26.4 的代码级 heartbeat 是必要的。
- 但“让宿主侧更懂进度”不能直接把 voice 逻辑塞进所有路径。
- 横切能力应先抽公共事件边界，再接具体 listener。
- 播报策略应外置，而不是写死在 Python if/else 里。

v26.5 的价值不在代码，而在暴露了下一层抽象：**AgentEventBus + VoiceProgressListener + voice_policy.yaml**。
