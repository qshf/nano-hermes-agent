# v25.1 — insights 离线分析 + 结构化日志（数据飞轮读路径）

> v25.0 让对话能落成训练样本（写路径），v25.1 接住**读路径**：`agent/insights.py`
> 把 v24 SQLite 跨会话聚合成报表（token/成本/tool top-N/失败率），`agent/logging.py`
> 加结构化日志（session 注入 + 滚动文件 + 写盘前脱敏）。新增 `/insights` + `/trajectory`。

---

## 0. 一句话

v25.0 把对话**写**成样本，v25.1 把样本背后的 SQLite **读**成洞见 —— 数据飞轮的
两半。读路径**只依赖 v24 store，不依赖 v25.0 jsonl**（见决策 4）。

## 1. 决策清单

### 决策 4：insights 的数据源是 v24 SQLite，不是 v25.0 trajectory jsonl

这是本档最重要的决策，也纠正了原 roadmap 的一个错误前提。

| 候选数据源 | 问题 |
|-----------|------|
| v25.0 trajectory jsonl | **有损**：脱敏改了内容、拍平丢了 tool_call_id。拿它算 token/成本会失真 |
| ✅ v24 SQLite sessions 表 | 现成有 4 维 token + turn_count + model + created_at，**原始计量** |

三条理由：

1. **字段齐全**：v24 `sessions` 表已有 `input/output/cache_read/cache_write` 4 列 +
   `turn_count` / `model` / `created_at` / `end_reason`，insights 要的全在表里。
2. **数据无损**：jsonl 是训练格式（脱敏 + 拍平），SQLite 存的是原始计量。算钱要准
   就得读原始的。
3. **关注点正交**：trajectory 写训练、insights 读计量，各取数据源互不耦合。

**因此 v25.1 不依赖 v25.0** —— 删光 `trajectories/` 后 `/insights` 仍正常出报表
（test 15 `independent_of_trajectory` 验证这条独立性）。

> 纠错：原 system-roadmap 把 insights 列在"依赖 trajectory jsonl 做统计"。那前提
> 源于"v14 只有 jsonl 无 SQLite"的旧认知，已被 v24 的 SQLite 会话子系统推翻。本档
> 落地时改成读 SQLite，roadmap 同步重写（场景 C：承认偏离 + 基于现实重新基线）。

### 决策 5：成本估算 hardcode 当前两家单价，未知 model 记 0 + 标 unknown

`estimate_cost(model, tokens)` 内嵌 deepseek + qwen 的 input/output/cache 三档单价
（USD / 1M tokens），按子串匹配 model 名。

- **为什么 hardcode**：教学版只跑这两家。源项目的多家 pricing 表 + pricing_version +
  actual_cost 对账是生产级需求，归 v26+。
- **未知 model 怎么办**：无价目 → 返回 `(0.0, "unknown")`，报表把它从成本剔出并提示
  "N sessions unknown pricing"，**不瞎猜价**。
- **已知简化**：官方调价后这表会过时。真要准确对账再开档（v26 候选）。

### 决策 6：日志脱敏挂在 formatter，不挂在调用点（对齐源项目）

`RedactingFormatter.format()` 把格式化后整行过 `redact()` —— 脱敏是"最后一道写盘前
的闸"，**不依赖调用方记得脱敏**。无论哪段代码 `log.info(...)` 带了密钥（transport
每次调用都带 `Authorization` 头），落盘前都被掩。

这与 v25.0 trajectory 写盘前过 redact 是**同一道防线的两处出口**（trajectory 喂训练 /
日志供排查），共用 `agent.redact.redact`。源项目 `hermes_logging.py` 同样把
`RedactingFormatter` 挂在所有 handler 上。

### 决策 7：session_id 走 thread-local 注入，不走显式参数

`agent/logging.py` 用 `threading.local()` 存当前 session_id，`_SessionFilter` 在每条
record 上注入。理由：日志调用点遍布各模块，逐个传 session_id 参数会污染所有签名。
thread-local 天然隔离 —— 父 main loop 与 delegate 子线程各自带自己的 session，互不串。

### 决策 8：读路径暴露并修复 v24 写路径 bug（model 名记错）

**这是数据飞轮"读出来才发现写错了"的第一个实例。**

`/insights` 第一次把 sessions 表的 `model` 字段聚合成报表，跑真实 DB 时报表显示
4 个会话全是 `gpt-4o-mini` + 成本 `$0`（unknown pricing）—— 但实际跑的是
`TRANSPORT_CHAIN=chat_completions:deepseek-v4-pro,...`，从没调过 gpt-4o-mini。

**根因**（main.py:444-445）：
```python
client = chain.primary_client
model = os.environ.get("MODEL", "gpt-4o-mini")   # ← bug
```
`.env` 只配了 `TRANSPORT_CHAIN`、没单设 `MODEL`，于是 `os.environ.get` 取不到 →
回退到硬编码 `"gpt-4o-mini"` → 这个**从未真正调用过的假名**被 `save_session` 写进
sessions 表。bug 自 v24.0 持久化层就潜伏，直到 v25.1 把 model 读出来才现形。

**修复**：model 优先取 `chain.primary_model`（TransportChain 早在 V19.1 就让每个
`_ChainEntry` 自带内联 model），env 仅作 chain 未内联时的回退：
```python
model = chain.primary_model or os.environ.get("MODEL", "gpt-4o-mini")
```
验证：修复后 `primary_model` 返回 `deepseek-v4-pro`；回归 v17(11)/v19(17)/v24.0(10)/
v24.1(8)/v25.1(6) 全绿。

**为什么合进 v25.1 而非单开 v24.2**：一行回退默认值的修复不值当走完整版本周期；
且它与 v25.1 是同一条因果链（读路径暴露写路径 bug），合并记录更能体现数据飞轮价值。
存量脏数据（已写进 DB 的 4 行 gpt-4o-mini）不回填 —— 教学项目不值当写迁移，新会话起
即正确。

> 已知遗留：成本价目表（决策 5）只内嵌 deepseek+qwen。model 名修对后真实就是这两家，
> 价目表够用；gpt 系等其它 model 仍标 unknown 记 0，留待 v26 多家 pricing 档。

### 决策 9：日志 handler 挂 root（不挂私有 logger）+ 真正接线进 main.py

**这是 v25.1 review 时发现的第二个"写了没接"的债，与决策 8 同源。**

初版 `agent/logging.py` 写完后**从没被任何生产代码调用** —— `setup_logging()` 不在
`main.py` 启动路径里，`LOG_FILE` 指向的文件永远是空的，`RedactingFormatter` / session
注入全是死代码。测试全绿是因为测试自己 import 了模块，绕过了生产路径。**这是"模块写完
即交付"的错觉**，跟决策 8 的"model 写进 DB 才发现写错"是同一类问题：写路径单测过了不等于
真的接进系统。

接线时又发现**靶子也错了**。初版把 handler 挂在私有 `nano` logger + `propagate=False`，
但代码库已有 **8 个模块**（`transports.chain` failover / `tools.delegate_tool` /
`tools.registry` / `memory.manager` / `agent.child_loop` …）早就在用
`logging.getLogger(__name__)`，它们的 record 沿 logger 树 propagate 到 **root**。挂私有
logger 等于一条都收不到 —— 尤其本档 docstring 明确承诺要排查的 "transport failover"
日志，密钥（每次调用都带 `Authorization` 头）照漏。

**修复**（对齐源项目 `hermes_logging.py` 的 `root = logging.getLogger()`）：
1. handler 挂 **root**，`nano` 埋点 logger 改回 `propagate=True` 冒泡享受 root 脱敏；
2. `_SessionFilter` 挂在 **handler 上而非 logger 上** —— Python logging 的
   `logger.filter` **只过滤直接 log 到该 logger 的 record，不过滤 propagate 上来的**。
   filter 挂 root logger 时，propagate 来的 record 跳过 filter → `record.session_id`
   缺失 → formatter 引用 `%(session_id)s` 直接 `KeyError`。挂 handler 才对所有到达的
   record（含 propagate 来的）生效；
3. `main.py` 启动尽早 `setup_logging()` + boot 埋点（model / chain 配置）；session
   resolve 后 + `/new` `/resume` 切会话后 + 压缩分裂后三处 `set_log_session`。

**验证**：端到端实跑确认 `transports.chain` 的 failover 日志被 root handler 接住、
`Bearer sk-deepseek-...` 脱敏成 `sk-dee...XYZW`；delegate 子线程 `[child-1]` 与父
`[default]` session 隔离不串（兑现决策 7）；不变量 16 改成用**别的模块名 logger**
（模拟 transports.chain）验 propagate→root→脱敏，比旧版只测 nano 自身更强。6/6 +
回归 v17/v19/v22/v23.4/v24.0/v24.1 全绿。
