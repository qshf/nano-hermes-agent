> 的服务端实现记在 `nano_voice_kit` 的决策日志（FR-1/FR-2）。

---

## 0. 一句话

让主 agent 能调一个外部 agent 服务（首例：假搜索服务），**控制流走 MCP**（阻塞请求/响应），
**观测流由服务自己 POST envelope** 给 voice orchestrator —— 两条链路正交，nano 不转发搜索内部细节。

---

## 1. 为什么是两条正交链路

MCP 是请求/响应：`call_tool("mcp_search_search", ...)` 在搜索跑完前一直阻塞，nano 在这几秒
**收不到任何中间事件**。所以「播报搜索内部进度」只能靠搜索服务**自己**在干活时发 envelope，
不可能由 nano 转发。这正是 v27.1 非目标第 3 条「父进程只发 aggregate child phase，不播子 agent
内部」的自然延伸 —— 子服务进度归子服务播，父 nano 只播自己的 turn。

---

## 2. 落地

### FR-3 · `fake_search_service.py`（联调用，零外部依赖）

- FastMCP stdio 外壳 + 极简 mini-agent 循环：`思考 → 检索 ×2 → 汇总`，每节拍 `_emit` 一个
  v2 扁平 envelope + `time.sleep` 模拟耗时。
- `SESSION="svc-search"` 独占稳定 producer 身份（FocusRouter 按它区分服务）。
- 时间线：`turn_started → activity_started(thinking) → activity_progress×2(tool/web_search)
  → activity_started(generating_text) → activity_finished(ok) → turn_finished`。
- kind→category 自动归类（orchestrator 侧 activity_arc）：thinking→THINK、web_search→SEARCH、
  generating_text→COMPOSE，喇叭弧线跟着「思考 → 联网检索 → 整理回复」走。
- **`_emit` 失败 silent**：语音失败绝不影响搜索本职（连不上 orchestrator 照样返回结果，有测试守住）。
- 多服务联调备料：复制改 `SESSION="svc-writer"` + 不同节拍 → 第二进程，验证焦点轮播。

### FR-4 · `agent/bootstrap.py:connect_mcp_servers`（env 门控）

- env `NANO_MCP_SERVERS=search=python:/abs/fake_search_service.py`（分号隔多条，`name=command:arg`）。
- 放在 registry/runtime 就位后、prompt/banner 之前 —— 注册进 registry 的 `mcp_search_search`
  能进 available tools banner，主 agent 可调。
- **连接失败只 warning 不抛**：外部服务是可选增强，连不上不该掀翻主 agent 启动。
- 复用既有 `tools/mcp_client.py:mcp_manager`，零改动 MCP 层。

---

## 3. 诚实的取舍

- 假搜索服务的 `_emit` 用 `urllib` 同步 POST（timeout 0.5s）。极端情况下 orchestrator
  慢响应会拖慢搜索节拍最多 0.5s/帧；联调够用，真服务应改异步 fire-and-forget。
- `NANO_MCP_SERVERS` 用极简 `name=command:arg` 单参格式（arg 只允许一个）。多参服务需要时
  再扩 —— 当前 YAGNI。
