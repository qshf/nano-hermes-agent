# v21.4 — 工具结果协议收口（tool_result/tool_error + dispatch 兜底）

- **触发动机**：V21.3 完成后审视当前工具体系，用户提问 "skill_view 返回的 markdown 被 ``\n`` 转义了，是否应该去掉 JSON 包装"。研究源项目 hermes-agent 的 `tools/registry.py:537-548` 后发现：源项目的硬约定是"所有工具返回 JSON 字符串、不返回 dict、字段名 `error` / `output` / `content` 各自独占语义"，提供了 `tool_result()` / `tool_error()` 两个辅助函数收口。nano 当前 6 个工具都各自手写 `json.dumps({"output": ...}, ensure_ascii=False)` 重复 6 次，且 `tools/mcp_client.py:160` 直接 `return "\n".join(parts)` 漏掉 JSON 包装 — 协议出现裂缝。
- **选 1（要不要去掉 JSON 包装）**：保留 JSON 包装，与源项目约定一致。
- **没选**：把 `skill_view` 等"内容型工具"改成裸 markdown 直出。原因：(a) 源项目协议层是 JSON 字符串无差别，破坏一致性会让"工具调用方永远能 `json.loads(result)`"的下游假设失效，模型解析也要分情况；(b) 用户对"看着难受"的真实痛点其实是"长 markdown 全塞 messages 浪费 context"，正解是沙箱持久化（源项目 `tools/tool_result_storage.py:122-176` 的 `<persisted-output>` 机制），不是降级协议。沙箱机制独立成档（暂记 V21.5 候选），见 [system-roadmap.md V21.4 段](../system-roadmap.md)。
- **选 2（辅助函数签名）**：`tool_result(data=None, **kwargs)` 双形态 + `tool_error(message, **extra)`，与源项目逐行对齐。
- **原因**：源项目 `tool_result(data=None, **kwargs)` 的设计让 `tool_result({"output": "..."}, exit_code=0)` 的两种用法都自然 — 已经构造好 dict 用第一形态、临时拼字段用第二形态。nano 不发明新约定，照抄能让"看过源项目的读者来读 nano"零摩擦。
- **选 3（mcp_client 修复方式）**：把 server 返回的 text content 块拼接结果包成 `{"output": "..."}`，不试图判断"如果 server 已经返回 JSON 就透传"。
- **没选**：在 handler 里 `try: json.loads(text)` 判断是否已经是 JSON 再决定是否再包一层。原因：MCP server 协议层面 text content 就是任意文本，可能是 JSON 也可能是 markdown 也可能是日志输出。让 handler 猜会引入两条不同 code path（更难测试），还会出现"看起来是 JSON 但语义不对"的情况（例如 server 返回的 JSON 不是 dict 顶层）。统一包一层简单可靠 — 模型看到 `{"output": "<server JSON 原文>"}` 完全能解析。
- **选 4（dispatch 最终防线）**：把 handler 异常捕获 + 返回值类型校验 + JSON 合法性校验都放进 `registry.dispatch`，三层兜底全部转成 `tool_error()` / `tool_result(output=...)`。
- **原因**：源项目 `tools/registry.py:373-390` 的 `dispatch -> str` 是强类型签名 + 异常包装。nano V21.3 之前 `dispatch` 只在"工具未注册"和"被 hook block"时返回 JSON，handler 自身抛异常会冒泡到 `main.py` 主循环 — 一个工具坏整个 agent 死。三层兜底是"协议不变量"的最后一道防线：无论上游 handler 怎么写错，`messages[]["content"]` 永远是合法 JSON 字符串。
- **选 5（兜底降级到什么字段）**：异常用 `tool_error()`、非 str 和非 JSON 都用 `tool_result(output=str(...))`。
- **原因**：异常天然是错误语义，归到 `error` 字段；返回值类型错或 JSON 不合法属于"开发者写错"，但模型 *看到这个数据* 还是当作输出处理最合理 — 强转 str 包成 `output` 让对话能继续，同时 dispatch 层 `log.warning` 让开发者排错。如果都报 error 会导致一个"日志级别问题"被升级为"对话失败"，过度反应。
- **选 6（read_file 字段名继续用 `content` 而非 `output`）**：保留 V1 时代选定的 `{"content": "..."}`。
- **原因**：刚好和源项目 `tools/file_tools.py:447-654` 的 `read_file_tool` 命名一致。源项目把 `content` 留给"文件类内容"语义、`output` 留给"执行类输出"语义（terminal/code_execution）。nano 沿用此约定，是一个 V1 时代的"无意识对齐" — V21.4 复盘时确认这个差别不是 bug 而是协议特征。
- **选 7（不动 main.py 的解析逻辑）**：`main.py:369-381` 的 `try: parsed = json.loads(result)` 去打印 `[error]` / `[result]` 的逻辑保持原样。
- **原因**：那段是用户可见的 CLI 提示，逻辑已经判 `"error" in parsed` / `"output" in parsed` 兼容了所有字段约定（`content` 走 `(ok)` 兜底分支，能用）。改的话牵连 V21.1 的 slash 注册表无关代码，与本档"协议层收口"主题不同 — 留待将来如果出现 `content` 内容也想 preview 时再改。
- **真实数据点（修复前）**：6 个工具中 `mcp_client._make_handler` 的裸 `return "\n".join(parts) if parts else "{}"` 是唯一违例 — `parts` 来自 server text content 块，可能是任意字符串。一旦 server 返回包含双引号或换行的内容，CLI `[result]` 解析的 `json.loads` 会成功（因为 fallback 到 raw print）但对模型来说协议格式就是错的，影响后续轮的工具结果稳定解析。
- **真实数据点（修复后）**：`scripts/test_v21_4_tool_result_protocol.py` 10 项不变量。其中 test 8/9/10 是 dispatch 兜底测试 — 主动注册"故意返回非合法值"的 rogue 工具，验证 dispatch 把异常 / dict / 非 JSON 字符串都强转成合法 JSON。回归：V21.2 PromptBuilder 15/15、V21.3 Skill 13/13、V21 Slash 14/14 全绿。
- **改动文件清单**：新增 `tools/result.py` (~50 行) + `scripts/test_v21_4_tool_result_protocol.py` (~180 行)；改 `tools/skill_view_tool.py` / `read_file_tool.py` / `terminal_tool.py` / `docker_exec_tool.py` / `async_demo_tool.py` / `mcp_client.py`（删 `import json`、用辅助函数替换重复 `json.dumps`）；改 `tools/registry.py` 的 `dispatch` 加最终防线。
- **不改的"看似该改"清单**：
  - `tools/memory_store.py` 返回 dict 不返回 JSON 字符串 — 但它是 builtin memory provider 的内部存储层，被 `provider.handle_tool_call` 包装后才出现在 messages 里，不走 `tools/registry.dispatch` 路径，不属于本档协议范围。
  - `memory/manager.py:228` / `:241` 的 `MemoryManager.handle_tool_call` 也有两处 `json.dumps({"error": ...}, ensure_ascii=False)`，命中同一重复模式。本档主题是"工具结果协议"，memory 子系统是相邻话题但独立路径（不经过 registry.dispatch），如果要让 memory 子系统也用 `tool_error()` 应该独立审视——provider 接口本身是否要约束返回 JSON 字符串、要不要在 manager 层加同样的最终防线。留待将来如果出现"工具协议改第二次"时一并梳理。
