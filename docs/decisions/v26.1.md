# v26.1 — 可用性门控（env vars + requires_tools）

> skill 现在能**声明依赖**：`required_environment_variables` 声明需要哪些 env，
> `metadata.requires_tools/toolsets` 声明需要哪些工具。缺 env → 软标记（进索引标 ⚠）；
> 缺工具 → 硬隐藏（不进索引省 token）。计划见
> [docs/Skill-system/skill-system-completion-plan.md](../Skill-system/skill-system-completion-plan.md) §6。

---

## 0. 一句话

v26.0 让 skill 能携带资源，v26.1 让 skill 能**声明自己用不用得了**——
没配 `DASHSCOPE_API_KEY` 的 voice skill 不再被无差别注入然后白调一次工具才发现缺 key。

---

## 1. 决策清单

### 决策 1：env 缺失走「软标记」，requires_tools 不满足走「硬隐藏」

两种门控策略不同，因为「能不能补救」不同：

| 门控 | 策略 | 行为 | 为什么 |
|------|------|------|--------|
| `required_env_vars` 缺失 | **软标记** | 仍进索引，渲染层追加 `⚠ (setup: set X)` | agent 可以引导用户「设置 X 后再用」——硬隐藏会让这个交互无从发生 |
| `requires_tools/toolsets` 不满足 | **硬隐藏** | 根本不进索引 | 工具不存在时 skill 无法工作，留着只浪费 token，没有可补救的交互 |

这是本档最核心的判断：**门控不是非黑即白的「显示/不显示」，而是按「缺失能否被用户补救」分流**。

### 决策 2：`list_metadata(available_tools=None)` 向后兼容默认全显示

`available_tools=None` 表示「调用方没传工具信息」→ 不做硬隐藏，全显示。
这让 V21.x 旧调用方（`/skill list` slash、单测）行为不变——只有 PromptBuilder
显式传入当前可用工具时才触发硬隐藏。`available_toolsets` 独立同理判断。

**为什么不默认空 set**：`None`（无信息）和 `[]`（确实没有任何工具）语义不同。
前者向后兼容全显示，后者会把所有声明了 requires_tools 的 skill 全隐藏——这是
有意义的区分，不能合并。

### 决策 3：PromptBuilder 复用现有依赖取 available_tools，不新增构造参数

`_render_skill_index` 需要的「当前可用工具名」从 builder 已持有的
`_get_toolset_tool_names(self._enabled_toolsets)` + `memory_manager.get_all_tool_names()`
取（抽成 `_available_tool_names()`，与 `_render_tool_list` 同源）。
**不给 PromptBuilder 加新构造参数**——可用工具是 builder 已知的派生信息，不是新输入。

### 决策 4：nano 只做 `requires_*`，不做 `fallback_for_*`

源项目 `_skill_passes_conditions` 还有 `fallback_for_tools/toolsets`（主工具可用时隐藏
兜底 skill）。nano 教学场景没有「兜底 skill」概念，YAGNI 不做。

### 决策 5：env 声明支持两种写法，但 nano 不做交互式 secret capture

`required_environment_variables` 支持 `[KEY1, KEY2]` 纯名字列表，也支持
`[{name: KEY, help: "..."}]` 带 help 的对象列表（与源项目兼容）。nano 只取 `name`——
**不做源项目的交互式 secret capture 回调**，配置交给用户改 `.env`。help 文案
留给作者写进 SKILL.md 正文。

### 决策 6：`skill_view` 工具结果回填 readiness，字段名与源项目对齐

读完 SKILL.md（tier 2）后结果加 `readiness_status`（`available` | `setup_needed`），
缺 env 时再加 `missing_env_vars` + `setup_needed=True`。让 agent 读完说明书立刻知道
「这个 skill 现在能不能用、缺什么」，而不必再调一次才发现。

## 3. 裁剪（vs 源项目）

- 不做交互式 secret capture 回调（`_capture_required_environment_variables`）——只检查 + 标记
- 不做 `required_credential_files` / `env_passthrough` / `register_credential_files`
- 不做 `fallback_for_tools/toolsets`（兜底语义，nano 用不到）
- 不做磁盘快照缓存键含 tools/platform（每次 build 实时算，nano 规模无性能压力）

## 4. 验证

`scripts/test_v26_1_availability.py` —— 10/10 不变量：

- **字段解析**（3）：顶层 `required_environment_variables` 抽出；`metadata.requires_tools/toolsets` 抽出；缺字段→空 tuple 不报错
- **env 软标记**（3）：全设置→setup_needed=False；缺一个→missing_env_vars 含它+setup_needed=True；env 缺失仍出现在 list_metadata
- **requires_tools 硬隐藏**（4）：tool 在 available→出现；不在→不出现；available=None→全显示（兼容）；toolset 不在→不出现 + skill_view 回填 readiness

回归：v26.0 10/10、v21.3 13/13、v21.2 prompt_builder 15/15（fake loader 的 `list_metadata`
补上可选 kwargs + `missing_env_vars()`，匹配真实接口）。

真跑：`SkillLoader('skills')` 对真实 `voice-runtime` skill →
- `list_metadata()`（无工具信息）→ voice-runtime 出现（兼容）
- `list_metadata(available_tools=['skill_view'])`（无 terminal）→ voice-runtime **硬隐藏**
- `voice-runtime.missing_env_vars()` → `['DASHSCOPE_API_KEY']`、`setup_needed=True`

## 5. 决策一句话总结

| 决策 | 选项 | 没选 | 原因 |
|------|------|------|------|
| env 缺失策略 | 软标记（进索引标 ⚠） | 硬隐藏 | agent 需要「引导用户配置」的交互机会 |
| requires_tools 策略 | 硬隐藏 | 软标记 | 工具不存在 skill 无法工作，留着浪费 token |
| 兼容默认 | `available_tools=None`→全显示 | 默认空 set→全隐藏 | 「无信息」与「确实没工具」语义不同 |
| available_tools 来源 | 复用 builder 现有依赖 | 加新构造参数 | 可用工具是已知派生信息，非新输入 |
| fallback_for_* | 不做 | 移植 | nano 无「兜底 skill」概念（YAGNI）|
| secret 配置 | 只检查 + 标记 | 交互式 capture | 配置交给用户改 .env，教学版不做回调 |
