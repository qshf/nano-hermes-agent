# v21.3 — Skill 系统（progressive disclosure tier 1 + tier 2）

- **选 1**：tier 1 索引由 `agent/skill_loader.py` 在启动期扫描 `skills/<name>/SKILL.md`，把 frontmatter 的 `name`/`description` 灌进 system prompt（V21.2 已经占好的 `_render_skill_index` 段）。
- **没选**：把所有 SKILL.md 的全文都拼进 system prompt。原因：源项目 V20 阶段实测 30+ skill 全文塞进 prompt 是 50K+ token，缓存命中率上去后这部分单价是免费的没错，但 first-turn cache miss 本就比 read 贵 1.25x — 教学场景大多数对话只有几轮，写入成本换不回来；progressive disclosure 把 first-turn 的成本压到 1-2 KB（仅 name+desc），需要细节时 agent 再调 `skill_view`，省掉了"准备给 1% 的对话用、却让 100% 都付钱"的浪费。
- **选 2**：tier 2 用 `tools/skill_view_tool.py` — agent 看到 tier 1 索引后判断要用哪个 skill 就调 `skill_view(name="plan")`，tool result 落进 messages 给下一轮推理用。
- **原因**：Tool result 进对话历史 = 跟 cache breakpoint 对齐（系统 + 最后 3 条），比改 system prompt 成本低；并且天然兼容多轮对话里"agent 改主意换 skill"的情况 — 多次调用产生多条 tool result，不互相替换。
- **选 3**：单一 schema 的 nano 目录约定 — `skills/<name>/SKILL.md`（一级）。
- **没选**：源项目的 `skills/<category>/<name>/SKILL.md`（两级 + qualified namespace）。原因：nano 教学示例最多 ~10 个 skill，分类纯粹是负担；扁平目录配合 `name` 在 frontmatter 唯一即可。
- **选 4**：Loader 模块级 singleton + `set_skill_loader(loader)` 注入器，由 `main.py` 在构造完 `SkillLoader` 后回调注入到 `tools/skill_view_tool.py`。
- **原因**：`tools/__init__.py` 在 import 期 `discover_tools()` 触发 `tools/skill_view_tool.py` 模块级 `registry.register(...)`，但此时 `main.py` 还没构造 loader 实例。两条解决路径：(a) 让 tool 接受工厂函数 lazy 构造 — 但 loader 状态需要在 `/skill reload` 时同步，工厂会复制实例破坏一致性；(b) 模块级 singleton + setter — 注入是同一个引用，`/skill reload` 调 `loader.scan()` 后 tool 看到的就是新缓存。选 (b)。
- **选 5**：`skill_view` 的 `check_fn` — loader 未注入或为空时把工具从 `get_tool_definitions(['core'])` 里隐藏。
- **原因**：让"不挂任何 skill"的部署仍然干净 — 没必要让 LLM 看到一个永远返回 `error: not initialized` 的工具，那只会污染上下文增加困惑。`/skill list` 仍然可以工作（slash 命令旁路 LLM）— 给运维一个验活窗口。
- **选 6**：YAML 解析失败 → 单 skill 跳过 + 打 warning，不阻断启动；frontmatter 缺 `name` / `description` → `KeyError` 直接抛。
- **原因**：教学场景对错误的偏好是"显式失败 + 易排错"。yaml 损坏经常是 SKILL.md 写的人手抖（如缺一个 `]`），跳过就行让其它 skill 可用；但缺 `name`/`description` 是写错了 SKILL.md 的契约，必须立刻让作者看到。源项目 511 行的 `agent/skill_utils.py` 还有 fallback 简单 `key:value` 解析等容错路径，nano 都不要。
- **选 7**：把 `skill_view` 加进 `core` toolset（不开新 toolset）。
- **没选**：开 `skills` toolset 让用户自己 enable。原因：(a) 第一次落地这个特性，让默认开就开，否则用户不知道有；(b) `check_fn` 已经隔离了"无 skill 部署"的噪音。下个版本如果有需要细粒度控制的场景再独立 toolset。
- **选 8**：YAML frontmatter 字段集合大幅删减 — nano 只识别 `name` / `description` / `platforms` 三个字段。
- **没选**：照搬源项目的 `version` / `author` / `license` / `metadata.hermes.tags` / `related_skills` / `requires_toolsets` / `requires_env_vars` 等 8+ 字段。原因：这些字段在源项目里服务的功能 nano 都没做（条件激活、qualified namespace、tag 过滤、版本演进通知），照搬只会让 SKILL.md 看起来很复杂、误导读者以为这些字段被使用了。教学价值 > 兼容性。
- **真实踩坑**：`yaml` 解析虚拟环境里没装 — `import yaml` 启动报 `ModuleNotFoundError`。本来 nano 的 `pyproject.toml` 没列 PyYAML，因为之前没用到。修复：`pyproject.toml` 加 `pyyaml>=6.0`，`uv pip install` 装 yaml 6.0.3。决策：导入移到 `parse_frontmatter` 里 lazy import — 没挂 skill 的部署不需要付加载代价。
- **真实踩坑（测试期）**：写 `test_5_parse_frontmatter_split` 时断言 `body.lstrip() == "the body"`，但实际 body 末尾还有一个 `\n`。早该用 `.strip()` 一并 trim。修复：用 `.strip()`。这是"写测试时假设和实际边界条件不一致"的典型 — body 后边可能有 trailing newline 是 yaml 文档的常态，不是 bug。
- **关于 V20 prompt cache prefix 兼容**：V21.2 已经把 skill 索引段位置占住（loader=None 时返回空），V21.3 只填实现 — system prompt 段顺序没变，cache 兼容性自然保持。验证方式是看 `agent/prompt_builder.py:127-135` 的 `sections` 顺序与 V21.2 一致。
- **验证**：`scripts/test_v21_3_skill.py` 13 项不变量（loader 扫描 / view / 缺失字段 / 平台过滤 / yaml 错误隔离 / tool 隐藏与暴露 / `/skill` 三个子命令 / PromptBuilder 集成）。`scripts/test_v21_slash.py` 的"已注册命令集合"测试同步加上 `skill`（11 → 12）。回归：v12-v20 + v21.1 + v21.2 全绿；v15 的 `test_5_iterative_update` / `test_6_compress_structure` 维持 V19 时代起的 2/9 失败（`compress()` 多了个 transport 参数那次没同步该 test，是 baseline，与 V21 无关）。
