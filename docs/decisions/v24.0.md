# v24.0 — 会话状态持久化（SQLite 会话子系统 + 真 resume）

> 实现日期：2026-05-31
> 分支：`delegate/v0.24.0`（基于 `delegate/v0.23.4`）
> 基于：`v23.4`（多智能体结构化结果 + 父子成本聚合）
> 计划：[docs/session-persistence-v24.md](../session-persistence-v24.md)
> 源项目对照：`hermes-agent/hermes_state.py`（SQLite 会话存储，SCHEMA_VERSION=11）

## 这一档解决什么

**v14 的假 resume。** v14 标题是"会话与压缩"，但它只落了 `on_session_switch`
生命周期钩子（给 memory manager 切 bank key），**从没把对话 `messages` 存过盘**。
后果：

- `/resume <id>` 只换了 memory bank 的 key、把 `messages` 清成只剩 system
  prompt，拿不回任何历史对话
- 进程一退，整段对话蒸发——下次启动同一 `MEMORY_SESSION_ID` 也是空白
- "会话"在 v14–v23 里始终是个**进程内临时态**，与"持久实体"的直觉相悖

v24.0 让 `messages` 成为可持久化的真实实体：每轮末 / 退出落盘到 SQLite，
`/resume` 真正 load 回历史。这是补上 v14 欠的债，也为 v24.1（append-only +
压缩链）和后续 trajectory 数据飞轮打地基。

## 关键设计决策

### 1. 落盘后端：SQLite + WAL，逐条入行（不是整段 JSON）

**选了什么**：`sessions/state.db`，两张表——`sessions`（元数据）+ `messages`
（一行一条消息）。WAL 模式 + `busy_timeout=5000`。

**为什么逐条入行而非把 messages 整段 JSON 塞一列**：

- 对齐源项目 `hermes_state.py` 的 messages 表结构，教"把 OpenAI 消息规范化
  进表 + 读时重建 shape"这个真实生产模式
- 为 v24.1 的 append-only 游标（`COUNT(*)` 拿 seq tip）和后续可选 FTS5 全文
  检索留地基；整段 JSON 这两样都做不了
- 代价：写时要 `_insert_message` 规范化、读时 `_row_to_message` 重建，比
  `json.dumps(messages)` 多 ~40 行。这 40 行正是教学价值所在。

**为什么 SQLite 不是 JSON 文件**：并发写保护（WAL）、原子事务（轮末 save 半截
crash 不留坏档）、查询能力（list/preview/倒序）——JSON 文件三样都得手写。

### 2. 写入语义：v24.0 全量删重插，v24.1 才迁 append-only

**选了什么**：`save()` 在一个事务里 `DELETE` 旧 messages + 重插当前视图。

**为什么不一步到位做 append-only**：

- append-only 与压缩链**绑死**：append-only 下一旦 in-place 压缩（v15 的
  5 阶段压缩让 messages 变短），游标与变短的 messages 错位，必须靠"会话分裂 +
  parent 串链"化解。这套机制进不了第一档。
- 全量重写简单、能**独立**修掉假 resume、切割面干净，先交付里程碑。
- v24.1 再迁 append-only + 压缩链——约 30 行返工，换 v24.0 独立上线。

代价：v24.0 不保留压缩前的旧消息（压缩后 save = 当前视图覆盖）。这是有意的
过渡形态，不变量 5 的测试明确锁这个语义。

### 3. system message 不落盘——resume 时重建

**选了什么**：`save()` 剔除首条 `role=system`；`load()` 不返回 system；
`/resume` 和启动 load 都在 messages 前用 `prompt_builder.build()` 重建 system。

**为什么**：system prompt 随启动环境变化（skill 列表、MCP 工具、`--cwd` 项目
上下文、记忆 banner 都会变）。存旧的 system 再 load 回来，等于把上次启动的
环境"冻"进这次会话——工具列表、项目上下文全是过时的。重建才正确。

### 4. 存档时机：轮末 save + 退出兜底

**选了什么**：每轮 tool loop 跑完（`sync_all` 之后）`save` 一次；`finally`
块退出时再 `save` + `close` 一次。

**为什么两处都要**：

- 轮末写的不变量是"crash 最多丢一轮"——进程崩在第 N 轮中途，最多丢这一轮
- 退出兜底覆盖"轮中途按 quit / Ctrl+D / Ctrl+C 退出"的边界（轮末写没走到）
- 退出 save 包 `try/except` 防遮蔽：save 失败不能吃掉 `memory_manager.shutdown_all()`，两者都要尽力跑完
- `close()` 让 WAL checkpoint 回主库，避免 `.db-wal` 旁路文件越积越大

### 5. delegate 子线程不碰 store（线程模型）

**选了什么**：`sqlite3` 连接只在父 main loop 单线程用；delegate 子线程不
持有、不调用 store。

**为什么**：`sqlite3.Connection` 非线程安全。子的对话结果（v23.4 起是结构化
`{"results":[...]}`）已经作为 tool message 进了父 `messages`，随父会话一起落盘，
无需子单独存。这样 `check_same_thread` 保持默认 True，不引入连接池 / 锁。

### 6. 并发写：WAL + busy_timeout，不引入会话级锁

**选了什么**：WAL（读不挡写）+ `busy_timeout=5000`（第二个写者等 5s）。

**为什么不做会话级锁**：多窗口共享同一 `state.db` 且 `/resume` 同一
`session_id` 时，last-write-wins（后 commit 覆盖先 commit）——这是逻辑覆盖，
不是物理损坏。nano 单用户教学版约定"每窗口用不同 `MEMORY_SESSION_ID` 物理
隔离"，不值得为多窗口并发同一会话引入分布式锁的复杂度。WAL + busy_timeout
保证的是"不出半截坏档"，够用。

## 不在本档范围（明确划给后续）

| 能力 | 归属 | 为什么不在 v24.0 |
|------|------|----------------|
| append-only 游标增量写 | v24.1 | 与压缩链绑死，见决策 2 |
| 压缩链（会话分裂 + parent 串链） | v24.1 | `parent_session_id` 列已建但 v24.0 不写值 |
| resume 沿链重定向到 tip | v24.1 | v24.0 直接 load target |
| FTS5 全文检索 | 可选后续 | messages 逐条入行已留地基 |
| `ended_at` / `end_reason` / `title` | v24.1+ | 列已建，v24.0 不写 |
