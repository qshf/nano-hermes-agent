# v27.4 — 子 agent 调 MCP + 子流自报身份（producer_role）【计划 / 待实现】

## 0. 一句话

让 **MCP 服务在它发的 envelope 里自报 `producer_role="subordinate"`**——声明「我不是平级的一轮，
我是主 agent 某次阻塞工具调用期间的插入观测流」。FocusRouter 认这个标记后：插入流**不抢焦点 owner、
不进 closing 候选、不走 idle 闸即时放行**。一个标记，同时治好「尾部赘语」和「开头黑屏」两个 bug。
顺带把「子 agent 继承不到 MCP 工具」的初始化时序 bug 一并修掉，让原设计（MCP 服务=被包装的子 agent）真正可用。

## 2. 为什么从 emit 一侧入手（否决 A2/A3）

修「子流从属」有三条路，权衡见下。结论：**让 producer 自报**最干净。

| 方案 | host 改动 | 靠不靠猜 | C 落地后（子 agent 也能调 MCP） | 评价 |
|------|----------|---------|------------------------------|------|
| A2 命名约定（FocusRouter 靠 `mcp_search_*`↔`svc-search` 对名） | 零 | 靠命名对齐，**脆** | 要额外处理「父是子 agent」 | 凑合 |
| A3 host 进工具发 yield_focus 信号 | **要新增信号** | 不猜 | 同左 | host 恰恰最不知情 |
| **A' emit 自报 `producer_role`（本档）** | **零** | producer 直说，不猜 | **天然兼容**：插入流不点名父亲，只声明身份、跟当前焦点 | ✅ |

关键洞察：**A3 的死穴是 host 不知道「这次工具调用背后有没有语音流」**——svc-search 是 MCP 服务
*自己*决定要不要 POST 语音的，host 只看到一次普通阻塞工具调用，是瞎的。而 MCP 服务**自己**百分百
知道自己是插入流。把判断放在信息最充分的那一侧 = 让 producer 自报。

且这条与既有决策约定一致：`self-narrate-yield.md` 就是让策略层认 envelope 里 host 已发的
`activity.name=voice_say`——「host 发事实，编排器定策略」。`producer_role` 同理，只是这个事实由
MCP 服务（第三方 producer）发，不经 host。host **零改动**正是这条路最大的好处。

## 3. 架构回顾：谁向谁发什么

```
┌─ host (nano_hermes_agent) ─┐   ① MCP call: search(query)  ┌─ MCP 服务 (fake_search_service) ─┐
│  主 agent turn loop         │ ───────────────────────────▶ │  search 工具（阻塞 req/resp）      │
│  发 turn_started/finished + │ ◀─────────────────────────── │  _mini_agent: think→fetch→compose │
│  activity_* envelope        │   ② 阻塞返回 report           │  _emit: 每拍 POST 观测 envelope    │
└──────────┬──────────────────┘                              └──────────────┬───────────────────┘
           │ ③ 主会话事件 session=session-xxxx                              │ ④ 观测流 session=svc-search
           ▼                                                               ▼  （本档给它打 producer_role=subordinate）
        ┌──────────────────────── nano_voice_kit ────────────────────────┐
        │  FocusRouter（认 producer_role）→ SpeechPolicy → NarrationQueue │→ 🔊
        └─────────────────────────────────────────────────────────────────┘
```

主 agent 阻塞在 ② 期间自己不发声（无中间事件），④ 的插入流填的正是这段静默 gap——**因果上它本就
该是「同一个故事」的一部分**，不该被当成抢麦的对手。

## 5. 阶段一 · C：子 agent 继承 MCP 工具（host 侧）

**根因**（见 bug 文档 §8）：[bootstrap.py:370](../../agent/bootstrap.py#L370) 的 `connect_mcp_servers(log)`
跑在 [bootstrap.py:355](../../agent/bootstrap.py#L355) 算 `parent_full_toolset` 快照**之后**。子 agent 的
`_resolve_child_toolset`（[tools/delegate_tool.py:149](../../tools/delegate_tool.py#L149)）读的是这份冻结快照，
此时 MCP 工具还没进 registry → 子 agent 永远看不到 `mcp_*`。主 agent 不受影响（它读 registry 实时态）。

**改动**：把 `connect_mcp_servers(log)` 从 line 370 上移到 line 355 `parent_full_toolset = ...` **之前**。

**为什么安全**：`connect_mcp_servers` 只依赖 `os.environ` + `mcp_manager` + registry 注册路径；
`registry.set_runtime(runtime)`（line 347）已先行，上移后依赖仍齐备。`_resolve_child_toolset` 无 `mcp_`
黑名单（黑名单只有 `delegate_task`/`memory`/`memory_` 前缀）→ MCP 工具自然进子允许集。

**要验证的非显然点**：子 agent 与父**共享同一 `mcp_manager` 单例**（同一 stdio 子进程连接），
不能各连各的。这是阶段一测试重点。

**测试**（新建 `scripts/test_v27_4_subagent_mcp.py`，套现有 test 约定）：
1. 单元：注入 DelegateContext 后 `_resolve_child_toolset(None)` 的允许集**包含** `mcp_search_*`。
2. 单元：`_resolve_child_toolset(["mcp_search_query"])` 交集拿得到该工具。
3. 端到端：delegate 一个子任务，子 agent 实际调通 MCP search 拿回 report。
4. 回归：主 agent 调 MCP 路径不变（沿用 `test_v27_2_mcp_search.py`）。

## 6. 阶段二 · A：子流自报 producer_role（emit + voice 两侧）

### 6.1 emit 侧（`fake_search_service.py`，host 仓内的示例 MCP 服务）

`_emit` 的 body 加一个字段：

```python
"producer_role": "subordinate",   # 我是插入观测流，不是平级 turn；跟当前焦点走
```

含义约定写进模块 docstring：`subordinate` = 「本 producer 的事件是某个主会话阻塞工具调用期间的
内嵌观测流，不应被当作抢麦的平级 turn」。缺省 / 不带该字段 = `"peer"`（现有平级服务语义，向下兼容，
真正并行的 svc-writer 那种仍走老路）。

### 6.2 voice 侧（`nano_voice_kit/orchestrator/`）

envelope schema（`TurnEventIn` / models）加可选字段 `producer_role: str = "peer"`。FocusRouter 据此分流：

| 行为 | peer（现状，不变） | subordinate（新增） |
|------|-------------------|--------------------|
| 抢焦点 owner | 会（无焦点时占位 / 久候轮播） | **不会**——永远不当 owner |
| idle 闸门 | 非焦点要熬满 `idle_switch_seconds` | **不走闸**，跟当前焦点即时 `pass_through` |
| closing 候选 | `turn_finished` 进 `finished` 池，可补收尾 | **不进**池，`turn_finished` 不触发独立收尾 |
| memo | 正常记 | 仍记（供 `/status` 观测），但 `closed` 视为恒真 |

实现落点（[focus_router.py](../../../nano_voice_kit/nano_voice_kit/orchestrator/focus_router.py)）：
- `route`：envelope `producer_role=="subordinate"` 且**当前有焦点** → 直接 `RouteResult(pass_through=True)`，
  不进 `_remember` 的 finished 标记路径、不参与 `_advance` 候选。
- `_remember`：subordinate 的 `turn_finished` **不**置 `finished=True`（否则会被 `_advance` 翻出来收尾）。
- `_advance`：候选过滤已天然排除（subordinate 不置 finished），无需额外改。

### 6.3 弧线状态归属（决策点 D，已定 D-i）

subordinate 放行后**照常过 `policy.decide()`**，享受 salience floor / cooldown 节流，phrase 进
`recent_phrases`。理由：① 改动最小（不新写旁路）；② 插入流填的就是焦点的静默 gap，本就该共用一条故事弧线；
③ 主 agent 恢复念结果时，`recent_phrases` 里已有「搜索完成」类话，反帮它不重复。

### 6.4 测试

emit 侧：`fake_search_service.py` 的 `_emit` body 含 `producer_role=="subordinate"`（轻量 assert）。

voice 侧（扩 `scripts/test_focus_rotation.py`）：
1. 焦点存在时，subordinate envelope **立即** `pass_through`（不等 idle，对比 peer 要等）。
2. subordinate 的 `turn_finished` **不**进 closing 候选 → 焦点 `turn_finished` 不触发它的独立收尾（治 Bug 2）。
3. subordinate 全程不夺焦点 owner（治 Bug 9 的同时不引入新的抢麦）。
4. peer 路径**完全不变**：现有 14 项焦点测试 + `test_orchestrator_mvp.py` 全绿（真·并行服务仍走老语义）。

## 7. 阶段三 · B：陈旧 memo 保险（voice 侧，与 A 同档）

A 落地后 subordinate 不再进 closing 候选，幽灵会话场景已大幅收窄。B 退化为一行防御：
`_advance` 选 `closing_for` 时，跳过 `now - last_seen_at > 阈值`（建议 `2 × idle_switch_seconds`）的陈旧
memo——挡住跨进程残留（orchestrator 不重启时 `_memos` 跨运行累积）。

**测试**：构造 `last_seen_at` 远早于 now 的 finished peer memo，断言 `_advance` 不把它当 `closing_for`。

## 8. 诚实的取舍

- **靠 producer 自觉**：`producer_role` 由 MCP 服务自报，恶意 / 写错的 producer 谎报 `subordinate` 会
  逃过焦点仲裁。可接受——producer 都是自己人（自写的 MCP 服务），且谎报最坏是「该独立的服务没独立」，
  不造成串台（subordinate 仍过 policy 节流）。
- **subordinate 永不当焦点 owner**：若某次主会话**只**有 subordinate 流、主会话自己一个事件都没发
  （理论边界），则没有焦点可跟 → subordinate 被旁路。现实中主 agent 调 MCP 工具必先发 `activity_started`，
  焦点已是主会话，不触发该边界。文档记下，留作 §6.2「当前有焦点」前提的已知约束。
- **C 与 A 在本方案下解耦**：producer_role 自报让插入流不必点名父级，所以「子 agent 也能调 MCP」不再
  使 A 复杂化。代价是 FocusRouter 失去「这条插入流到底属于哪次工具调用」的精确归属——但单焦点单喇叭下
  「跟当前焦点」已足够，YAGNI。
- **schema 加字段**：`producer_role` 是 v2 envelope 的新可选字段，缺省 `peer` 向下兼容，不需 schema 版本号
  升 v3（沿用 v27.1 「bounded envelope 可加可选字段」惯例）。
