# V22 — 流式输出 + 中断

## 一句话定位

把 transport ABC 从"只跑同步"补到"流式那一半也通"，并把 SIGINT 翻译成
``StreamCancelled`` 让流式期间的 Ctrl+C 优雅回到 prompt 而不是杀进程。

## 痛点起源

V17–V21 把 transport 抽象做实了，但只用了同步那一半 — 任何一次响应都要等
LLM 整段写完才出现在终端上（DeepSeek thinking 模式 5–30s 一片黑屏）。Ctrl+C
落到 ``input()`` 上才管用，落在 ``chain.call`` 阻塞期间只能 SIGKILL 整个 agent
进程，对话历史全丢。

源项目把流式做成 ``call`` 的内部分支（``run_agent.py:7484+`` 一个 800+ 行的
``_interruptible_streaming_api_call``，按 ``stream_callback != None`` 分流）。
教学版选**正交**路径：流式是单独入口 ``stream_call``。

## 设计选型

### 选型 1：流式作为独立方法，不和 ``call()`` 混

| 路径 | 优点 | 缺点 |
|------|------|------|
| ``call`` 内部按 callback 分支 | 复用 build_kwargs / convert / normalize | 单方法 800+ 行；同步路径仍要带流式状态机；测试矩阵翻倍 |
| **独立 ``stream_call`` 方法** | call() 保持"一进一出"；V17-V21 同步不变量测试零改动 | transport 子类要写两套 SDK 调用 |

选独立方法。代价是 ``ChatCompletionsTransport`` 同时存在 ``call`` /
``stream_call`` 两条路径，但两条都很短（~50 / ~100 行），重复换来：

- V17-V21 写过的 11+12+17+13+14+15+13+10 = 105 项不变量原样过
- 流式改造**只**碰 transport / chain / main 三处，agent loop 的"压缩 /
  memory / sync_turn"等无关循环节零改动

### 选型 2：StreamEvent 类型而不是裸文本流

源项目的 ``stream_delta_callback`` 是 ``Callable[[str], None]`` —
单纯文本回调。问题：UI 想知道"现在开始调 read_file 工具了"或"现在是 reasoning
不是正文"必须看 callback 之外的私有累加器。

V22 把事件抽出来：

| 事件 | 含义 | 何时 fire |
|------|------|---------|
| ``text_delta`` | 文本增量 | ``delta.content`` 非空 |
| ``reasoning_delta`` | DeepSeek/Kimi 的隐式 CoT 增量 | ``delta.reasoning_content`` 非空 |
| ``tool_call_started`` | 第一次见到完整 tool name | tool_call.name 累积成型时（仅一次） |
| ``done`` | 流结束，response 字段是完整 NormalizedResponse | 流尾 |

agent loop 拿到 ``done`` 直接读 ``response``，不必自己拼 tool_calls / usage。

### 选型 3：``CancelToken`` 用 ``threading.Event`` 而不是裸 bool

V22 单 agent 单线程，按理裸 bool 够。提前用 ``threading.Event`` 是为 V23 多
agent / delegate 时父 token 会被多个子 agent 线程同时检查 / 设置 — Event 提供
原子语义零成本，避开"V23 时回头改"的回炉。

### 选型 4：``StreamCancelled`` 与 ``KeyboardInterrupt`` 分家

| 异常 | 触发位置 | 期望行为 |
|------|---------|---------|
| ``KeyboardInterrupt`` | prompt 上 Ctrl+C | 退出 agent |
| ``StreamCancelled`` | 流式期间 Ctrl+C | 回到 prompt，不退出 |

main.py 的 SIGINT handler 用一个 ``streaming_active`` 旗标分流：

```python
def _sigint_handler(signum, frame):
    if streaming_active["flag"]:
        cancel_token.cancel()
    else:
        raise KeyboardInterrupt
```

源项目把这分得更细（``_interrupt_requested`` 三种语境），nano 一个 bool 够。

### 选型 5：Chain 流式失败策略 — "首帧前可切，首帧后必抛"

源项目 ``run_agent.py:7966-8082`` 的 ``deltas_were_sent`` 哨兵：已经吐过 token
后失败默认不重试（用户已经看见前半段，重试会重发同样的开头，UI 体感很糟）。

V22 chain 抄这个语义：

| 场景 | 行为 |
|------|------|
| 主家 ``stream_call`` 抛 → 没 yield 过任何事件 | 切下一家（用户感知"卡了一下后正常" |
| 主家 yield 过 ≥ 1 个事件后抛 | 不切家，原异常透传给上层 |
| ``StreamCancelled`` | 透传，**不**计为失败（不动断路器） |

这意味着 V22 流式不做单 entry 的 RETRYABLE 内部重试 — 同步路径的 jittered
backoff 在流式里没用（重试会重发 token）。这是流式的硬约束，不是简化。

### 选型 6：reasoning 不实时回显

DeepSeek/Kimi 的 thinking 模式会先吐一大段 ``reasoning_content`` 再吐正文。
源项目有个 ``reasoning box`` UI 把它分区显示。nano 简化：``reasoning_delta``
不实时回显，只在首次到达时打个 ``[think] ...`` 占位告知"模型在思考"，正文
``text_delta`` 到达时清掉这个占位。``reasoning_content`` 仍完整保存到
``NormalizedResponse.provider_data`` — 下一轮 messages 回传需要它。

## 真实踩坑

### 坑 1：context-compaction 后 main.py 顶部叠了重复 docstring

会话压缩恢复时第二次 Edit main.py 顶部 docstring 时，旧 docstring 没被
``old_string`` 匹配（因为 string 体太大、多行，patch 实际把新 docstring 叠在
旧的上方导致语法上文件有两段 docstring 串接）。Python AST 不报错（裸字符串
当无副作用表达式吃了），但 banner 显示成 V22 + 旧 V21 双段，导入照常。

修复：第二次 Edit 用更精准的小切片（"docstring 关闭 + import""block 整体"）替
换，验证手段是 ``wc -l main.py`` 看行数从 398 → 417 是合理增量（不是 ~100 重
复行）。

教训：跨 session 的大 docstring 替换永远比想象的脆。优先用最小 hunk + 在替换
后立刻 `python -c "import ast; ast.parse(...)"` + 行数比对兜底。

### 坑 2：测试 12 缺一个 V21.4 hook 同步

V22 加 ``/stream`` 命令后，V21.1 那个"启动期注册的命令清单等于固定集合"测试
立即红。expected 集合写死在 ``test_v21_slash.py``，新增命令必须同步进去。

修复：``expected`` 加 ``"stream"`` 一行，并在注释里写"V22 加 /stream"。

教训：硬编码"应等于这一组"的不变量测试，每次新增命令 / 工具 / 钩子都要回头
改 — 后续档（V23 多 agent 会加 ``/agents`` 等命令）也要记得同步。

### 坑 3：流式 + Anthropic input_json_delta 不必单独累计

第一稿想给 ``content_block_delta`` 的 ``input_json_delta`` 做 partial JSON
累积（仿 chat_completions 的 tool_call.arguments concat）。后来发现：
``stream.get_final_message()`` 返回的原生 Message 对象里 tool_use block 的
``input`` 字段已经是**完整 dict**（SDK 内部累积过了）。只要 done 时复用
``normalize_response(final_msg)`` 就 0 成本拿到完整 ToolCall.arguments。

教训：先看 SDK 给什么再决定要不要自己累。一行 ``stream.get_final_message()``
省掉 50 行手写状态机。
