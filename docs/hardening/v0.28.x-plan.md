## 2. v0.28.0 — 异常链 `raise ... from e`

**目标**：在 `except` 块内抛出**新类型**异常的地方挂 `from exc`，保住 traceback 因果链。不改任何控制流。

**背景知识**：
- `raise New(...) from exc` 把原始异常挂到 `__cause__`，traceback 显示完整链路（笔记 1.5 第 2 节）。
- **裸 `raise`（重抛原异常）不需要 from** —— 它本身就保留了链路。
- **不在 except 块里的 raise 不是候选**（如参数校验 `if not x: raise ValueError`，没有原始异常可挂）。
- 真正原因要挂 `from exc`；想**切断**噪音链才用 `from None`（本档基本用不到）。

**定位方法**（在新窗口第一步先跑这个，确认范围没漂移）：
```bash
cd /Users/qshf/my-project/nano_hermes_agent
# 找"在 except 块内 raise 新异常实例、且没挂 cause"的位置
grep -rn "raise " transports/ tools/ agent/ memory/ --include="*.py" | grep -v "from "
# 再人工确认每一处是否在 except 块内（不在 except 内的跳过）
```

**已知候选**（基于上次排查，新窗口需重新确认行号可能已漂移）：
- `transports/chain.py` — `raise FailoverExhausted(attempts)` 两处（同步 `call` ~L216、流式 `stream_call` ~L301）。它们在 `for entry` 循环耗尽后抛出，可考虑把**最后一次** classified 对应的原始异常挂上去。⚠️ 注意：FailoverExhausted 当前签名只收 `attempts` 列表，要挂 cause 需在循环里保留最后一个 `exc` 引用，再 `raise FailoverExhausted(attempts) from last_exc`。
- 其余 transports 里的 `raise ValueError(...)`（如 `chat_completions.py:303`、`anthropic.py:293`、`client_factory.py:47`）经确认**不在 except 块内**（是 validate/参数校验失败），**不属于本档范围**，别误改。
- `except StreamCancelled: raise` / `except ... : raise`（裸重抛）—— 正确写法，**保持不动**。

**范围红线**：本档**只**加 `from exc`，不重命名异常、不改异常层级、不动控制流。若发现某处该重构（如 FailoverExhausted 签名），记进 todo 留给后续档，本档不做。

**验证**：

## 3. v0.28.1 — 脏 JSON 解析错回喂 LLM 自修

**目标**：工具参数 / LLM 结构化输出解析失败时，把错误**作为 tool 结果喂回模型**让它自己改一轮，而非静默吞掉 / 直接 tool_error 终止（笔记 1.7 第 2 节 self-correction）。

**现状**（上次排查结论，新窗口需复核）：
- 两层容错已存在：`tools/registry.py:195` 附近 `json.loads` 接 `JSONDecodeError`（语法层）+ `isinstance(parsed, dict)` 检查（结构层）。
- **缺的是回喂**：错误被 log + 返回 `tool_error`，没给 LLM 重试机会。

**改动位置**：`agent/turn_loop.py` 的工具调用环节 + 可能 `agent/child_loop.py` 对称处理。把解析失败的错误信息（含 `e.errors()` 式的 loc/type 若有）拼成一条 tool 结果消息塞回 messages，让下一轮 LLM 修正。

**设计要点**：
- 要有**重试上限**（如同一 tool call 最多自修 1–2 次），否则模型可能反复给错 JSON 死循环。
- 错误消息要**可操作**：告诉模型期望的 schema 形状 + 具体哪里错了，而非只说"parse failed"。
- 区分语法错（可能是 LLM 输出截断 → 提示重发完整 JSON）vs 结构错（字段理解错 → 说清 schema）。

**风险**：这是**行为变更**，会改变 turn_loop 控制流和 messages 序列。务必单独成档、独立验证自愈真生效。

**验证**：
```bash
.venv/bin/python scripts/test_v21_4_tool_result_protocol.py   # 工具结果协议
.venv/bin/python scripts/test_v22_streaming.py
# 新增：写一个 test_v0_28_1_json_self_correction.py 构造一个故意返回坏 JSON 的场景，
#       断言 agent 把错误喂回后第二轮能修正成功
```
**本档需新增测试**（项目惯例每档 8–13 项不变量），放 `scripts/test_v0_28_1_json_self_correction.py`。

## 4. v0.28.2 — 高频对象开 `@dataclass(slots=True)`

**目标**：给流式高频创建的 dataclass 加 `slots=True`，长会话省 ~40% 单实例内存（笔记 1.4 第 8 节）。

**候选对象**（按创建频次，新窗口确认行号）：
- `transports/types.py` — `StreamEvent`（最高频，每个 token 一个）、`ToolCall`、`Usage`、`NormalizedResponse`。
- `agent/turn_events.py` — `TextPreview` / `PhasePreview` / `TurnEventEnvelope`。

**关键陷阱**（必须验证）：
- ⚠️ `ToolCall` 有 `@property`（`type`/`function` 返回 self，见 `transports/types.py:48`）。**`slots` 与同名 property 冲突**：若 slot 名和 property 名撞了会报错。开 slots 前确认 property 名**不在** `__slots__` 字段里（property 是类属性，不该出现在 slots 中，通常没问题，但务必跑测试确认）。
- ⚠️ slots 类**不能动态加属性**。检查代码里有没有对这些对象做 `obj.xxx = ...`（非 `__init__` 声明的字段）的地方。
- ⚠️ 继承链：若有子类没声明 slots，优化会失效（笔记 1.4 第 8 节继承陷阱）。

**做法**：逐个对象加 `slots=True`，每加一个跑一次测试，绿了再加下一个（别一次全加，撞 property 时难定位）。

**验证**：
```bash
.venv/bin/python scripts/test_v17_transport.py
.venv/bin/python scripts/test_v22_streaming.py        # StreamEvent 主场
.venv/bin/python scripts/test_v23_4_structured_result.py
.venv/bin/python scripts/test_v27_1_voice_orchestrator.py   # TurnEventEnvelope
# 可选：写个小基准证明内存收益（sys.getsizeof 对比 slots vs 非 slots）
```

## 5. v0.28.3 — 工厂统一 + 单例注释

**目标**：消除两套工厂模式不一致 + 给 registry 单例补"依赖单线程"说明（笔记 1.8）。

**两个机械改动**：
1. **`transports/client_factory.py:24` `make_llm_client` 改注册表**：现在是 if-elif-else（chat_completions / anthropic_messages），改成和 `transports/__init__.py` 的 `get_transport` 一样的 dict 注册表查表，消除开闭原则违背。
   - 可保留一份 if-else 版做**反面教材注释**（呼应笔记 1.8 工厂对比）。
2. **`tools/registry.py:59` 单例补注释**：`registry = ToolRegistry()` 是模块级单例，无锁。补一句注释说明**依赖单线程主循环假设**（子 Agent 在独立 child_loop 跑、不共享 registry 变更，所以安全）；若未来多线程并发 `register()`，`_tools` dict 写入有竞态。

**风险**：低。工厂改注册表要确保所有 client 创建路径都走新表（grep `make_llm_client` 找调用点）。

## 6. 不做的事（明确边界，防跑偏）

下面这些在 1.11 文档里讨论过，但**经分析是合理的教学取舍，0.28.x 不碰**：
- ❌ 顶层改 async —— 单用户串行负载下同步是正确答案，async 是过度工程（详见 1.11 第 3 节）。
- ❌ `deque(maxlen)` 替换语义压缩 —— 压缩保语义，是更高级方案，deque 至多作兜底，价值低。
- ❌ `weakref` 缓存 —— 工具就几十个，过度设计。
- ❌ `tracemalloc`/`gc.collect()` —— CLI 短命进程无所谓。
- ❌ 引入 Pydantic 替换 `coerce_args` —— 手写 coerce 更适合教学，不引重依赖。
- ❌ 重试逻辑抽装饰器 —— 收益低（项目工具 schema 手写，`wraps` 核心动机不存在），列为「以后想做再说」。
