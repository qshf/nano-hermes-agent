## 导览 `[核心]`

**【slide 正面】**

> **一条线分了三层，每层解决上一层暴露的问题：**

```
v0.6  存储：把要记的话写进一个文件
v0.7  抽象：MemoryProvider 契约（要换数据库/远程服务，主循环不能跟着改）
v0.8  调度：MemoryManager 编排多个来源 + 隔离错误
v0.9  时机：prefetch / sync_turn 生命周期钩子
v0.10 验证：做一个真用钩子的远程 HTTP provider
```

**【讲稿】**
记忆这条线最能体现"一次只解决一个问题"。我们不是一上来就设计一套华丽的记忆框架，而是：先用最笨的办法存文件能跑通；跑通了发现存储方式焊死在代码里，才抽出一个接口契约；有了多个来源才加调度器；有了调度器才定义"什么时候召回、什么时候记下"的时机。**每一档都只往前迈一小步，且都建立在上一步已经稳定的前提上。**

**【过渡】**
先看第一档 v0.6：不用数据库、不做召回，先用最笨的办法让它真的"记住"。

## v0.6 — 文件持久化记忆 `[核心]`

**【slide 正面】**

> 分支：`memory/v0.6`　核心文件：`tools/memory_tool.py`
>
> 第一版记忆，只做一件事：**跨会话保存少量长期事实**。

```python
class MemoryStore:
    def load(self): ...
    @property
    def snapshot(self) -> Optional[str]: ...
    def add(self, content: str) -> dict: ...
    def replace(self, old_text: str, new_content: str) -> dict: ...
    def remove(self, old_text: str) -> dict: ...

def memory_tool_handler(args: dict) -> str: ...
    if action == "add":
        result = _store.add(content)
    elif action == "replace":
        result = _store.replace(old_text, content)
    elif action == "remove":
        result = _store.remove(old_text)
    else:
        result = {"error": f"Unknown action: {action}"}

registry.register(schema=MEMORY_SCHEMA, handler=memory_tool_handler)
```

函数职责：

- `load`：从 `~/.hermes/nano_memory/MEMORY.md` 读取记忆，并生成启动时冻结快照。
- `snapshot`：返回要注入 system prompt 的记忆块。
- `add / replace / remove`：提供最小可用的记忆编辑能力，`replace/remove` 用 `old_text` 子串定位条目。
- `memory_tool_handler`：把模型传来的 `action` 分发到对应的记忆操作，并返回 JSON。

> 记忆点：**先让能力闭环，再谈抽象。**

**【讲稿】**
v0.6 没有复杂架构，只有一个 `MemoryStore` 和一个 `memory` 工具。类上只有五个对外入口：`load` 负责启动时加载，`snapshot` 负责给系统提示提供记忆块，`add / replace / remove` 负责编辑记忆。工具入口 `memory_tool_handler` 只做一件事：读模型传来的 `action`，分发到对应方法，再把结果包装成 JSON 返回。

这版还做了两个很小但重要的保护。
第一，记忆有字符上限，防止越记越多把上下文撑爆。
第二，启动时生成一份**冻结快照**：系统提示用这份快照，工具调用后的返回值显示实时状态。也就是说，"模型这一轮看到的记忆"和"磁盘上刚刚改完的记忆"不会在同一次调用里混在一起，状态更容易解释。

这一档的价值不是把记忆系统设计完，而是跑通最小闭环：**模型能主动调用工具写记忆，下次启动能读回来。** 跑通之后，问题才会暴露出来：如果以后记忆不在文件里，而在数据库、向量库、远程服务里，主循环难道都要跟着改吗？这就引出下一步的抽象。

**【过渡】**
v0.6 跑通了，但它也暴露了第一个架构问题：记忆逻辑写死在一个 tool 里。v0.7 开始把它拆开。

## v0.7 — MemoryProvider 契约 `[核心]`

**【slide 正面】**

> 分支：`memory/v0.7`　核心文件：`memory/provider.py` / `memory/builtin.py`
>
> v0.7 的重点不是新增功能，而是**把 v0.6 的记忆工具拆成可替换后端**。

```python
class MemoryProvider(ABC):
    @property
    def name(self) -> str: ...
    def is_available(self) -> bool: ...
    def initialize(self, session_id: str = "", **kwargs) -> None: ...
    def get_tool_schemas(self) -> list[dict[str, Any]]: ...
    def handle_tool_call(self, tool_name: str, args: dict[str, Any]) -> str: ...
    def system_prompt_block(self) -> str: ...
    def shutdown(self) -> None: ...

class BuiltinMemoryProvider(MemoryProvider):
    # 把 v0.6 的 MemoryStore 包成一个标准 provider
    @property
    def store(self) -> MemoryStore: ...
```

函数职责：

- `MemoryProvider`：定义所有记忆后端都要遵守的契约，主循环只认这层接口。
- `is_available / initialize / shutdown`：管理后端生命周期，给未来的远程服务、数据库连接留位置。
- `get_tool_schemas`：告诉模型这个 provider 要暴露哪些 memory 工具；没有工具的 provider 可以返回空列表。
- `handle_tool_call`：provider 自己处理属于自己的工具调用，不再走全局 `registry` 自注册。
- `system_prompt_block`：返回要注入系统提示的静态记忆内容。
- `store`：暴露底层 `MemoryStore`，给 `/memory` 这类直接查看记忆状态的命令使用。

**【讲稿】**
v0.6 的 `memory_tool.py` 里混着三件事：文件存储、工具 schema、工具调用分发。v0.7 做的就是拆职责：`tools/memory_store.py` 只保留纯存储；`memory/provider.py` 定义统一契约；`memory/builtin.py` 用 `BuiltinMemoryProvider` 把本地文件记忆包装成一个标准 provider。

Agent 的接入方式也变了。以前 `memory` 工具靠 registry 自注册；现在主循环先问 provider：你有什么工具 schema？模型真的调用 memory 时，再把调用路由给 `provider.handle_tool_call`。这一步还没有多 provider 编排，那是 v0.8 的事；v0.7 只是先把"以后能替换后端"这件事变成可能。

```python
# V7: 合并 provider 暴露的工具 schema
provider_schemas = memory_provider.get_tool_schemas()
all_tools_schema = tools_schema + [
    {"type": "function", "function": s} for s in provider_schemas
]
provider_tool_names = {s["name"] for s in provider_schemas}

# V7: 路由 — provider 工具走 provider，其余走 registry
if name in provider_tool_names:
    result = memory_provider.handle_tool_call(name, args)
else:
    result = registry.dispatch(name, args)
```

**【演示】**
`git checkout memory/v0.7`，看三个文件的职责边界：`MemoryProvider` 是契约，`BuiltinMemoryProvider` 是适配器，`MemoryStore` 是纯存储。再看 `agent.py` 里工具调用的路由：provider 工具走 provider，其余工具才走 registry。

**【过渡】**
有了 provider 契约，agent 还是直接拿着一个 provider。只要第二个 provider 出现，主循环又会开始变脏。v0.8 加一层 manager。

## v0.8 — MemoryManager 编排器 `[核心]`

**【slide 正面】**

> 分支：`memory/v0.8`　核心文件：`memory/manager.py`
>
> v0.8 的重点：**agent 只和 manager 对话，不再感知 provider 数量。**

```python
class MemoryManager:
    def add_provider(self, provider: MemoryProvider) -> None: ...
    def build_system_prompt(self) -> str: ...
    def get_all_tool_schemas(self) -> list[dict[str, Any]]: ...
    def has_tool(self, tool_name: str) -> bool: ...
    def handle_tool_call(self, tool_name: str, args: dict[str, Any]) -> str: ...
    def initialize_all(self, session_id: str = "", **kwargs) -> None: ...
    def shutdown_all(self) -> None: ...
```

函数职责：

- `add_provider`：注册 provider，并建立 `tool_name -> provider` 的路由表；内置 provider 总是允许，外部 provider 暂时只允许一个。
- `build_system_prompt`：收集所有 provider 的静态记忆块，拼进系统提示；单个 provider 出错时跳过。
- `get_all_tool_schemas`：统一收集 provider 暴露给模型的工具，并按工具名去重。
- `has_tool / handle_tool_call`：判断某个工具是否归 memory manager 管，归它管就路由到对应 provider。
- `initialize_all / shutdown_all`：统一初始化和关闭所有 provider，失败时只记录 warning，不拖垮主循环。

**【讲稿】**
v0.7 抽出了 `MemoryProvider`，但 agent 还是直接持有一个 `memory_provider`。这意味着第二个 provider 一来，agent 就要自己写"收 schema、判工具名、分发调用、捕获异常、合并结果"这些逻辑。v0.8 把这些事情收进 `MemoryManager`：agent 只问 manager 要工具 schema，只问 manager 这个工具是不是你管的，真正执行时也交给 manager 路由。

这一层的关键不是复杂，而是**隔离复杂**。`MemoryManager` 内部维护一张 `_tool_to_provider` 路由表，所以多个 provider 暴露工具时，主循环不用关心工具来自谁。每个 provider 的调用都包了错误隔离：某个记忆后端坏了，最多返回一个 JSON error，不影响其他工具继续执行。

这版还故意限制"最多一个外部 provider"。教学项目里这不是能力不足，而是边界控制：外部 provider 太多会让 tool schema 膨胀，也容易出现后端语义冲突。v0.8 先把编排形状立住，v0.9 再往这层上加生命周期时机。

**【演示】**
`git checkout memory/v0.8`，看 `agent.py` 的变化：初始化时 `memory_manager.add_provider(BuiltinMemoryProvider())`；发请求前用 `get_all_tool_schemas()`；工具调用时先问 `has_tool(name)`，归 manager 管才走 `handle_tool_call()`。

**【过渡】**
有了 provider 和 manager，还差一个关键问题：记忆后端应该在一轮对话的哪个时机做事？v0.9 把时机编进主循环。

## v0.9 — Agent Loop 生命周期集成 `[核心]`

**【slide 正面】**

> 分支：`memory/v0.9`　核心文件：`memory/provider.py` / `memory/manager.py` / `agent.py`
>
> v0.9 的重点：**把"何时召回、何时持久化"固定成生命周期。**

```python
class MemoryProvider(ABC):
    def on_turn_start(self, turn_number: int, message: str, **kwargs) -> None: ...
    def prefetch(self, query: str, *, session_id: str = "") -> str: ...
    def sync_turn(self, user_content: str, assistant_content: str, *, session_id: str = "") -> None: ...

def sanitize_context(text: str) -> str: ...
def build_memory_context_block(raw_context: str) -> str: ...
```

```text
用户输入
  → on_turn_start_all
  → prefetch_all：召回内容清洗后包进 <memory-context>
  → 把 recalled context + 原始输入 合成 user message
  → tool loop
  → sync_all：只同步原始 user 输入 + 最终 assistant 文本
```

函数职责：

- `on_turn_start`：每轮开始时通知 provider，可用于轮数统计、作用域管理、定期维护。
- `prefetch`：在模型调用前，根据用户输入召回相关记忆，返回要注入本轮上下文的文本。
- `sync_turn`：一轮结束后，把原始用户输入和最终助手回复持久化到记忆后端。
- `sanitize_context`：清理外部 provider 返回内容中伪造的 `<memory-context>` 标签和系统注释。
- `build_memory_context_block`：用唯一一对 `<memory-context>` 围栏包住召回内容，明确它是记忆上下文，不是新用户输入。

**【讲稿】**
v0.8 解决的是"谁来管 provider"，v0.9 解决的是"什么时候让 provider 做事"。这一步给 `MemoryProvider` 增加三个生命周期方法：每轮开始通知、模型调用前召回、每轮结束后同步。注意它们都是默认 no-op：内置文件记忆已经通过 `system_prompt_block` 一次性注入全部记忆，不需要每轮召回；真正会用到这些钩子的，是后面的外部语义记忆 provider。

`MemoryManager` 对应增加三个广播方法。它不是简单地把 provider 返回的文本拼进去，还做了一层安全处理：外部 provider 返回的内容先经过 `sanitize_context`，去掉可能伪造的围栏和系统注释，再由 `build_memory_context_block` 统一包成一段 `<memory-context>`。这相当于告诉模型："这是召回出来的参考记忆，不是用户刚刚新说的话。"

agent 主循环也在这一版定型：用户输入一到，先 `on_turn_start_all`，再 `prefetch_all`，把召回内容拼进这一轮的 user message；等 tool loop 结束，拿原始 user 输入和最终 assistant 文本去 `sync_all`。这里特意同步**原始输入**，不把围栏和召回内容写回记忆库，避免后端越存越脏。

**【演示】**
`git checkout memory/v0.9`，看 `agent.py` 的时序：`on_turn_start_all → prefetch_all → messages.append(user) → tool loop → sync_all`。再看 `memory/manager.py` 里的围栏辅助，强调召回内容进入 user message，而不是 system prompt。

**【过渡】**
这页顺手带出一个契约设计细节：为什么生命周期方法是默认空实现，而不是强制所有 provider 都实现？

## 设计点 A — 契约为什么留"空实现" `[核心]`

**【slide 正面】**

```python
class MemoryProvider(ABC):
    @abstractmethod
    def is_available(self) -> bool: ...      # 必须实现
    @abstractmethod
    def get_tool_schemas(self) -> list: ...  # 必须实现

    def prefetch(self, query) -> str:        # 默认空实现
        return ""
    def sync_turn(self, user, assistant):    # 默认空实现
        ...
```

**【讲稿】**
看这个契约：有的方法标了"必须实现"，有的给了默认的空实现。为什么不全部强制？因为最简单的"文件记忆"是一次性把全部内容塞给模型的，它**根本不需要**"每轮去召回"。如果强制所有实现都写 `prefetch`，那个最简单的实现就被迫写一堆空方法——**契约的复杂度会污染最简单的使用者**。默认空实现的意思是：只有真正需要召回的远程语义后端才去写它，简单的保持简单。

**这是一条可迁移的设计原则**：让接口的复杂度，对不需要它的人透明。

**【过渡】**
第二个决策，关于一个看不见但很烧钱的细节。

## 设计点 B — 一个决策省下真金白银 `[可选]`

**【slide 正面】**

> 召回的记忆，拼进 **用户消息**，而不是 **系统提示**。

```
系统提示(system prompt)：每轮都一样 → 能被模型缓存 → 省钱省时间
召回内容：每轮都在变 → 塞进系统提示 → 缓存全废
```

**【讲稿】**
模型 API 有个"前缀缓存"：开头那段每轮不变的内容可以缓存命中，又快又便宜。系统提示就是这段固定开场白。如果把"每轮都变"的召回内容塞进系统提示，缓存就整段失效了。所以项目特意把召回内容拼进用户消息，保住系统提示的稳定。**一个放哪儿的小决策，直接影响线上成本。架构决策从来不只是好不好看的问题。**

**【过渡】**
契约和时机都备好了，可前面没有一个 provider 真用到 `prefetch`/`sync_turn`——它们一直是空实现。v0.10 起，让这套钩子接上一个真正的外部记忆服务。

## v0.10 → v0.16 — 外部语义记忆服务 `[核心]`（高层带过，不逐档展开）

**【slide 正面】**

> 分支：`memory/v0.10 → v0.16`（7 档）　核心类：`RemoteSemanticProvider` + 一个独立的 mock memory server
>
> 这 7 档把"远程语义记忆"从 HTTP 形态一路做到生产级。一句话各自的着力点：

```
v0.10   HTTP 边界            provider 走 HTTP，服务端先用 dict + hash 向量占位
v0.10.1 真向量存储           pgvector + OpenAI 范式 embedding + LLM 事实抽取/去重
v0.11   知识图谱（Hindsight） 实体/关系/事实三层抽取 + 多策略检索 + reflect 合成
v0.12   异步 retain          后台 writer 线程，主循环写记忆 0 阻塞
v0.13   后台 prefetch 预热   上一轮结束就预热下一轮召回，近零延迟
v0.14   会话切换            /new /resume：drain 写队列 + 清缓存 + 轮转 session
v0.15   上下文压缩          对话超长时压缩，压缩前原文抢救进 retain 队列
v0.16   召回质量            retain 批量 + N-hop 图遍历 + 时间半衰减
```

> 记忆点：**契约一旦立住，后端可以从"假的 dict"一路换到"知识图谱 + 读写双异步"，主循环始终不动。**

**【讲稿】**
这一段我不逐档拆，只讲它整体证明了什么。前面 v0.6→v0.9 立的那套 `MemoryProvider` 契约 + 生命周期钩子，到这里才迎来第一个真正的"重度用户"——一个跑在另一个进程里的语义记忆服务。

挑四个关键跳跃说，每个配一段核心代码。

### 跳跃 ① 从假到真（v0.10 → v0.10.1）

先用 HTTP + 一个 dict 假后端验证"边界形态对不对"，跑通了再把存储换成 pgvector 真向量库、embedding 走 OpenAI 范式接口。**这一步换了整个存储引擎，provider 端业务逻辑一行没改**——这正是 v0.7 抽契约时承诺的"两端独立演化"兑现了。

v0.10 先造一个最简陋的外部记忆服务端：存储就是个内存 dict，embedding 用 md5 凑数。目的只有一个——**用最小代价验证 HTTP 边界形态对不对**，请求/响应字段定下来，provider 能正常发收。

```python
# scripts/mock_memory_server.py（v0.10）—— dict 存储 + md5 假 embedding，只为验证边界
def recall(req: RecallRequest) -> RecallResponse:
    q_vec = fake_embedding(req.query)
    scored = [(text, cosine(q_vec, vec)) for text, vec in bucket]
    scored.sort(key=lambda x: x[1], reverse=True)
    hits = [RecallHit(text=t, score=s) for t, s in scored[: req.k] if s > 0]
    ...

def sync(req: SyncRequest) -> SyncResponse:
    text = f"User: {req.user.strip()}\nAssistant: {req.assistant.strip()}"
    bucket.append((text, fake_embedding(text)))   # 内存 dict，进程一退就没
    ...

def fake_embedding(text: str) -> list[float]:
    """md5(text) → 16 维 float（每维 [0, 1]）。纯占位，无任何语义。"""
    digest = hashlib.md5(text.encode("utf-8")).digest()
    return [b / 255.0 for b in digest]
```

边界跑通后，v0.10.1 把后端整段换成真货——pgvector + OpenAI 范式 embedding。**关键是下面 provider 端的代码从 v0.10 到 v0.10.1 一行没动**，它只认 HTTP 契约：

```python
# memory/remote_semantic.py —— provider 端：后端是 dict 还是 pgvector，它都不知道也不关心
def _do_recall(self, query: str) -> str:
    payload = {"bank_id": self._bank_id, "query": query, "budget": self._budget}
    resp = self._client.post(f"{self._base_url}/recall", json=payload)  # httpx.Client
    resp.raise_for_status()
    results = resp.json().get("results") or []
    return "\n".join(f"[{i}] (score={h['score']:.3f}, {h['source']}) {h['text']}"
                     for i, h in enumerate(results, 1) if h.get("text"))

# scripts/mock_memory_server.py（v0.10.1）—— 服务端把 fake_embedding 换成真 embedding
def embed(text: str) -> list[float]:
    """OpenAI 兼容范式 —— DeepSeek/DashScope/vLLM 换 base_url 即可。"""
    kwargs = {"model": EMBEDDING_MODEL, "input": text}
    if EMBEDDING_DIM != 1536:
        kwargs["dimensions"] = EMBEDDING_DIM
    return _embedding_client.embeddings.create(**kwargs).data[0].embedding

# 检索从内存 cosine 换成 pgvector 的 <=> 算子（1 - 余弦距离 = 相似度）：
#   SELECT text, 1 - (embedding <=> %s::vector) AS cosine
#   FROM facts WHERE bank_id = %s ORDER BY embedding <=> %s::vector LIMIT %s
```

> 踩坑（已写进决策日志）：`init.sql` 写死 `VECTOR(1536)`（OpenAI 默认维度），但 DashScope `text-embedding-v3` 是 1024 维，直到第一次写入才以 "expected 1536 dimensions" 炸出来。修复是启动时读 `pg_attribute.atttypmod` 校验列维度 vs `EMBEDDING_DIM`，不一致就 fail-fast。**配置维度 vs schema 维度这种隐式约束，必须在启动期就拦。**

### 跳跃 ② 从向量到图谱（v0.11）

对标源项目 Hindsight，服务端把对话抽成"实体/关系/事实"三层知识图谱，检索时不止做向量相似，还能顺着实体关系做图遍历——"问 A 能召回 A 关联的 B 的信息"，这是图谱相对纯向量库的核心价值。还加了 `reflect`：不返回命中列表，而是跨记忆合成一段连贯回答。

### 跳跃 ③ 从同步到异步（v0.12 → v0.13）

`retain` 一次要 LLM 抽取 + 多次 embedding，2-5 秒。于是写路径丢给后台 writer 线程（主循环 0 阻塞），读路径在上一轮结束就预热好下一轮的召回（近零延迟）。**这两档正是吃到了 v0.9 把"召回/持久化"明确成生命周期钩子的红利**——时机点清晰，才好把它们挪到后台。

**写路径**：`sync_turn` 不直接打 HTTP，而是入队，后台单写者串行 drain。

```python
# memory/remote_semantic.py —— sync_turn 不直接打 HTTP，而是入队，后台单写者串行 drain
def _ensure_writer(self) -> None:
    if self._thread is not None and self._thread.is_alive():
        return

    self._thread = threading.Thread(
        target=self._writer_loop,
        name="demo-writer",
        daemon=True,
    )
    self._thread.start()
    print("[main] writer started")

def _enqueue_retain(self, payload: dict[str, Any]) -> None:
    """把一次 retain HTTP 调用包成 job 入队。"""
    def _do_retain() -> None:
        resp = self._client.post(f"{self._base_url}/retain", json=payload)
        resp.raise_for_status()

    self._ensure_writer()
    self._register_atexit()
    self._retain_queue.put(_do_retain)

def _writer_loop(self) -> None:
    """串行 drain retain 队列；sentinel 触发退出。"""
    while True:
        try:
            job = self._retain_queue.get(timeout=1.0)   # 周期性醒来查关闭标志
        except queue.Empty:
            if self._shutting_down.is_set():
                return
            continue
        try:
            if job is _WRITER_SENTINEL:
                return
            try:
                job()                                    # 真正的 HTTP retain
            except Exception as exc:
                logger.warning("retain failed: %s", exc) # 单 job 失败不杀线程
        finally:
            self._retain_queue.task_done()               # 让 queue.join() 可等
```

> 三个关键点：`timeout=1.0` 让线程能周期检查关闭标志、单 job 异常被吞下（写者必须活到 sentinel）、`task_done` 始终触发让 `queue.join()` 能 drain 干净。

**读路径**：v0.13 用两阶段预热。当轮 tool loop 一结束就 `queue_prefetch` 启后台线程去算下一轮的召回；下一轮真要用时，`prefetch` 直接取缓存——线程早跑完了，近零延迟。第一轮没有"上一轮"可预热，就走同步 fallback 兜底。

```python
# memory/remote_semantic.py（v0.13）—— 当轮结束：启动后台线程预热下一轮
def queue_prefetch(self, query: str, *, session_id: str = "") -> None:
    if self._memory_mode == "tools" or not self._auto_recall:
        return                                          # tools 模式不做隐式召回
    if self._shutting_down.is_set():
        return

    def _run():
        text = self._do_recall(query)                   # 后台真打 HTTP，结果存缓存
        if text:
            with self._prefetch_lock:
                self._prefetch_result = text

    self._prefetch_thread = threading.Thread(target=_run, daemon=True)
    self._prefetch_thread.start()

# 下一轮开始：消费缓存；冷启动 / 超时则同步 fallback
def prefetch(self, query: str, *, session_id: str = "") -> str:
    thread = self._prefetch_thread
    if thread is not None and thread.is_alive():
        thread.join(timeout=3.0)                        # 上限 3s，超了不死等
    with self._prefetch_lock:
        result, self._prefetch_result = self._prefetch_result, ""
    if not result:                                      # 第一轮无预热 → 同步兜底
        result = self._do_recall(query)
    return result
```

> 两条后台线程各管一头、互不相干：**writer 线程管写（retain，FIFO 串行）、prefetch 线程管读（recall，单次预热）**。生命周期不同，刻意不复用。第 2 轮起预热生效，主循环里召回几乎不花时间。

### 跳跃 ④ 从单会话到可运营（v0.14 → v0.16）

切会话时要先把写队列 drain 干净再轮转（不丢数据）；对话超长要压缩、且压缩前原文要抢救进记忆；最后把召回质量打磨到位——批量 retain、多跳图遍历、按时间半衰减给旧记忆降权。

**a) retain 批量缓冲**：N>1 时累积到第 N 轮才合并入队，服务端 LLM 一次看完整对话块。

```python
# memory/remote_semantic.py（v0.16）—— N>1 时累积到第 N 轮才合并入队，服务端 LLM 一次看完整对话块
def sync_turn(self, user_content, assistant_content, *, session_id=""):
    if not self._auto_retain or self._shutting_down.is_set():
        return
    turn_text = f"User: {user_content}\nAssistant: {assistant_content}"
    with self._buffer_lock:
        self._session_turns.append(turn_text)
        self._turn_counter += 1
        if self._turn_counter % self._retain_every_n_turns != 0:
            return                                       # 没到阈值 → 继续缓冲
        turns_snapshot = list(self._session_turns)       # 到阈值 → snapshot 后清空
        self._session_turns = []
    self._enqueue_buffered_retain(turns_snapshot, session_id=self._session_id)
```

> `on_session_switch` / `shutdown` 都会先 `_flush_buffer()`（把当前缓冲的 turn 立即入队）再 drain，否则缓冲里没入队的 turn 会丢——这是 v16 最容易踩的一致性坑。

**b) 召回质量：N-hop 图遍历 + 时间半衰减**（服务端）。从命中实体逐跳 BFS，按跳数染色，跳得越远权重越低；再叠加按更新时间的指数衰减。

```python
def _hop_weight(hop_distance: int) -> float:
    return 1.0 if hop_distance <= 1 else math.pow(HOP_DECAY, hop_distance - 1)

# 时间半衰减：age=0 → 1.0；age=half_life → 0.5
def _time_weight(age_days: float) -> float:
    if DECAY_HALF_LIFE_DAYS <= 0:
        return 1.0
    return math.pow(0.5, age_days / DECAY_HALF_LIFE_DAYS)

def _decay_blend(age_days: float) -> float:     # α=0 关闭衰减；α=1 完全跟随时间
    if DECAY_ALPHA <= 0:
        return 1.0
    return (1.0 - DECAY_ALPHA) + DECAY_ALPHA * _time_weight(age_days)

# 最终打分把三者相乘：final = cosine * _hop_weight(hop) * _decay_blend(age_days)
```

> α 混合让"关闭衰减"和"完全跟随时间"成一个连续旋钮，是教学项目刻意保留的可观测性——RecallResult 还会回吐 `cosine / hop / age_days / time_weight`，方便回答"为什么 A 排在 B 前面"。
