## 导览 `[核心]`

**【slide 正面】**

> **一档群（5 个小档），但有一条贯穿的主轴：派生子 Agent 是"加功能"，但这一幕真正的主题是"加约束"——能力边界的默认值，直接决定出事时的爆炸半径。**

```
痛点：V22 收尾后，单 Agent 能边想边说、能随时打断，但仍然单线程串行。
      "并行分析 A/B/C 三个文件并对比" —— 父只能连串调三次工具，每次阻塞 5–30s。
      前 22 档辛苦建立的"隔离质量"也没法被真实场景检验：父加一个工具会不会污染整个对话？

五个设计点（沿 v23.0 → v23.4 演进）：
  ① 三行权限    白名单 ∩ 父能力 − 黑名单，最后一步减；默认拒绝、最小权限、纵深防御
  ② 裁剪子循环  child_loop 单独一份精简文件，不复用父 1300 行 —— 差异在代码层一目了然
  ③ 并行 + 分层 主线程构建 / worker 跑 LLM / fail-fast 不半启动 / 白名单"至多包含"
  ④ cancel 桥接 父子共享同一个 CancelToken —— 兑现第五幕埋的 threading.Event 承诺
  ⑤ 结构化结果  子→父从"黑盒一行字"升级到 {"results":[...]} + 父子成本聚合
```

**【讲稿】**
第五幕的主题是"新功能不能污染已经证明对的路径"——流式走在同步路径旁边。第六幕换了一个维度：**新功能一旦能"派生自己"，第一件事不是让它跑得更快，是先想清楚它能干坏什么。** 子能不能再派生子子 Agent，无限递归把机器拖垮？能不能乱改父的记忆？这一幕的重点从"功能"明确转向"安全"——而最浓缩的表达，就是 v23.0 那三行权限计算。

**【呼应第五幕】**
第五幕结尾那句话现在要兑现了：`CancelToken` 当时特意用 `threading.Event` 而不是裸 `bool`，理由写的是"为 V23 多线程预留"。这一幕的设计点 ④ 就是接上那条线——父按一次 Ctrl+C，三个并发 worker 里的子 Agent 下一帧全部收到。**上一幕埋的抽象，这一幕零改动地用上了。**

**【过渡】**
先看这三行权限——它决定了整幕的底色。

## 设计点 ① 三行权限计算 — 出事时的爆炸半径 `[核心]`

**【slide 正面】**

> **解决**：子 Agent 能用哪些工具，不是"配出来的"，是"算出来的"——三步，每步都是一道安全闸。

```python
# tools/delegate_tool.py:_resolve_child_toolset —— 子允许集三步算出
allowed  = parent_full                       # 起点：父的全部能力
allowed &= set(requested)                     # ① 交集：白名单只能更少，不能更多
allowed -= {"delegate_task", "memory", "memory_*"}  # ② 减黑名单 —— 最后一步减
# ③ 真正 dispatch 前，child_loop 再查一次：子模型幻觉硬调，照样拦
if name not in allowed_tool_names:
    result = tool_error(f"tool '{name}' is not available to this sub-agent")
```

**【讲稿 · 金句】**
三行，三条安全原则，缺一不可：

- **第一，交集——权限只能收窄，不能放大。** 用户（其实是父 LLM）写的白名单先和父能力取交集。写了父没装的工具（`"nonexistent"`）静默丢弃，不报错——父偶尔会幻觉工具名，给个 hard error 反而让它连重试机会都没有。
- **第二，黑名单是最后一步减——而且强制。** 就算有人手滑把 `delegate_task` 写进白名单，交集之后照样被剔掉。**安全红线不能被配置绕过**：减黑名单放在交集之后，顺序本身就是纪律。
- **第三，dispatch 前再查一次——不信任上游。** 前两步是在"发工具清单给子 LLM"时算的；但子 LLM 可能幻觉一个清单外的工具硬调。所以 `child_loop` 在真正执行前，又拿 `allowed_tool_names` 验一遍。**纵深防御**：schema 层挡一道，dispatch 层再挡一道。

> 记忆点：把这套翻译成任何系统都通用的四个词——**默认拒绝、最小权限、纵深防御、约束不可被配置绕过。** 这对任何插件系统、多租户平台、任何"能加载第三方代码"的地方都成立。**能力边界的默认值，直接决定出事时的爆炸半径。**

**【真实细节 · 黑名单为什么是"精确名 + 前缀"双轨】**
源项目黑名单是 5 个精确名（`delegate_task / clarify / memory / send_message / execute_code`）。nano 没那么多工具，但黑名单写成了"精确名 + 前缀"两套：

```python
_DELEGATE_BLACKLIST_NAMES    = frozenset({"delegate_task", "memory"})
_DELEGATE_BLACKLIST_PREFIXES = ("memory_",)   # 兜底未来 hindsight 拆出的 memory_recall_v2 等
```

`memory` 是 nano 当前 memory 子系统暴露的**单一**工具名（V8 设计，dispatcher 内部按 args 路由 retain/recall/reflect）；前缀 `memory_*` 是给未来留的——源项目里 hindsight 把 memory 拆成了多个子工具，nano 暂未拆，但前缀匹配能让"未来拆分时无需回头改 delegate"。**为可扩展留位，但当下不滥用**——这条会在设计点 ⑤ 再出现一次。

**【过渡】**
权限算清楚了，子 Agent 跑在哪段代码里？这里有个和第五幕"正交路径"同构的选择。

## 设计点 ② 裁剪子循环 — 父子为什么不复用一份代码 `[核心]`

**【slide 正面】**

> **选择**：子 Agent 不复用父的 1300 行主循环，而是单独写一份不到 200 行的 `child_loop`，只留"调模型 → 跑工具 → 拼上下文"。

```
源项目 run_agent.py:run_conversation     nano agent/child_loop.py
──────────────────────────────────       ──────────────────────────
父子复用同一份 1300+ 行                    子是独立的 ~190 行纯函数
  子的"我不要 X" 靠 if 分支砍：             子的"我不要 X" 是结构性的缺席：
  if role == "leaf": skip streaming         它根本没拿 memory_manager 引用
  if role == "leaf": skip memory            它根本没 import compressor
  if role == "leaf": skip compress          它根本不碰 stdout UI
  ...                                        ...
优点：任何父能力子自动有                    优点：父子差异在代码结构上一目了然
缺点：父 if/else 分支爆炸                    缺点：子加新能力要两边各加一次
```

**【讲稿】**
源项目走"父子复用 `AIAgent.run_conversation`"，1300+ 行同时被父和子调用。这在生产环境**完全合理**——生产要求父子能力等价（流式 / cache / failover / trajectory / session 钩子全都要），共用一份代码是对的。

但这是个**教学版**，目标是讲清楚"父子的差异到底在哪"。如果差异埋在 `if role == "leaf"` 的分支里，它就看不见了。nano 单独写一个精简子循环，差异立刻变成**结构性的缺席**：

```text
子不调 memory_manager  → 因为它压根没拿这个对象（不是 if 分支跳过）
子不调 compressor      → 因为它压根没 import（任务短小，max_iterations=8 兜底）
子不打印 UI            → stdout 静默，progress 只走 stderr 侧路
子无 prefetch/sync_turn → 子没有会话生命周期
```

> 金句：**这就是"架构服务于场景"——同一个问题，教学场景和生产场景的最优解可以完全不同。** 子的"不能写 memory / 不能流式 / 不能压缩"不再是一句 `if role == leaf` 的禁令，而是"我没拿这个对象"的事实。教学叙事因此从"子被禁止做什么"变成"子能做什么"——**能清醒地做减法，和能做加法一样，都是本事。**

**【代价 · 诚实交代】**
裁剪不是免费的。代价是**子加新能力时要在父子两边各加一次**。但要看清这点重复的性质——它和第五幕"正交路径"的代价是同一种：

- 重复是**横向、隔离**的。v23.3 加流式中继、v23.4 加结构化结果时，改动范围天然限定在 `child_loop` + `delegate handler` 两处，**不溢出到 `main.py` 的父循环**（父循环行 502-625 全程没动）。
- 对比共用代码：在 1300 行热点函数里给子加特判，改的是父子共享、状态纠缠的代码，谁改谁担风险。

**什么时候这个选择会翻盘**：如果产品要求父子能力**严格等价**（生产环境），或子要支持父的全部钩子，那共用一份就是对的——源项目正是如此。nano 子能力受限、要可读、要让差异显形，裁剪是对的。**和第五幕一样，这是权衡，不是非黑即白。**

**【过渡】**
子循环有了。但 v23.0 的子只能一个一个串行跑——下一档要让它们并行，而并行立刻把"线程安全"摆上桌。

## 设计点 ③ 并行 + 分层 — 让并发只发生在该发生的地方 `[核心]`

**【slide 正面】**

> **解决**：v23.0 的子只能串行跑，"并行分析三个文件"反而比单 Agent 还慢。v23.1 加 `tasks: []` 数组 + `ThreadPoolExecutor`——但并发只放在一个地方，其余全是单线程。

```python
# tools/delegate_tool.py:delegate_task_handler —— 主线程构建，worker 只跑 LLM
for i, t in enumerate(tasks):          # ① 主线程逐条校验，任一不合法整体拒绝
    err = _validate_task_entry(t, idx=i)
    if err: return tool_error(err)     #    fail-fast：绝不"半启动"

with ThreadPoolExecutor(max_workers=...) as pool:
    results = list(pool.map(           # ② executor.map 保留输入顺序
        lambda it: _run_one_task(it[1], task_index=it[0], is_batch=True),
        list(enumerate(tasks)),
    ))
```

**【讲稿 · 三层纪律】**
v23.0 落地后立刻露馅：父 LLM 要"并行分析 A/B/C"，只能连串发起 3 次 `delegate_task`，每次父都阻塞等子完成——**承诺的"并发"在 v23.0 完全没兑现，反而比 V21 单 turn 串行 `read_file` 还慢**（多了 3 次子 system prompt 解析开销）。v23.1 把并发引进来，但守住三条纪律：

- **线程安全责任分层——构建期主线程独占，worker 不碰父状态。** `_resolve_child_toolset` / 校验 / system prompt 渲染**全在主线程做完**；扔进 `ThreadPoolExecutor` 的 worker 只做"调 LLM + 跑工具"这一件纯逻辑的事。worker 之间不共享可变状态，并发 bug 的面积就被压到最小。这和源项目"主线程构建循环 + worker 跑 LLM"语义一致。
- **fail-fast，绝不半启动。** 批量 5 个任务，第 3 个的 `tools` 写错——整个 `delegate_task` 直接 `tool_error`，**一个子都不启动**。为什么不"合法的先跑、错的报错"？因为父 LLM 一次给一个 batch 往往是"打包计划"，部分跑会让它以为"task#0/1 完成 = 计划完成"，对剩余任务做错决策；半启动还要给未启动任务一个 placeholder dict，凭空加协议复杂度。fail-fast 让父简单重派即可。
- **`executor.map` 而非 `as_completed`——保序优先。** map 天然按输入顺序返回，父 LLM 看到的 `task_index` 永远是 `[0,1,2]`，无须排序。代价是不能"边跑边收"，但 v23.1 不做进度中继（v23.3 才接），用不上这优势。

**【白名单语义辨析 · 与 V3 反向】**
v23.1 暴露的 per-task `tools` 白名单，语义和 V3 toolsets 挂载的"白名单"**正好相反**，这点容易混：

```text
V3 toolsets 白名单   "至少包含"   挂载哪些 toolset → 工具被加进来
V23.1 delegate 白名单 "至多包含"   最终生效集 = min(tools, parent_full) − blacklist
```

V3 是做加法（把能力装进来），v23.1 是做减法（在父能力内收窄）。**同一个词"白名单"，在能力扩张语境是上界、在安全收窄语境是上界——方向不同，别套用直觉。**

**【真实踩坑 · 两个并发暴露的 bug】**

- **`_FakeChain` 不是线程安全的。** v23.0 测试的 fake chain 用 `responses.pop(0)`，单线程 OK；v23.1 直接复用跑批量，3 个并发 worker 各 pop 一次，`pop(0)` 的"检查非空→pop"不是原子操作，第二个 worker 撞 `IndexError` → `RuntimeError: ran out of responses`。修复：fixture 加 `threading.Lock`。**教训：从上一档复制 fixture 不能复制完就跑——先想"本档新引入的并发会让哪些隐式假设失效"。**
- **父 loop 裸 `json.loads` 崩穿进程（真模型烟测发现）。** `child_loop.py:208` 早就用 `try/except json.JSONDecodeError` 把坏 args 翻成 `tool_error` 让 LLM 重试，但**父 loop `main.py:611` 是裸 `json.loads`**——流式拼帧的 args 偶发拼出无效 JSON（chunk 边界切在中文字符上 / 超长 `tasks[]` args），父进程直接崩，连"让 LLM 重试"的机会都没有。fake 测试的 args 都是手工构造的合法 JSON，永远 trigger 不到，**真模型 + 流式 + 复杂 args 三个条件凑齐才暴露**。修复：父 loop 与 child_loop 对齐 `try/except`，构造 `tool_error(raw_arguments=args[:500])` 让 LLM 看到自己写错了什么自行修正。

> 这个坑的元教训写进了测试：test 08 不仅验 `tool_error` 协议，**还反向 grep `main.py` 源码确认用的是 `json.JSONDecodeError` 而不是 catch-all `Exception`**——防止未来有人"为了稳定"把 except 范围改宽，把别的真 bug 也吞掉。**"fake 全过 + 真模型烟测发现新 bug" 是迭代项目的常态：fake 只能覆盖已知失败模式，真模型暴露未知组合。每档都要跑一遍真模型烟测。**

**【过渡】**
并行起来了，新问题随之而来：3 个子在 worker 线程里跑，父按 Ctrl+C 它们收得到吗？这就接上第五幕埋的那条线。

## 设计点 ④ cancel 桥接 — 兑现第五幕埋的那行 threading.Event `[核心]`

**【slide 正面】**

> **解决**：父外层流式（用户看到打字），子内层却走同步 `chain.call`——父一 delegate，UI 冻结 1-3 分钟；子死循环还 kill 不掉。v23.3 把"父 UI 不静默 + 子可立即 kill"一起做完。

```python
# 父子共享同一份 CancelToken —— 不各开
set_delegate_context(DelegateContext(
    chain=chain, model=model, parent_toolset_names=...,
    runtime=AgentRuntime(cancel_token=cancel_token,  # ← 就是 V22 父侧那个实例
                         stream_enabled=stream_enabled),
))

# child_loop 每轮 LLM 前 / 每个 tool 前 check —— 命中就退出
if _is_cancelled():
    return _build_result(exit_reason="interrupted", ...)
```

**【讲稿 · 呼应第五幕】**
第五幕设计点 ④ 说 `CancelToken` 用 `threading.Event` 而非裸 `bool`，理由写的是"为 V23 多线程预留"。现在兑现：

- **父子共享同一份 token，不各开。** 父侧 V22 已构造的 `cancel_token` 直接 setter 注入 `delegate_tool`，所有子 worker 拿这**同一个实例**。父 `cancel()` 一次，三个 worker 下一帧 `check()` 同步收到。`threading.Event` 本身跨线程原子可见，多线程同时 `check()`/`cancel()` 零成本——**这正是 V22 那行注释预留的场景，零改动用上。** 源项目要给子单独写 `child._interrupt_requested = True` + 一层"父→子"广播，是因为它的子不一定支持 streaming；nano 的 Event 天然省掉这层。

**【关键设计 · cancel 翻译成"软状态"，不重抛】**
子 loop catch `StreamCancelled` 后**翻译**为 `exit_reason="interrupted"` 返回 dict，**不让异常穿出 worker**：

```text
若让 StreamCancelled 抛出 worker → executor.map 整个迭代器在那条结果上抛异常
                                  → 已完成的兄弟子 summary 被一并丢掉
                                  → 违反 v23.1 "已完成的子结果不丢" 契约
翻译成软状态 → handler 能收齐 worker 的 dict,把线程池干净收口
            → 父 loop 发现共享 cancel_token 已触发,丢弃本轮 assistant/tool 主路结果
            → 回到 prompt；父 LLM 不继续读取这批 interrupted JSON
```

> 金句：**取消是"用户改主意了"，不是"出错了"。** 在 worker 层把它建模成结果里的一个状态字段,是为了让线程池有机会干净收尾；在父 loop 层再把同一个 cancel 翻译成"本轮作废,回到 prompt",避免父 LLM 继续基于半截子结果规划。这和第五幕"StreamCancelled 与 KeyboardInterrupt 分家"是同一种思路——**同一个 Ctrl+C，在不同层要翻译成不同语义。**

**【侧路输出 · progress 走 stderr 不污染主路】**
子的 `StreamEvent` 经 `progress_callback` → 写父 **stderr**，**不**进 `tool_result(output=...)`：

```text
主路 tool_result(output=JSON)  → 给"父 LLM"看，进对话历史 → 必须干净
侧路 stderr progress 行         → 给"用户"看，不进历史    → 可以是噪音
```

- **为什么不进 output**：progress 拼进 output，父 LLM 会误以为是工具返回内容，对话历史堆 noise，长期把 V20 的 cache 命中率打穿。
- **为什么 stderr 不是 stdout**：父侧流式正用 stdout 实时打字，子 progress 进 stdout 会和父对话流交织成一锅粥。
- **只取里程碑，不逐 delta。** `text_delta` / `reasoning_delta` 全静默——3 个 worker 各 yield 30+ delta，即便有 lock 也会把 stderr 刷成滚动条。只在 `tool_call_started` / `done` 回显一行就够用户知道"进度推进到哪"。
- **fan-in 用一把模块级 `threading.Lock`，不上 queue。** progress 行短（<200 字符）+ 频率低（仅里程碑），lock 争抢成本远低于一行 print；queue + 消费者线程要再开一个长生命周期线程 + shutdown 协议，对教学版"杜绝行交织"这唯一目的是杀鸡用牛刀。（对比第五幕迭代2 的 per-consumer queue——那是"真长出多消费者背压需求"才做；这里没有。）

**【真实踩坑】**

- **fake `time.sleep(5)` 测不出 cancel 传播。** 最初 fake 帧间一次性 `time.sleep`，test 卡 5s 才返回——`time.sleep` 不响应 Event，父 cancel 没法中途打断。修法：fake 内分片 sleep（每 50ms 一片）每片间 check token——真实 SSE 本来就是分片到达的，**分片 + check 才是 V22 cancel 模型的正确仿真**。
- **注入时序：`cancel_token = CancelToken()` 必须在 `_inject_delegate_context` 之前。** 最初顺序写反，setter 注入时 `cancel_token=None`，子永远拿不到父 token。setter 注入模式天生有时序耦合，和 v23.0 那个"toolset 缓存先于注入"是同一类坑。

**【过渡】**
父能管住子的"生死"了。但子回传给父的还是黑盒一行字——父根本不知道子吃了多少 token。最后一个设计点。

## 设计点 ⑤ 结构化结果 — 从"黑盒一行字"到 {"results":[...]} `[核心]`

**【slide 正面】**

> **解决**：v23.0~v23.3 子回传给父的是一行 summary 字符串。父 LLM 不知道子跑了几轮 LLM、用了多少 token、读了哪些文件、有没有工具失败。v23.4 把"子返回什么 + 父能看到什么"一起升级。

```python
# 单任务 / 批量统一返回 {"results":[...]} —— 父 LLM 永远 json.loads → r["results"][i]
tool_result(output=json.dumps({
    "results": [{
        "task_index": 0,
        "status": "completed",     # completed|max_iterations|interrupted|error 四态
        "summary": "...",
        "tokens": {"input":N, "output":N, "cache_read":N, "cache_write":N},
        "tool_trace": [{"tool":"read_file", "args_preview":"...", "result_bytes":1234, "status":"ok"}],
        "duration_seconds": 2.3, "iterations": 3, "exit_reason": "completed",
    }],
    "total_duration_seconds": 4.1,
}))
```

**【讲稿 · 协议统一是有意推翻】**
v23.0 故意留白："父 LLM 视角下子返回的就是一个字符串"——为的是给 v23.4 留一个痛点起点（"等等，子吃了多少 token？"）。v23.4 把它推翻：**单任务也走 results 数组（含 1 条），父 LLM 永远 `json.loads → r["results"][i]`，无单/批分支。**

- **为什么不保 v23.0 plain string 兼容**：保兼容等于让一半场景（单任务）拿不到 token / trace——这是"结构化"的反面；父 LLM 看两套 schema 才是真正的认知负担，统一一种最清晰。
- **代价诚实交代**：v23.0/v23.1/v23.3 测试里 10 处 `output == "hello"` 断言**会回归**。这是有意的协议演进，不是 bug——决策日志明确记录"v23.0 单任务 output 就是 summary 文本"这条约定被本档推翻的理由。**教训：协议升级的连锁影响要按"前档每个 fake chain 的形态"枚举，而不是按"前档测试数"**——v23.3 的两个 fake chain（流式 + 同步）各贡献几条断言，所以比预估多 2 处。

**【父子成本聚合 · 为什么子要 lock 父不用】**
子 worker 完成后把 token 累加到父 `runtime.session_tokens`（4 维：input/output/cache_read/cache_write）：

```python
# tools/delegate_tool.py:_accumulate_runtime_tokens —— 模块级 lock 保护
with _SESSION_TOKENS_LOCK:
    for k in SESSION_TOKEN_KEYS:
        runtime.session_tokens[k] += int(child_tokens[k])
```

> 为什么子要 lock、父不用？**父 turn 在 main loop 单线程里跑；子 worker 是 `ThreadPoolExecutor` 的并发线程。** `d[k] += n` 在 CPython 下是 LOAD/ADD/STORE 三步，GIL 只保单字节码原子，两个 worker 同时累加同一键会丢一次。这是"并发写共享 dict"的经典竞态，和设计点 ③ 的 `pop(0)` 是同一类。每子完成后**立即** finalize（不等批量整体结束），即使后续 worker 被 cancel，本子已写入的不丢。

**【几个克制的设计选择】**

- **session_tokens 挂 `AgentRuntime`，不新建 `SessionTokens` 类。** 当前只是 4 个 int 累加，加个 dict 字段足够；独立类是过度设计。AgentRuntime 已是父子共享真理源（`cancel_token`/`stream_enabled`），新累加字段加这儿语义自然延续。v24 trajectory 真要做历史落盘时再类化。
- **status 只 4 态，不含 timeout。** nano child_loop 没有真实超时机制（只有 max_iterations + cancel），引入 `threading.Timer` 会和 `CancelToken` 的"外部信号→内部退出"模式**双重事实源**。**诚实标注当前能力边界，比为对齐源项目硬塞 fake timeout 测试更有价值。** 但 `status` 与 `exit_reason` 双字段并存（当前完全冗余、同源）是**有意为 v23.5+ 保留**——如 `status="error"` 时 `exit_reason="failover_exhausted"`。**为可观测留扩展位，但当下不滥用**——和设计点 ① 黑名单前缀是同一条原则的第二次出现。
- **tool_trace 现场 append，不 post-hoc 从 messages 重建。** 源项目子完成后从 `result["messages"]` 扫描重建 trace（要 match `tool_call_id` 配对 assistant 与 tool 消息）。nano dispatch 时同时知道 `name`/`raw_args`/`result`，直接写一条——更关键的是**取消/异常路径下 messages 可能不完整，post-hoc 扫描会漏 trace；现场 append 不丢**。字段也裁剪：只留 `tool`/`args_preview`(截断 200 字节)/`result_bytes`/`status` 四个，完整 trajectory 留 v24。
- **`_build_result` helper 收口 7 处 return。** child_loop 有 7 个终止分支（自然完成 / max_iter / 4 类 except / 流式 done 帧缺失），新加字段若分散填，漏一处的概率是 7 倍。helper 让"加字段"只改一处签名 + 一处构造体，每条 return 上新字段必填。

**【过渡】**
五个设计点走完，回头看这一幕到底证明了什么。

## 这一幕证明了什么 `[核心]`

**【slide 正面】**

```
第五幕：契约不被污染 —— 加流式这个新维度，走在同步路径旁边
第六幕：能力即风险 —— 派生子 Agent 的第一件事是先想清楚它能干坏什么
        ① 三行权限    → 默认拒绝 / 最小权限 / 纵深防御 / 约束不可被配置绕过
        ② 裁剪子循环  → 父子差异是"结构性缺席"，不是 if role==leaf 的禁令
        ③ 并行 + 分层 → 主线程构建 / worker 跑 LLM / fail-fast 不半启动
        ④ cancel 桥接 → 共享 threading.Event，兑现第五幕的预留；cancel 是软状态不是异常
        ⑤ 结构化结果  → {"results":[...]} 统一协议 + 父子成本聚合（子 lock 父不用）
```

**【三条贯穿主线】**

1. **能力边界的默认值，直接决定出事时的爆炸半径。** 三行权限计算是整幕的题眼——任何"能加载第三方代码"的系统都该先算清楚"它最多能干什么"，而不是先让它跑起来。
2. **克制和扩张一样是本事。** 裁剪子循环、status 不塞 timeout、tool_trace 字段裁剪——每一处"不做"都标注了能力边界，并留了扩展位但不滥用。
3. **上一幕埋的抽象，这一幕零改动用上。** 第五幕 `threading.Event` 那行注释写"为 V23 预留"，v23.3 的 cancel 桥接一行没改地用上了——**演进主轴特有的叙事：好的抽象会在下一档自己证明价值。**

**【过渡】**
单 Agent 能边想边说、能打断；多 Agent 能并行、能管住、能算成本。但有个一直没解决的尴尬：关掉程序，整段对话就没了——子 Agent 跑的那些 token、那些 trace，下次启动一片空白。第七幕，给它装上"记得住"的能力。
