## v0.19

### 断路器机制
- 失败了，记录失败次数，切另一家服务
	- 当失败次数>=阈值。永久打开断路器
- 失败<阈值. 重试
	- 重试 在冷却窗口 跳过
	- 冷却窗口过了，重试一次，成功，关闭断路器

### jittered backoff：抖动防惊群

多个 session 同时撞上同一家故障，重试时刻会精确对齐，冷却到点的瞬间一起重试，把刚恢复的服务再打挂——这就是惊群。

```python
def _jittered_backoff(self, attempt: int) -> float:
    """base * 2^(attempt-1) + uniform(0, 0.5 * base * 2^(attempt-1))"""
    exponent = max(0, attempt - 1)
    delay = min(self.base_delay * (2 ** exponent), 60.0)   # 指数主体，封顶 60s
    jitter = random.uniform(0, 0.5 * delay)                # 0~50% 的随机抖动
    return delay + jitter
```

### 重试和切家

```python
for attempt in range(self.max_retries + 1):
	try:
		resp = entry.transport.call(entry.client, **call_kwargs)
		# V20: 累计 cache 统计 — usage.cached_tokens 已被 transport 标准化
		self._accumulate_cache_stats(entry, resp)
		return resp
	except Exception as exc:
		classified = classify_error(exc) # 错误分类 以此来区分是否 重试/切家
		attempts.append(classified)
		logger.warning(
			"transport=%s attempt=%d failed: action=%s reason=%s status=%s",
			entry.api_mode, attempt, classified.action.value,
			classified.reason, classified.status_code,
		)

		if classified.action == ErrorAction.FATAL:
			# 用户/输入问题 — 切了也是错，直接抛出
			raise

		if classified.action == ErrorAction.RETRYABLE and attempt < self.max_retries:
			delay = self._jittered_backoff(attempt + 1)
			logger.info("retry %s after %.2fs", entry.api_mode, delay)
			self._sleep(delay)
			continue

		# FAILOVER 或 RETRYABLE 用尽 — 这家算 1 次失败
		self._record_failure(entry, classified)
		return None
```

## v0.20

Anthropic  缓存机制和 OpenAI 的不一样

采用 **缓存策略属于 provider 差异**

```python
_MAX_BREAKPOINTS = 4    # Anthropic 单次请求最多 4 个 breakpoint

def apply_anthropic_cache_control(api_messages, cache_ttl="5m"):
    messages = copy.deepcopy(api_messages)     # 深拷贝，避免污染原始历史
    marker = {"type": "ephemeral"}
    if cache_ttl == "1h": marker["ttl"] = "1h"
    breakpoints_used = 0

    # 1 breakpoint @ system：每轮最稳定的前缀，命中率最高
    if messages and messages[0].get("role") == "system":
        _apply_cache_marker(messages[0], marker); breakpoints_used += 1

    # 其余 breakpoint @ 最后几条非 system 消息：滚动窗口
    remaining = _MAX_BREAKPOINTS - breakpoints_used
    non_sys = [i for i in range(len(messages)) if messages[i].get("role") != "system"]
    for idx in non_sys[-remaining:]:
        _apply_cache_marker(messages[idx], marker)
    return messages
```

![[Pasted image 20260604120109.png]]

- 源项目把流式做成 call 的内部分支，按 stream_callback != None 切路径，
	- 代价是一个 800+ 行的方法。
	- 针对每个事件类型写了一个callback
	
- nano 先做一个结构性选择：同步还是一进一出的 call，流式单独走 stream_call。
	- 代价是每个 transport 多写一条 SDK 调用；
	- 收益是 V17 到 V21 的 105 项同步不变量测试，一个字不用改。
	- 更关键的是：stream_call 的返回值可以被设计成"事件流"，而不必迁就 call 的单值返回。



nano版本代价是**每个 transport 子类要写两套 SDK 调用**(`call` + `stream_call`):

| transport | `call` | `stream_call` |
|-----------|--------|---------------|
| ChatCompletions | ~50 行 | ~100 行(含累积器) |
| Anthropic | ~40 行 | ~85 行 |
加第三家(如 Gemini)确实要再写一个 `stream_call`。但要看清这点冗余的**性质**:

- 冗余是**横向、隔离**的:每家一个独立文件,加 Gemini 不碰 agent loop、不碰 chain、不碰其它 transport,改动 O(1)。对比内部分支:加一家要去那个 800 行热点函数里塞特判,**改的是所有厂商共享、状态纠缠的代码**,谁改谁担风险。前者加法,后者乘法。
- 会不会脱节?`call` 的 105 项 + `stream_call` 的 13 项不变量测试互为防线,任一边改坏立刻红。

**什么时候这个选择会翻盘**: 厂商极多(几十家)且流式逻辑高度雷同 → 横向冗余累积,该抽流式基类模板;或产品根本不需要保留同步路径

class Consumer:
    def __init__(self, name, handle, *, maxsize, on_full):
        self.name, self.handle, self.on_full = name, handle, on_full
        self.q = queue.Queue(maxsize=maxsize)
        threading.Thread(target=self._run, daemon=True).start()

    def offer(self, ev):
        try:
            self.q.put_nowait(ev)        # 生产者绝不阻塞
        except queue.Full:
            self._on_full(ev)            # drop_oldest / drop_new / coalesce

    def _run(self):
        while True:
            ev = self.q.get()
            try:
                self.handle(ev)
            except Exception as exc:
                log_consumer_error(self.name, exc)

## Stream 如何和 Transport system 进行适配问题 ？

Transport system 实现的是非流式（关于切家+重试服务）

| 场景                | 行为      | 用户体感                                        |
| ----------------- | ------- | ------------------------------------------- |
| 首帧**之前**挂         | 切下一家    | "卡了一下后正常出字"                                 |
| 首帧**之后**挂         | 不切，异常上抛 | 半截真实内容 + 干净失败提示                             |
| `StreamCancelled` | 不动断路器   | [cancelled] (Esc / Ctrl+C — back to prompt) |

- 同步路径:模型整段写完才一次性显示,失败了在后台重试,用户**根本看不见**中间过程——重试是纯收益。

- 流式路径:每吐一小块就**立刻泼到屏幕上**,泼出去就收不回。这时候切到另一家,新模型从第一个字重新生成,但用户屏幕上已经有前半段了——新内容要么和旧的重复、要么对不上,**没有干净的办法把已显示的收回再重来**。

  ① 三行权限   白名单 ∩ 父能力 − 黑名单，最后一步减；默认拒绝、最小权限、纵深防御
  ② 裁剪子循环 child_loop 单独一份精简文件，不复用父 1300 行 —— 差异在代码层一目了然
  ⑤ 结构化结果 子→父从"黑盒一行字"升级到 {"results":[...]} + 父子成本聚合


# 从项目里抽出的软件工程经验

这个项目表面上是在重构一个 Agent，实际上一遍遍遇到的是同一类工程问题：

> 需求会变、能力会长、外部服务会挂、模型输出会脏、并发会把小问题放大。

所以最后想分享的不是"Agent 应该这么写"，而是这个项目真实留下的一套工程闭环：

```text
系统路线图            docs/system-roadmap.md
  └─ 拆分系统：每个系统负责什么、实现顺序、依赖关系、优先级
子系统迭代计划        docs/*-system/iteration-plan.md
  └─ 根据系统优先级，把每个系统拆成一档档可验证版本
每版本决策记录        docs/decisions/v*.md
每版本行为测试        scripts/test_v*.py
对外讲解材料          docs/值得讲的地方/*.md
```

> 代码只是结果；真正可复用的是"怎么把复杂系统一步步长出来"的过程记录。

## 这些经验具体对应什么

| 工程经验 | 项目里的具体证据 |
|------|------|
| 一次只解决一个问题 | `docs/system-roadmap.md` 先拆系统、排优先级、梳理依赖，每个子系统再写 `iteration-plan.md` |
| 抽象等第二个用例验证 | `v17` 先抽 Transport ABC，`v18` 接 Anthropic 验证主循环不动 |
| 决策要记录没选的路 | `docs/decisions/v*.md` 固定写"为什么选 / 为什么不选 / 怎么验证" |
| 测试守住行为底线 | `scripts/test_v17_transport.py` 到 `test_v25_1_insights.py`，每版一组 |
| 能力越大，边界越要清楚 | `v23.0` 黑名单、`v23.1` 白名单交集、`v23.4` 结构化结果 |
| 横切能力收进统一关口 | `ToolRegistry` hooks、`MemoryManager` 生命周期、日志脱敏 formatter |

## 每个版本都跑一遍这个循环

还有一个很现实的前提：

> 不可能在没做之前就设计出完美方案，也不可能一开始就写出完全可靠的方案。

路线图和迭代文档只能先给方向；真正的问题和 bug，是在代码迭代、测试、真实接入里被发现的。

```text
1. 上一版暴露一个具体痛点
2. 子系统迭代文档里切出最小版本
3. 代码只改这个最小切片
4. 写 scripts/test_vN_*.py，测对外行为
5. 写 docs/decisions/vN.md，记录取舍和坑
6. 旧测试重跑，确认零回归
7. 把新发现回写到路线图 / 决策文档 / 讲解材料
```

举几个具体版本：

```text
v12  异步 retain        → test_v12_writer.py
v19  Transport failover → test_v19_failover.py
v22  流式 + 中断         → test_v22_streaming.py
v23  父子 agent          → test_v23_*.py
v25  轨迹 + insights     → test_v25_*.py
```

> 每个版本都不是"按计划施工"，而是"用代码和测试校准计划"。

最后一句：

> **一次只解决一个问题，每步都站在上一步的稳定之上。**

希望大家带走的不是某个具体实现，而是一种节奏：

> 先定方向，小步演进，清楚边界，持续验证。
