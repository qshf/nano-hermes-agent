> 这一幕分 6 小页（v0.0→v0.5），是全场唯一"逐档拆开讲"的子系统——因为它是地基，且每一档都演示一个会贯穿全场的模式。时间紧时，至少讲 v0.0 / v0.1 / v0.5 三页。

## 导览 `[核心]`

**【slide 正面】**

> 分支：`tools/v0.0 → v0.5`（6 档）　核心类：`ToolRegistry`
>
> 一幕看完工具系统怎么从"几十行硬编码"长成"可插拔 + 自我保护"的地基：


**【过渡】**

## v0.0 — 最小可用版 `[核心]`

**【slide 正面】**

> 分支：`tools/v0.0`　几十行，两张手维护的表
>
> **问题**：模型说"我要调用 `read_file`"，程序怎么真去执行？

```python
# agent.py 里逐个 import 每个工具
from tools.terminal_tool  import TERMINAL_SCHEMA,  terminal_handler
from tools.read_file_tool import READ_FILE_SCHEMA, read_file_handler

TOOLS = [                       # 表①：给模型看的"说明书"清单
    {"type": "function", "function": TERMINAL_SCHEMA},
    {"type": "function", "function": READ_FILE_SCHEMA},
]
DISPATCH = {                    # 表②：名字 → 真正执行的函数
    "terminal":  terminal_handler,
    "read_file": read_file_handler,
}
handler = DISPATCH.get(name)    # 派发：查字典，没有就报 Unknown tool
```

**【讲稿】**
最朴素的 Agent 就是"模型 + 一张派发字典"。模型说要调 `read_file`，程序拿名字去字典里查到对应函数、真去读文件、把结果喂回模型。**这版能跑，派发本身也不丑——它已经是字典查表，不是一长串 if-else 了**。但你还是能闻到味道：要让一个工具能用，得在 `agent.py` 里改**三个地方**——顶部 import 一行、`TOOLS` 表加一行、`DISPATCH` 表加一行。两张表得手动保持同步，漏一处就出错；而且 `agent.py` 被迫认识每一个具体工具。**问题不在"派发"，在"工具的登记信息散落在主程序里、还得手动对齐"**。这正是下一档要解决的。

**【演示】**
`git checkout tools/v0.0`，让大家看整个 Agent 才几十行——一个能转的循环，长这么小就够了。顺手指一下那两张表 `TOOLS` / `DISPATCH`，强调"加工具要同时改两处"。

**【过渡】**
工具一多，两张表手动同步就容易出错。v0.1 用一张注册表 + 自动发现，把登记这件事还给工具自己。

## v0.1 — 注册表 + 自动发现 `[核心]`

**【slide 正面】**

> 分支：`tools/v0.1`　核心类：`ToolRegistry`

```python
registry.register(
    schema,    # 给模型看的"说明书"：名字、参数
    handler,   # 真正执行的函数
)
registry.dispatch(name, args)   # 主循环派发，只此一句
```

**【讲稿】**
把两张手维护的表换成一张注册表：每个工具在自己的文件里登记两样——给模型看的说明书、真正干活的函数。`agent.py` 顶部只剩一行 `import tools`，触发自动发现:扫描所有 `*_tool.py` 自动完成注册,主程序不再认识任何具体工具。主循环要派发,还是一句 `dispatch` 查表。**关键变化**：新增一个工具，只要在它自己的文件里登记一行，**主程序一个字都不用改**，也不存在"两张表漏同步"的隐患。工具从"登记信息散落在主程序"变成"自注册、被自动发现"。这是整个项目第一个、也是反复出现的模式——**注册表 / 可插拔**。后面的 Transport 层会原样再用一次。

**【过渡】**
但"有这个工具"不等于"这个工具现在能用"。比如 docker 没装，相关工具就该消失。v0.2。

---

## v0.2 — Toolsets + check_fn `[核心]`

**【slide 正面】**

> 分支：`tools/v0.2`　给 register 加第三个参数 `check_fn`

```python
registry.register(schema, handler,
    check_fn=lambda: shutil.which("docker") is not None,  # 现在可用吗？
)
```

> 字幕：**每轮重算"现在有哪些工具可用"** —— 故意暴露 check_fn 的性能开销

**【讲稿】**
真实环境里，工具的可用性是**动态**的：docker 没装、某个 API key 没配，对应工具就不该出现在给模型的清单里。所以给注册表加一个 `check_fn`——一个"现在能不能用"的探针。还把工具按用途分了组（toolsets）。

**这一档有个反直觉的决定**：它**故意每一轮都重新计算一遍"当前可用工具清单"**，明知道这有性能开销。为什么？因为 `check_fn` 可能要 fork 进程去探测环境，是有成本的。先把这个成本**暴露出来、让它可见**，下一步才知道该不该上缓存、缓存多久。**先把问题摆到台面上，再决定优化——而不是一上来就拍脑袋加缓存。** 这个缓存正是**下一档 v0.3 才补上的**（30 秒 TTL），下一页会讲——正因为先看见了开销，才知道缓存该设多久。

**【过渡】**
工具不光来自我们自己写的，还能来自外部。下一档 v0.3 做了两件事：接入一个标准协议，顺手把刚才那个性能开销用缓存收掉。

## v0.3 — MCP 集成 `[核心]`

**【slide 正面】**

> 分支：`tools/v0.3`　核心类：`MCPManager` / `MCPConnection`
>
> MCP = 一个让 Agent 接入"外部工具服务"的标准协议

```
我们自己写的工具  ┐
                  ├─→ 同一张 ToolRegistry ─→ 模型只看到统一的一张表
外部 MCP 服务的工具 ┘
```

```python
# tools/mcp_client.py —— 外部工具走的是同一个 register 入口
async def discover_and_register(self):
    for tool in await self._list_remote_tools():
        schema, handler = self._wrap(tool)   # 把远程工具包成本地 schema+handler
        registry.register(schema, handler)   # ← 和手写工具同一张表，主循环无感
```

**【讲稿】**
工具不该只能是"我们自己写在代码里的"。MCP 是个标准协议，外部服务可以通过它把自己的工具暴露出来。这一档把外部 MCP 工具也接进来——**关键是，它们注册进的是同一张 `ToolRegistry`**。模型完全不知道某个工具是我们手写的、还是从外部服务动态拉来的，它只看到统一的一张表。**这正是 v0.1 那层抽象的回报**：因为有了统一注册表，新增一个"工具来源"不需要动主循环，只要让新来源往同一张表里登记。

```python
# tools/registry.py —— check_fn 结果带 30s TTL 缓存
CHECK_FN_TTL = 30.0

def _is_available(self, name, entry):
    check_fn = entry["check_fn"]
    if check_fn is None:
        return True
    now = time.time()
    cached = self._check_fn_cache.get(name)
    if cached and (now - cached[0]) < CHECK_FN_TTL:   # 命中：直接复用
        return cached[1]
    result = check_fn()                                # 未命中：才真正探测（可能 fork 进程）
    self._check_fn_cache[name] = (now, result)
    return result

# register/deregister 时 _generation += 1，外层据此判断缓存是否失效
```

**【讲稿 · 收上一页的尾】**
这一档还顺手把上一页留的性能债还了：给 `check_fn` 加了一个 **30 秒 TTL 缓存**，再加一个 `_generation` 计数器——工具表没变化时，可用性探测的结果直接复用，不必每轮 fork 进程重算。**注意这个顺序：v0.2 先把开销暴露出来，v0.3 才上缓存。缓存设 30 秒，是因为先量过开销、知道它值多少，而不是拍脑袋。先测量，再优化。**

**【过渡】**
工具来源丰富了，新麻烦也来了：模型传参经常传错类型、有些工具还是异步的。v0.4 兜住这些。

## v0.4 — 类型矫正 + 异步桥接 `[核心]`

**【slide 正面】**

> 分支：`tools/v0.4`　核心模块：`tools/coerce.py`

```python
# LLM 常把数字传成字符串、把 true 传成 "true"
coerce_args(schema, {"count": "42"})  → {"count": 42}
# 按工具的 schema 自动修正；转不动就保留原值，绝不抛异常

# 有些工具是 async def，主循环是同步的 → 注册表负责桥接
result = _run_async(handler(args))
```

**【讲稿】**
两个很实际的脏活。第一，**类型矫正**：大模型经常把数字 `42` 传成字符串 `"42"`、布尔 `true` 传成 `"true"`。与其让每个工具自己防，不如在派发前按工具的 schema 统一修正一遍。设计原则很克制——**只在能确定该转时才转，转不动就保留原值、绝不抛异常破坏调用**。第二，**异步桥接**：有些工具是 `async` 的，但主循环是同步的，注册表负责把它们桥接起来跑。两件事的共同点：**把"脏"收在一个地方，让上层工具和主循环都保持干净。** 又是统一关口的思想。

**【过渡】**
最后一档，给这个注册表留出"别人能往里插逻辑"的扩展点。

## v0.5 — 插件钩子 pre/post/transform `[核心]`

**【slide 正面】**

> 分支：`tools/v0.5`　核心类：`HookManager`
>
> dispatch 一次调用，串起三个扩展点：

```text
dispatch(name, args) 不是"查字典然后调用"那么简单了，
它变成了一条稳定的工具调用管线：

① 查注册表      Unknown tool 直接返回错误
② coerce        按 schema 修正 LLM 传来的脏参数
③ pre_hook      执行前最后一道门，可 block
④ run handler   同步/异步统一桥接，并记录耗时
⑤ post_hook     只观察：日志、指标、审计，不改结果
⑥ transform     第一个字符串返回值可以改写工具结果
```

> 记忆点：**dispatch 是工具系统的统一关口。**
> 所有横切逻辑都进这条管线，单个业务工具保持干净。

**【讲稿】**
最后给注册表留三个钩子，但这页的核心不是"多了三个函数"，而是：**工具调用从一个动作，变成一条可治理的管线**。先在统一入口把参数矫正掉，再经过执行前的安全门，真正调用 handler，执行后把耗时和结果交给观察者，最后允许结果被统一改写。

为什么要这样排？因为像鉴权、限流、黑名单、日志、审计、脱敏这类**横切关注点**，几乎每个工具都要，但又不属于任何单个工具。如果把它们塞进每个工具，工具会越来越脏；如果放在 `dispatch` 这条管线上，业务工具一行不用改。**还记得第六幕子 Agent 的"执行前再查一次黑名单"吗？就是挂在 `pre_tool_call` 上的。** 这一档埋的扩展点，后面真的用上了。

每个钩子回调都有独立的 try/except 包着——**一个插件出错，不拖垮其他插件，更不拖垮主循环**。

**【演示】**
`git checkout tools/v0.5`，对比开篇的 v0.0：同一个工具系统，从"几十行 + 两张手维护的表"长成了"可插拔来源 + 自我保护 + 可扩展"的地基，但主循环的派发依然只是一句 `dispatch`。**复杂度被关进了注册表内部，没有漏给主循环。**

**【过渡】**
地基铺好了。但这个 Agent 有个致命缺陷：每次对话都失忆。第二幕，给它记忆。
