# Async Writer + Sentinel

这是一种很常见的后台任务处理方式。

核心目标只有一个：

- 主线程尽快返回
- 后台线程顺序处理慢任务
- 退出时尽量把已排队的任务做完

它适合这类场景：

- 记录日志
- 落盘缓存
- 发网络请求
- 写记忆、写索引、写审计记录

你可以把它看成一种“异步但可收尾”的结构。

## 先理解几个基础件

### `threading.Event`

`Event` 是线程间共享的状态标志。

它像一个开关：

- 初始是关的
- `set()` 后变成开
- `is_set()` 用来检查现在是不是开着

它的价值在于：多个线程都能安全地看同一个状态。

### `set()`

```python
event.set()
```

表示把状态打开。

常见语义有：

- 正在关闭
- 已准备好
- 允许继续

### `is_set()`

```python
event.is_set()
```

表示“现在是不是已经打开了？”

在后台写线程里，它通常用来判断：

- 是否已经进入 shutdown
- 是否该停止接收新任务
- 是否该退出空转循环

### `atexit`

`atexit` 是 Python 的退出钩子。

你可以注册一个函数：

```python
atexit.register(func)
```

程序正常结束前，Python 会尽量调用它一次。

它适合做兜底清理，不适合做复杂业务逻辑。

### `task_done()`

`queue.Queue` 里，任务有两个阶段：

1. 放进去
2. 取出来并处理完

`task_done()` 的意思是：

> 这个任务我已经处理完了

它和 `join()` 配套使用。

如果没有 `task_done()`，`join()` 永远不知道任务是否真的做完了。

### `join()`

`join()` 是“等一等，直到它结束”的意思。

在这个主题里，最常见的是两种：

```python
thread.join()
queue.join()
```

#### `thread.join()`

等待某个线程结束。

它常用于 shutdown 阶段：

- 主线程发出停止信号
- 然后等后台 writer 真正退出

例如：

```python
self._thread.join(timeout=self._join_timeout)
```

意思是：

> 等这个后台线程退出，最多等 `_join_timeout` 这么久。

注意：`join()` 只是等待，不会强行杀掉线程。

如果线程在超时前退出，`join()` 就正常返回；如果超时后线程还活着，`join()` 也会返回，线程本身可能还在继续跑。

所以 `timeout` 的价值不是“超时后杀死线程”，而是“不要让主线程永远卡死”。

例如后台 writer 正在做一个很慢的网络请求：

```text
shutdown()
  -> 发送停止信号
  -> 等 writer 退出，最多等 10 秒
```

如果没有 `timeout`，主线程可能永远停在 `join()`。加了 `timeout` 之后，程序至少能继续退出流程，并记录“后台线程没有按时停下”。

真正让 writer 退出的不是 `join()`，而是它自己在循环里收到停止信号后 `return`。`join()` 只是站在旁边等这个结果发生。

在 sentinel 模式里，关系通常是：

```text
shutdown()
  -> queue.put(SENTINEL)
  -> thread.join(timeout=...)

writer loop
  -> queue.get() 拿到 SENTINEL
  -> return
  -> 线程结束
  -> join() 返回
```

#### `queue.join()`

等待队列里所有任务都被处理完。

它要求每个 `put()` 进去的任务最后都配一个 `task_done()`。

如果你把它和 `task_done()` 连起来看，意思就是：

- `put()`：加入一个待办
- `task_done()`：这个待办做完了
- `join()`：等所有待办都做完

## 这个模式怎么拼起来

### 1. 主线程只负责投递

主线程不直接做慢活，而是把任务放进队列。

这样它能马上继续干别的事。

### 2. 一个后台线程顺序消费

只有一个 writer 线程处理队列。

好处是：

- 顺序稳定
- 逻辑简单
- 不容易并发打架

### 3. 用 sentinel 表示退出

队列里除了普通任务，还会放一个特殊对象，叫 sentinel。

writer 线程拿到它后，就知道：

> 后面不用再干了，可以退出了

这个做法比“靠外部强杀线程”优雅得多。

### 4. shutdown 先停收，再收尾

关闭时通常做两件事：

1. 标记系统正在关闭
2. 给队列塞一个 sentinel

然后等待后台线程把剩余任务处理完。

这里的“等待”通常就是通过 `thread.join(timeout=...)` 实现的。

它表示：

> 我给你一段时间收尾，你做完就退出，超时我也不会无限卡住。

这个设计是在“尽量不丢任务”和“不要退出时卡死”之间折中。

如果后台任务在限定时间内完成，shutdown 就很干净；如果后台任务卡住，主线程会放弃继续等待。此时如果 writer 是 daemon thread，进程退出时它会跟着消失，没做完的任务可能丢。

### 5. `atexit` 作为最后保险

如果正常流程忘了显式 shutdown，`atexit` 可以补一次。

它不是主路径，只是兜底。

## 为什么要这样设计

因为后台任务有两个矛盾的要求：

- 不能阻塞主流程
- 又不能一退出就全丢

这个模式就是在这两者之间找平衡。

它的策略是：

- 平时异步执行
- 退出时尽量 drain
- 实在等不及，就有限等待，不无限卡死

## 和 `remote_semantic.py` 的关系

你项目里的 V12 异步 retain 就是这套思路：

- `sync_turn()` 只入队，不同步发请求
- writer 线程串行调用 `/retain`
- `_WRITER_SENTINEL` 用来结束线程
- `threading.Event` 记录 shutdown 状态
- `atexit` 防止 CLI 直接退出时漏收尾

所以你看到的不是一个简单线程例子，而是一种可复用的后台写入架构。

## 什么时候会丢任务

这套模式不是“绝对不丢”。

以下情况仍可能丢：

- 进程被强杀
- 用户连续多次 `Ctrl+C`
- `join(timeout=...)` 超时后直接退出
- 线程里的 IO 自己卡死

所以它的承诺是：

> 尽量优雅，不无限等待

## 你可以记住的一句话

**队列负责排队，单 writer 负责顺序执行，Event 负责状态，sentinel 负责退出，atexit 负责兜底。**
